一句话讲清微服务：从「一个厨师全包」到「分工的厨房」

先用一个你一定见过的场景，把微服务这个词变具体。

单体应用 = 一个厨师又切菜、又炒菜、又洗碗。微服务 = 一个分工的厨房：配菜师傅只管配菜，炒锅师傅只管炒，洗碗工只管洗碗。

先看「单体」：一个人干所有活

小饭馆刚开业，只有一个厨师。点一份番茄炒蛋，他要先洗番茄、切番茄、打蛋、炒、装盘、最后自己洗碗。

问题出在哪？这三件事其实互不相干，但被捆在同一个人（同一个程序）身上：

  • 洗菜洗到一半，来了 5 桌客人点单 —— 全部排队，因为这个人腾不出手（功能之间互相拖慢）。
  • 切菜的速度是天花板，想快一点只能整体换一个更强的厨师（要扩容只能整体复制，不能只扩切菜这一块）。
  • 厨师切到手了，整个店今天都开不了张（一个地方出错，全店挂掉）。
  • 想请个擅长做甜点的师傅？没地方放，因为整个厨房就一个灶台（不能只给某个功能换技术）。

在 Java 里，这个"一个厨师"就是一个 war / 一个 jar，里面塞了登录、客户、会话、工单、AI、报表所有代码，所有功能共用一个进程、一个数据库连接池。

每个师傅只跟旁边的师傅"递盘子"（= 服务之间发 HTTP 请求），任何人请假只影响自己那一环，其他环节照常营业。

把比喻翻回技术，一句话定义

微服务 = 把一个大的程序，拆成若干个能独立运行、独立部署、独立扩容的小程序（服务）， 每个小程序只负责一件明确的事，之间通过网络请求互相调用。

餐厅里的说法技术里的说法
一个厨师全包单体应用（一个 jar 跑所有功能）
配菜师傅 / 炒锅师傅 / 洗碗工一个个独立的服务（auth、ticket、report…）
师傅只干自己那份活服务职责单一，自己的数据自己管（数据库也分开）
递盘子、喊一声"菜好了"服务间调用（HTTP / OpenFeign）
谁忙给谁加人手独立扩容（某个服务单独多起几个实例）
师傅请假只影响他那一环故障隔离（一个服务挂了不等于全站挂）
前台接待客人、叫单、拦闲杂人API 网关（统一入口）
厨房里的通讯录 / 公告板服务注册发现 / 配置中心（Nacos）
记住这一句 微服务就是把"一个人干所有活"改成"分工协作 + 谁忙给谁加人"；好处是各干各的、互不拖累，代价是原来喊一嗓子的事，现在得打电话（发 HTTP 请求）。

单体 vs 微服务 对比表

这张表面试至少会被问到其中一半，建议整张读熟，不用背字面，记住每行的"关键差别"就行。

对比维度单体应用（一个厨师全包）微服务（分工的厨房）
代码组织 一个工程里所有模块同进同出，改一行登录代码也要整体编译打包；代码越写越大，新人不知道从哪看起 按业务拆成多个工程，一个服务一个仓库/一个模块；看工单就只打开 ticket 服务的代码，改动范围天然被框住
部署方式 整体打包成一个 jar/war，任何一个小改动都要全量重新部署，上线像"全店停业装修" 每个服务单独打包、单独上线；改报表只重启 report 服务，会话服务一秒都不用停，可以按服务灰度发布
扩容 只能整体复制（多买几个"全能厨师"），你只想扩 AI 问答，却被迫连报表也一起复制，钱花在没用的地方 按需扩容：AI 服务吃紧就多起 2 个 ai 实例，报表服务一个实例够用就一个，资源花在刀刃上
故障影响范围 一个死循环、一次 OOM，全站一起挂；报表把数据库连接池占满，登录都进不去 故障被关在一个服务里：report 挂了，顾客照样能聊天、坐席照样能建工单；再配熔断降级，坏掉的那一环直接走兜底
技术栈自由度 只能一套技术栈到底，升级框架要全店一起动，风险评估起来让人头大 每个服务可以选自己合适的（AI 服务用 Python + LangGraph、报表用别的都行），新技术先在一个小服务里试，试错成本低
运维复杂度 简单：一个进程、一份日志、一个部署脚本，出问题登一台机器就够 复杂多了：要注册中心、网关、配置中心，还要监控一堆实例、看分布式日志；7 个服务就是 7 份日志
排查问题 一次请求全在一个进程里，打个断点、看一份日志就能顺着走完，堆栈清清楚楚 一次请求跨了 5 个服务，日志散在 5 台机器上，没有链路追踪（traceId）根本拼不出一条完整路径
数据管理 一个库、一张事务就能搞定，本地事务 ACID 免费得到 每个服务自己的数据自己管，没有跨服务的大事务了，"扣库存 + 建工单"要自己保证最终一致（消息、对账、补偿）
团队协作 人少时最舒服；人一多，所有人改同一个仓库，合并冲突、互相等对方上线 一个服务一个小组负责，边界清楚，可以并行开发互不阻塞；但要约定好接口契约，不然联调扯皮
网络与延迟 方法调用走内存，纳秒级，不会失败 跨服务调用是网络 IO，毫秒级，而且会超时、会失败、会重试，必须防着重试打爆下游
适合场景 创业早期、需求没稳定、团队 1~5 人、访问量不大 —— 先用单体跑起来才是对的 团队十几人以上、模块负载特征差异大（长耗时 AI / 重查询报表 / 实时会话）、需要按模块独立扩容和发布
一句话挑明：单体不是"落后"，微服务不是"高级"。单体解决不了的是团队规模和负载差异这两件事 —— 人多了会互相挤，负载差异大了会互相拖。这两个问题出现了，拆才有意义。
记住这一句 单体和微服务不是对错问题，是规模问题：人少、量小、需求还在变，单体最省钱；团队大了、模块负载差得远了，才值得付微服务那份运维代价。

七个核心名词（每个都配一张图）

这七个词是微服务的"骨架"。每个都按同一套模板讲：是什么 → 打个比方 → 在我们项目里干嘛。

1

服务注册与发现

Nacos＝ 公司通讯录
图 3-1 ｜ 通讯录
auth-service10.0.0.11:8081
ticket-service10.0.0.15:8084
📖 Nacos 通讯录谁上线就登记，谁下线就划掉
ai-service"ticket 在哪？"
拿到地址10.0.0.15:8084
是什么每个服务启动后，主动把自己的"名字 + IP + 端口"登记到一个公共的地方（注册中心）；别的服务要调用它，就问这个公共地方要地址，而不是把 IP 写死在代码里。
打个比方公司通讯录。新同事入职自动进通讯录，离职自动划掉。你要找财务，先翻通讯录拿分机号，而不是背下每个人的工位号 —— 因为座位会换、人会走。
项目里干嘛7 个服务全部注册到 Nacos。这样测试环境、生产环境 IP 不一样不用改代码；某个服务多起了 2 个实例，也会自动出现在通讯录里，调用方立刻就能用上；某个实例挂掉，Nacos 心跳超时会把它摘掉，请求不会再打到死机器上。
# 服务自己登记（application.yml 里两行配置的事）
spring:
  cloud.nacos.discovery:
    server-addr: 127.0.0.1:8848
    service: ticket-service   # 我在通讯录里的名字
面试延伸（会被追问）："如果 Nacos 挂了怎么办？" —— 已经拿到的地址会缓存在本地（本地缓存 + 定时拉取）， 已建立的调用不会立刻断；Nacos 本身也要做集群（3 个节点起），不能单点。

Spring Cloud Gateway＝ 公司前台 / 保安
图 3-2 ｜ 前台分流
网页 H5
小程序
坐席台
🚪 网关（唯一入口） 验 JWT · 限流 · 路由 · 注入客户身份 · 记日志
auth
conversation
ticket
外面的世界只看得见这一扇门
是什么所有外部请求的唯一入口。它挡在最前面，先做统一的事（验身份、限流、记日志），再按路径把请求转发给后面正确的服务。
打个比方公司前台兼保安。所有访客必须先在前台登记（验身份），前台问清你找谁（路由），然后指路或打电话叫人；门口还贴着"每人每天最多来 3 次"（限流）。没有前台，访客就得自己在大楼里乱窜，每个部门还得自己配一个保安。
项目里干嘛顾客和坐席的所有 /api/** 请求都先到网关：1）解析 JWT 拿到 userId / tenantId / roleId，塞进请求头带给下游（下游就不用各自再验一遍）；2）按前缀路由，/api/tickets/** → ticket-service，/api/ai/** → ai-service；3）对登录接口限流防爆破；4）内部接口 /inner/** 一律不放行，只允许服务之间互相调，外面的人打不进来。
# 网关路由：一句话说清"什么请求给谁"
routes:
  - id: ticket
    uri: lb://ticket-service   # lb = 去通讯录里找，并做负载均衡
    predicates: [ Path=/api/tickets/** ]
为什么需要它：没有网关，7 个服务就要各自实现一遍"验 token、限流、记日志、跨域"，改一次规则要改 7 个地方， 而且每个服务都得暴露在公网上，等于大楼每个房间都开一扇临街的门。
3

服务间调用

OpenFeign＝ 同事之间打电话（本质就是 HTTP 请求，没有魔法）
图 3-3 ｜ 一个请求的真实样子
ai-service"我要检索知识"
📞 一通"电话" POST /inner/knowledge/search (HTTP/1.1) Host: knowledge-service · Content-Type: application/json { "question": "怎么退货", "topK": 5 }
knowledge-service返回 JSON：5 段知识 + 分数
没有共享内存、没有共享事务、只有"发一个 HTTP、等一个 JSON"
是什么一个服务要去用另一个服务的能力时，就发一个 HTTP 请求过去。OpenFeign 只是把这个 HTTP 请求包装成"像调用本地方法一样"的写法，让你少写样板代码。
打个比方同事之间打电话。你不需要知道对方坐在哪、用什么姿势接电话，你只要拨号、说清要什么、等一个答复。Feign 就是帮你自动拨号的那个"语音助手"，但电话线那头还是电话线，不是心灵感应。
项目里干嘛AI 服务要检索知识库，就在代码里写一个接口加个注解，调用它跟调用本地方法一样自然；底层 Gateway/Feign 会去 Nacos 查地址、发出真正的 HTTP 请求、把 JSON 转成对象返回。
// 1) 声明"我要打的电话号码本"
@FeignClient(name = "knowledge-service")   // name 就是 Nacos 里的服务名
public interface KnowledgeClient {
    @PostMapping("/inner/knowledge/search")
    List<Chunk> search(@RequestBody SearchReq req);
}

// 2) 用起来跟本地方法一模一样，但其实已经发了一次 HTTP
List<Chunk> chunks = knowledgeClient.search(new SearchReq("怎么退货", 5));
重点强调（面试官最爱在这儿挖坑）：Feign 没有任何魔法，它就是一个 HTTP 客户端。 所以你必须自己想到：会超时（要配 connectTimeout / readTimeout）、会失败（要配重试或降级）、 会有序列化开销、会受网络抖动影响。答出这几句，说明你真的理解而不是背概念。

负载均衡

Spring Cloud LoadBalancer＝ 前台把客人分给空闲的同事
图 3-4 ｜ 三个实例，轮着来
ai-service"知识库服务给我一个地址"
LoadBalancer从 Nacos 拿到的 3 个地址里挑一个
实例 A本次选它 ✅
实例 B下次
实例 C再下次
默认轮询；也可以配"同机房优先""响应快的优先"
是什么同一个服务往往起了好几个实例（为了扛并发），当调用方拿到一串地址时，得有个规则决定"这次打哪一个"，这个规则就是负载均衡。
打个比方前台看到 5 位同事都能办这个业务，会挑一个手上活最少的客人交过去，而不是全塞给同一个人。要是有位同事今天不在（实例掉了），前台也不会再把客人指给他。
项目里干嘛conversation 服务要调 ai 服务，ai 起了 3 个实例，LoadBalancer 默认按轮询分发，压力自然摊平；某个 ai 实例挂了，Nacos 把它摘掉后，调用方下一轮就不会再选它，用户基本无感。网关里写的 lb://ticket-service 里的 lb 就是这个意思。
和 Nginx 的区别（会被问）：Nginx 是站在门口做负载均衡（外部流量进不来它不知道）； LoadBalancer 是服务自己内部做负载均衡（ai 调 knowledge 这种服务间调用，请求根本没经过 Nginx，只能靠它）。
5

熔断降级

Sentinel＝ 同事请假了，前台当场给个说法，别让客户干等
图 3-5 ｜ 熔断的三个状态
knowledge-service 挂了 / 变慢请求大量超时
🔌 Sentinel ① 关闭（正常放行） ② 打开（错误率超阈值 → 直接不调了，走兜底） ③ 半开（过一会儿放 1 个请求试探，通了就恢复）
兜底返回（降级）"知识库暂时查不到，我先帮您转人工"
对比：不熔断 = 客户干等 30 秒最后报错
是什么下游服务出错或变慢时，调用方快速失败，不再傻等，先返回一个提前准备好的"兜底答案"（降级），避免自己的线程被拖死，也避免把下游压垮。
打个比方某位同事今天请假了。前台不会让你在门口站半小时等他想办法，而是当场告诉你："今天这个业务办不了，我帮您转人工柜台。"客户立刻得到明确答复，前台也不会被一堆干等的客户堵住。
项目里干嘛AI 服务调知识库检索是最容易出问题的一环（向量库慢、模型超时）。我们给它配 Sentinel 规则：1 秒内如果超过 50% 的请求失败，就熔断 10 秒；熔断期间 ai-service 直接走降级逻辑 —— 不硬答，而是返回"我先帮您转人工"并触发转人工流程。这样顾客不会卡住，ai-service 的线程也不会因为等知识库而耗尽（一个线程被卡住，整台机器的并发能力就少一分）。
// 降级方法：名字、参数、返回值都要和被保护的方法一致
@SentinelResource(value = "kbSearch", fallback = "kbSearchFallback")
public List<Chunk> search(String q) { return knowledgeClient.search(q); }

public List<Chunk> kbSearchFallback(String q, Throwable t) {
    log.warn("知识库检索被熔断/降级，question={}", q);
    return Collections.emptyList();   // 空结果 → 上层判定为"无依据" → 转人工
}
一句话区分两个词：熔断是"不再调了"（对下游的保护动作），降级是"调不了就给个备选答案"（对用户的兜底动作）。 实践中一般是一起出现：熔断触发 → 走降级。

配置中心

Nacos Config＝ 公司公告板，改了所有人立刻看到
图 3-6 ｜ 公告板
📋 Nacos 公告板 ai-service.yaml： llm.timeout = 4000 transfer.keywords = 投诉,人工,退款 sentinel.flow.qps = 50

是什么把配置（数据库地址、第三方密钥、超时时间、阈值、开关）从代码里搬出来，集中放在一个地方统一管理，改完能让服务不重启就生效。
打个比方公司公告板。以前通知一件事要挨个进办公室喊（= 改配置 + 重启每个服务，7 个服务就是 7 次）；现在往公告板上一贴，所有人抬眼就看到了（推送到各个实例，动态刷新）。
项目里干嘛大模型 API Key、超时时间、转人工关键词、Sentinel 限流阈值、知识库召回 Top-K 这些都会变的东西都放 Nacos Config。比如大促期间要临时降低 AI 并发、或者换个模型供应商 —— 在 Nacos 改一下发布，几秒内所有实例生效，不用挑个深夜做一次全量发布。另外测试/生产环境各一套配置，代码一份不带改。

链路追踪

traceId / SkyWalking / Sleuth＝ 快递单号，能查到每一步卡在哪
图 3-7 ｜ 一个单号走完全程
traceId = 7f3a91c2… 顾客问一句"我要退货"
① gateway生成 traceId，往下传 · 2ms
② conversation收消息落库 · 12ms
③ ai-service意图识别 · 380ms
④ knowledge 🐌向量检索 2300ms ← 卡在这
⑤ LLM 生成1600ms
拿 traceId 一搜，五段日志拼成一条时间线
是什么给一次完整的用户请求发一个全局唯一的编号（traceId），这个编号会跟着请求一路传到它经过的每一个服务，每个服务打日志时都带上它。这样一次跨 5 个服务的请求，能用这个号把所有日志拼成一条完整时间线。
打个比方快递单号。包裹经过多少中转站、每个站停了多久，扫一下单号全看得见。要是没有单号，你只能一个个站点去问"你有没有见过我的包裹"—— 那就是在 7 个服务的日志里瞎翻。
项目里干嘛顾客抱怨"AI 答一句话要 4 秒"，以前只能靠猜；现在拿顾客那次的 traceId 一查，立刻看到时间花在哪：gateway 2ms、conversation 12ms、意图识别 380ms、向量检索 2300ms、大模型 1600ms —— 瓶颈一眼锁定在知识库检索。这就是链路追踪的价值：把"感觉慢"变成"知道慢在哪"。
怎么落地的（能被追问）：网关生成 traceId 放进请求头（如 X-Trace-Id）， 下游服务用拦截器把它放进 MDC，日志格式里带上 %X{traceId}，Feign 调用时自动透传， 再把日志收进 ELK / SkyWalking 里按 traceId 聚合查询。
记住这一句 七个词一句话串起来：服务上线先去通讯录（Nacos）登记；外部请求只走前台（网关）； 服务之间打电话（Feign，本质是 HTTP）；前台从多个同事里挑一个（负载均衡）； 同事请假就当场给客户个说法（熔断降级）；参数变了贴公告板（配置中心）不用重启；出问题靠快递单号（traceId）查卡在哪。
4

这个项目的 7 个服务（逐个说清）

项目是给企业客户做的「云联客服工单平台」：顾客从网页/公众号进来问问题，AI 先接待，答不了转人工坐席，坐席可以建工单走流程，所有数据进报表。 下面 7 个是业务服务；网关是入口层（门卫），不算业务服务，所以业务服务是这 7 个。

每个服务都有自己的库（或自己的表组）+ 自己的实例数：会话服务要横向扩（连接多），报表服务一个实例就够（跑得慢但没人等）。
auth-service认证授权JWTRBAC
职责一句话管"你是谁、你能干什么"：登录发令牌（JWT），校验令牌，按角色控制权限。
关键表sys_user（坐席/用户）、sys_role、sys_permission、sys_role_permission
暴露接口POST /api/auth/login（返回 JWT，里面带 tenantId/userId/roleId）、POST /api/auth/logout、GET /inner/users/{id}/permissions（内部用）
为什么它是一个独立服务 ① 安全边界要收口：认证是最敏感、最不能出错的一块，独立出来只有这一处实现，改规则不会有遗漏； ② 它被所有服务依赖：网关和每个服务都要拿它鉴权，做成公共服务比复制 7 份靠谱； ③ 它必须最稳：AI、报表这些服务可以短暂降级，但登录不能，独立部署才方便给它单独的保护（限流、独立资源）。
customer-service客户与坐席主数据技能组
职责一句话管"有哪些人、怎么分组"：客户（企业）信息、坐席账号、技能组、渠道配置。
关键表tenant（客户）、sys_user（坐席档案扩展）、skill_group（售前/售后/财务）、quick_reply（常用语）
暴露接口GET /api/tenant/agents（坐席列表，分页+按技能组筛选）、POST /api/tenant/agents、PUT /api/tenant/agents/{id}/status（在线/小休/离线）、GET /inner/agents/{id}
为什么它是一个独立服务 ① 典型的"主数据"：变更少、被所有人读（会话分配要看技能组、工单派单要看人、报表要按人统计）， 集中一处管理，其他地方只引用 ID，改一次不用改七处； ② 它的负载和别的服务完全不同：读写都很小，几乎不需要扩容，独立出来就不会被 AI、报表那种重负载绑架； ③ 权限与业务解耦：坐席的"组织架构"和"在线状态"分属不同关注点，放在一起会让会话服务的代码越滚越乱。
conversation-service会话与消息WebSocket有状态
职责一句话管"顾客和坐席怎么实时聊天"：维护长连接、存消息、保证顺序、接待分配、转接。
关键表session（会话）、message_202601（消息，按月分表）、session_transfer（转接记录）、agent_status（坐席在线状态）、session_evaluation（满意度）
暴露接口POST /api/session/start、WS /ws/agent（长连接）、GET /api/session/{id}/messages、POST /api/session/{id}/transfer、POST /api/session/{id}/close
为什么它是一个独立服务 ① 它是"有状态"的：WebSocket 连接绑在某台机器上，扩容方式、发布方式都跟普通 HTTP 服务不一样（要优雅关闭、考虑连接迁移），混在别的服务里会互相牵制； ② 写入量最大：按单客户日均 6 万条消息，一个月 180 万行，消息表和别的业务表根本不是同一个量级，独立出去才好做分表、归档、单独调优； ③ 实时性要求最高：聊天要秒回，不能被"顺手也放在这个服务里"的报表、AI 代码拖慢 —— 这是拆它最直接的理由。
ticket-service工单 + SLA状态机定时扫描
职责一句话管"跨部门的事怎么走完"：建单、指派、状态流转、SLA 计时与超时升级、评论与附件。
关键表ticket、ticket_template（模板+自定义字段）、ticket_flow_log（流转日志）、ticket_comment、ticket_attachment、ticket_sla（首响/解决时限）
暴露接口POST /api/tickets、PUT /api/tickets/{id}/assign、PUT /api/tickets/{id}/status（带 SLA 校验）、POST /api/tickets/{id}/comments、POST /inner/tickets（给 AI 的 createTicket 工具用）
为什么它是一个独立服务 ① 它有一套自己的流程和节奏：工单有状态机、有定时任务每分钟扫 SLA、有超时升级，这些都是"后台跑的活"， 和在线聊天抢资源最不划算 —— 独立部署后，SLA 扫描把 CPU 用满也不影响顾客聊天； ② 业务闭环清晰：从建单到关闭全在 ticket 里，接口边界天然明确，团队里一个人就能负责整个服务； ③ 它的数据寿命最长：工单要留档好几年，需要独立的归档和查询策略，跟会话消息那种"热数据"生命周期完全不同。
knowledge-service知识库 + 向量化向量库异步任务
职责一句话管"AI 回答的依据从哪来"：文档上传解析、切块、向量化、混合检索（BM25 + 向量）、FAQ 管理。
关键表knowledge_base、knowledge_document（文档+解析状态）、knowledge_chunk（片段+vector_id）、knowledge_faq（问题+相似问+命中次数）
暴露接口POST /api/knowledge/documents（上传，返回 docId，向量化异步做）、GET /api/knowledge/faq、POST /inner/knowledge/search（给 ai-service 做 RAG 检索）
为什么它是一个独立服务 ① 它依赖的东西不一样：别人用 MySQL，它还要用向量库（PGVector/Milvus）+ ES 做混合检索， 这种"特殊中间件依赖"放进别的服务会污染整个服务的启动和部署方式； ② 它的负载形态很怪：上行是"上传文档 → 解析 → 调 Embedding 模型"的长耗时批处理任务，下行是毫秒级的高频检索， 两者要各自限流；独立出来才好给它单独配资源； ③ 数据物理隔离：每个客户独立向量集合，知识库是 AI 的输入来源，宁可多一个服务也不跟业务库抢资源。
ai-serviceAI 编排单次 2~4 秒Agent
职责一句话管"机器人怎么把话答对"：意图识别 → 查知识库（RAG）→ 需要业务数据就调工具（Tool Calling）→ 生成答案 → 判定要不要转人工。
关键表ai_agent（机器人配置）、ai_agent_tool（可用工具）、ai_conversation、ai_execution（重点表：输入、意图、召回片段、工具调用、token、耗时、回答来源）、ai_unanswered（未命中问题回流）
暴露接口POST /api/ai/chat（顾客提问，SSE 流式返回）、POST /api/ai/summary/session（会话摘要）、POST /api/ai/quality/inspect（异步质检）、GET /api/ai/executions（执行日志）
为什么它是一个独立服务 ① 它的耗时和别的接口不是一个数量级：普通接口几十毫秒，它一次 2~4 秒，而且线程全在"等大模型回话"（消耗的是等待，不是 CPU）； 这种服务必须有自己的线程池和超时策略，混在会话服务里会把聊天线程池占满 —— 这是全项目最硬的一条拆分理由； ② 它的变化最快：换模型（DeepSeek 换通义）、调 Prompt、加工具、换框架（LangGraph / 自研编排），改得最勤， 独立部署才能一天发几次而不惊动其他服务； ③ 它最容易出问题：模型超时、限流、答偏，需要熔断降级和日志追踪，独立出来才方便"单独观察、单独降级、单独扩容"。
report-service报表统计重查询离线/实时两条线
职责一句话管"数据说明什么"：会话量、机器人解决率、转人工率、平均首响、工单超时率、坐席绩效、AI 效果指标。
关键表统计结果表（按天预聚合）report_daily_session、report_agent_perf、report_ticket_sla、report_ai_effect；明细数据通过 Kafka 事件 + 定时任务汇总，不直接压在线库
暴露接口POST /api/report/session/overview、GET /api/report/agent/performance、GET /api/report/ai/effect
为什么它是一个独立服务 ① 它是唯一"慢是正常的"的服务：一条报表 SQL 可能扫几十万行、跑好几秒， 这种查询绝对不能和在线会话共用数据库连接池 —— 报表一跑，聊天就卡，这是单体最典型的翻车场景； ② 它可以跑在从库/独立的库上，甚至预计算，物理上和业务库分开才敢随便加索引、随便跑大查询； ③ 口径变化最频繁：运营每个月都可能要改统计维度，独立服务可以随时发版，不用拉着会话、工单一起上线。
被追问"7 个是不是太多了 / 为什么不是 3 个"时的答法：拆分的依据是负载特征、数据生命周期、变更频率这三条是否明显不同。 这 7 个在这三条上都对不上号（AI 是长等待、报表是重查询、会话是实时高并发、工单是后台流程、others 是低变化主数据），所以拆； 如果一个小公司只有 3 个人维护，这些差异就不值得付运维代价，那时候就该合并成 2~3 个服务甚至单体。
记住这一句 判断一个服务该不该独立，只看三条：它的负载节奏是不是跟别人不一样、它的数据是不是自己一套、它的变更频率是不是明显更快。三条都对上，才值得拆。
5

为什么要拆：三类"节奏完全不同"的活混在一起会互相拖死

这是整个项目最真实、最能说服面试官的拆分理由 —— 不是"显得架构先进"，而是不拆真的会出事。

① AI 长耗时 IO

一次问答要调大模型，2~4 秒。这期间线程不干别的，就在等网络。

不是 CPU 忙，是线程被占着 —— 而线程池是有上限的（比如 200 个）。

② 报表重查询

一条统计 SQL 扫几十万到上百万行，吃 CPU 和数据库连接，跑起来好几秒。

它是"没人等着，但资源吃得最狠"的那种活。

③ 会话实时高并发

几百个坐席 + 上千活跃会话要秒回，要求延迟毫秒级、连接数上万。

它的特点是"单个请求很轻，但要求特别快、特别稳"。

面试时的标准说法（三句话讲完）

"我们拆分的核心理由是三类负载的特性完全不同：AI 问答是单次 2~4 秒的长耗时网络等待，报表是扫大量历史数据的重查询，会话是要求毫秒级的实时高并发。 放在一个进程里，它们会共用同一个线程池和数据库连接池，AI 把线程等满、报表把连接占满，最需要快的会话反而被拖到几百毫秒甚至超时。 所以按负载特征 + 数据边界 + 变更频率拆成了 7 个服务，各自独立扩容、独立降级。"

—— "共用同一个线程池/连接池"这几个字是这段话的力量来源，它把一个抽象概念变成了具体的资源竞争。

记住这一句 拆分的理由不是"显得高级"，而是三类活的节奏差太远（AI 是长等待、报表是重查询、会话是实时），混在一起就会互相抢线程和数据库连接，结果是该快的变慢、该慢的把全站拖挂。
6

拆完的代价（面试要主动说，别等着被挑）

只讲好处不讲代价，面试官会认为你没真做过。主动说代价 + 给出缓解方案，是"做过项目"和"背过概念"的分水岭。

代价 1 运维成本直接翻倍

从一个 jar 变成 7 个服务 + 网关 + Nacos + 消息队列 + 向量库。部署、监控、日志、告警、机器资源全都要乘以份数，出问题要看的地方从一个变成十个。团队里必须有一个人懂这些，小团队会被拖住。

所以怎么缓解：用 Docker + 一套统一的 CI/CD 模板，7 个服务用同一个流水线模板，减少重复配置；监控和日志集中收（Prometheus + Grafana + ELK），大家看同一块大盘，不用挨个登机器；环境用一份 docker-compose / K8s 编排文件描述清楚，新人一条命令能起全套。

代价 2 链路变长，排查问题变难

以前一次请求一个堆栈就看完了；现在一次请求可能经过网关 → 会话 → AI → 知识库 → 工单 → 大模型，日志散在 5~6 个服务的多台机器上。没有 traceId，你只能一个个服务去翻日志，猜是哪一环慢、哪一环报错。而且跨服务的异常不像本地堆栈那样一眼到底。

所以怎么缓解：全链路 traceId 透传（网关生成 → Feign 传递 → 每个服务日志都带上），日志集中到 ELK，按 traceId 一次搜出完整时间线；关键跨服务调用都打"入参、耗时、结果"三点日志；接口报错统一返回错误码 + traceId，让用户截图就能定位。

代价 3 没有跨服务大事务了，分布式事务很复杂

单体时代一句 @Transactional 就搞定的事，现在变成"工单建好了，但通知坐席失败了""会话结束了，但统计没写进去"。每个服务只能管自己的库，跨服务的"要么都成功要么都失败"要靠自己实现，还要处理中间态、重复消费、对账。

所以怎么缓解：能不跨就别跨 —— 把边界划在"一个事务能闭合"的地方，比如工单和它的流转日志、评论都在 ticket 服务内，一个本地事务解决；确实要跨的用最终一致：本地事务表 + Kafka 消息 + 消费端幂等（用业务唯一键去重）+ 定时对账兜底补偿；不追求强一致的地方就接受短暂不一致并明确告知用户（"工单已创建，通知稍后送达"）。

代价 4 网络调用一定会失败 —— 这是新引入的一整类问题

本地方法调用不会"半路消失"，但 HTTP 调用会：网络抖动、下游重启、下游变慢、超时、重复请求。多一次网络就多一个失败点，而且失败方式很讨厌 —— 你不知道对方到底执行了没有（超时可能是没收到，也可能是执行完了回包丢了）。

所以怎么缓解：① 所有 Feign 调用必须配超时（连接超时 + 读超时），不配就是默认等很久，线程全卡死；② 关键调用配重试 + 幂等（重试必须保证重复执行不出错，接口用业务唯一键去重）；③ 非核心调用配熔断降级（Sentinel），失败就走兜底，别把上游拖死；④ 允许延迟的调用改成走消息队列（Kafka），发出去就算成功，消费端慢慢处理 + 重试队列兜底。

图 6-1 ｜ 代价 vs 缓解，一眼记住
代价具体疼在哪缓解手段（面试说的就是这个）
运维成本东西多了一倍以上，人不够就乱统一 CI/CD 模板 + 集中监控日志 + 一份编排文件起全套
排查难日志散在多台机器，堆栈断了traceId 全链路透传 + ELK 聚合 + 关键调用三点日志
分布式事务跨服务没有免费的事务了边界内用本地事务；跨服务用本地消息表 + MQ + 幂等 + 对账补偿
调用会失败新增超时、抖动、重复请求一整类问题必配超时 + 重试要幂等 + 熔断降级 + 能异步就上 MQ
记住这一句 微服务不是免费午餐：它把"代码复杂度"换成了"分布式复杂度"。面试时先主动说出这四条代价，再补一句缓解方案，比只夸好处可信得多。

面试问答 10 问 10 答（点开看答案，答案可以直接背）

每条答案都按"先比喻 / 先结论 → 再说我们项目怎么做 → 最后补一句权衡"的结构写，2~4 句话，口语化，不要背成书面语。

Q1什么是微服务？和单体有什么区别？
可以直接这样说 "微服务就是把一个大的程序拆成多个能独立运行、独立部署的小服务，每个服务只干一件事，之间通过网络调用。 单体就像一个厨师又切菜又炒菜又洗碗，微服务就是分工的厨房 —— 配菜、炒锅、洗碗各管一摊，谁忙给谁加人。 区别主要在三点：单体改一处要整体上线，微服务可以只发一个服务；单体出问题全站挂，微服务故障被关在一个服务里；单体的扩容只能整体复制，微服务可以按需只扩某一个。"

追问"那微服务是不是更好"→ 答："不是，它运维更复杂、排查更难、还要自己处理分布式事务和网络失败，团队小、量不大的时候单体更划算。"

Q2你们的服务是怎么拆的？按什么维度拆？
可以直接这样说 "我们主要按业务能力拆，同时看三个具体的判断标准：负载特征、数据边界、变更频率。 比如 AI 问答是单次 2~4 秒的长耗时调用，报表是扫大量数据的重查询，会话是要求毫秒级的实时高并发，这三类节奏完全不同，放一个进程里会互相抢线程池和数据库连接，所以必须拆开。 拆完就是 auth、customer、conversation、ticket、knowledge、ai、report 这 7 个业务服务，每个服务自己的数据库表自己管。"

如果被追问"什么是高内聚低耦合"（这词不解释就用会被扣分）→ "说人话就是：一个服务里放的都是同一件事的代码，所以改动不出这个圈；服务之间只通过明确的接口打交道，所以我改我的实现，只要接口不变，别人不用动。就像厨房里配菜台换了把新刀，炒锅师傅完全不用知道。"

Q3服务之间怎么调用？为什么用 Feign？
可以直接这样说 "本质就是发一个 HTTP 请求，没有魔法。用 OpenFeign 只是因为它把这个 HTTP 请求包装成接口加注解，调用起来像调本地方法，省掉了手写 URL、拼参数、反序列化这些样板代码。 地址不用写死，Feign 会去 Nacos 按服务名拿地址，再配合 LoadBalancer 在多个实例里挑一个。 但因为是网络调用，所以我们一定会配连接超时和读超时，关键接口还要幂等和降级，不然下游一慢，上游线程就全卡住。"
Q4Nacos 是干什么的？
可以直接这样说 "Nacos 干两件事：服务注册发现和配置中心。 注册发现就是公司通讯录 —— 每个服务启动时把自己的名字、IP、端口登记进去，别的服务要调用就先翻通讯录拿地址，这样 IP 变了、实例多了少了都不用改代码；某台实例挂了，心跳超时会被自动摘掉，请求不会再打到死机器上。 配置中心就是公告板 —— 数据库地址、大模型超时、转人工关键词、限流阈值这些会变的东西都放上面，改完发布，各个实例动态刷新，不用重启服务。"

追问"它挂了怎么办"→ "Nacos 要做 3 节点集群，不能单点；客户端有本地缓存，已经拉到的地址不会立刻失效，能撑一段时间。"

Q5网关的作用是什么？为什么需要它？
可以直接这样说 "网关是所有外部请求的唯一入口，就像公司前台兼保安：先统一验身份（解析 JWT，把 userId、tenantId、角色塞到请求头带给下游），再按路径把请求转给对应的服务，同时做限流、记日志、跨域这些公共的事。 为什么需要：没有它，这 7 个服务就要各自实现一遍验 token、限流、日志，改一次规则要改 7 个地方，而且每个服务都得暴露在公网上。 另外我们还靠它把内部接口 /inner/** 全部拦掉，那些只允许服务之间互相调，外面打不进来。"
Q6什么是服务熔断和降级？举你们项目的例子
可以直接这样说 "熔断是下游出错或变慢时不再继续调它，快速失败；降级是调不了的时候给用户一个提前准备好的兜底答案。打个比方：某位同事请假了，前台当场告诉客户'今天这个业务办不了，我帮您转人工'，而不是让客户在门口干等半小时。 我们项目里最典型的是 AI 服务调知识库检索：如果 1 秒内失败率超过 50%，Sentinel 就把这条链路熔断 10 秒，这期间 ai-service 直接走降级逻辑，不硬答，而是返回'我先帮您转人工'并触发转人工流程。 这样顾客立刻得到明确答复，ai-service 的线程也不会因为干等知识库而被占满。"
Q7微服务有什么缺点？
可以直接这样说 "主要四条。第一，运维成本高，从一个 jar 变成七八个服务加一堆中间件，部署、监控、日志都要乘以份数。 第二，排查变难，一次请求跨五六个服务，日志散在多台机器上，没有 traceId 根本拼不出完整链路。 第三和第四是分布式带来的新麻烦：单体一句 @Transactional 的事，跨服务得靠消息、幂等、对账补偿才做到最终一致；网络调用还一定会失败，会超时、会重复，必须配超时、幂等和熔断降级。 所以我们的态度很明确：不是必要不拆。"
Q8你们怎么保证服务间调用的可靠性？
可以直接这样说 "我们分了四层：第一层是超时，所有 Feign 调用都显式配连接和读超时，绝不用默认值，避免线程被无限期占住。 第二层是熔断降级，用 Sentinel 给关键调用配规则，失败率超阈值就熔断走兜底，不让故障顺着调用链往上蔓延。 第三层是重试加幂等，只对查询这类可以安全重试的接口重试，写接口靠业务唯一键保证重复执行不出错。 第四层是能异步就异步，通知坐席、写统计、知识库向量化这些允许延迟的直接发 Kafka，发出去就算成功，消费端幂等消费加重试队列兜底。"
Q9一个请求进来了，完整链路是怎样的？
可以直接这样说 "以顾客问一句'我要退货'为例：请求先到 Nginx 再到网关，网关生成一个 traceId 并校验 JWT，把它路由到 conversation 服务；conversation 建会话、存消息、把最近几轮上下文放 Redis，然后通过 Feign 调 ai-service。 ai-service 先做意图识别，再到 knowledge-service 做 RAG 向量检索拿 Top5 知识片段；如果需要订单、物流、工单这类实时数据，就通过 Tool Calling 再调对应服务；最后把资料交给大模型生成答案，并写入 ai_execution 日志。 答案原路返回到 conversation，通过 WebSocket 推给顾客；如果命中了转人工条件，就由 conversation 做接待分配，把会话推给空闲坐席。整个链路所有日志都带同一个 traceId，方便事后查。"
Q10如果让你重新设计，你会怎么拆？
可以直接这样说 "如果重来，我会先从单体开始，把业务跑通，等模块的负载差异真的体现出来、团队也变大了，再按现在的标准拆 —— 因为一开始就上微服务，付出的是运维和分布式复杂度，换回来的是当时并不需要的弹性。 真拆的时候我会做两点改进：一是把报表从第一天就放在只读从库上、走预计算，而不是等它把在线库拖慢才想起来分离； 二是把 AI 的调用全部设计成异步加回调/SSE，不让任何一个 HTTP 线程在那儿干等 2~4 秒，这样 ai-service 的扩容压力会小很多。 另外我会把服务数量控制在更少一点，比如 auth 和 customer 合并成'用户与权限'，因为它们的负载和变更频率其实差不多，合并能省一套部署和运维成本。"

这一问考的是权衡意识，不是让你说自己项目拆错了。最后那句"合并两个服务"最能加分。

记住这一句 所有微服务面试题的答题模板都一样：先用生活比喻说清概念 → 再说我们项目里具体怎么做的（带数字） → 最后补一句代价或权衡。三步齐了，答案就不可能像背的。

⚡ 微服务速记卡（7 个服务 · 7 个名词 · 3 个必说代价）

▍7 个服务 —— 一句话记住它是谁
auth 认证授权登录发 JWT、RBAC 权限（管你是谁）
customer 客户与坐席客户、坐席、技能组（管有哪些人）
conversation 会话与消息WebSocket 长连接、消息顺序、转人工（管实时聊天）
ticket 工单 + SLA建单、流转、超时升级（管跨部门流程）
knowledge 知识库 + 向量化文档切块、向量检索（管 AI 的依据）
ai AI 编排意图识别→RAG→Tool Calling→转人工（管答得对）
report 报表统计解决率、首响、超时率（管数据说话）
▍7 个名词 —— 一句话记住它的比喻
服务注册发现（Nacos）公司通讯录：上线自动登记，挂了自动划掉
API 网关（Gateway）前台兼保安：唯一入口，先验身份再指路
服务间调用（OpenFeign）同事打电话：本质就是 HTTP，没有魔法
负载均衡（LoadBalancer）前台把客人分给空闲的同事
熔断降级（Sentinel）同事请假就当场给说法，别让客户干等
配置中心（Nacos Config）公司公告板：改了所有人立刻看到，不用重启
链路追踪（traceId）快递单号：一眼看出卡在哪一环
▍3 个必说的代价（说完立刻补缓解方案）
1. 运维成本翻倍→ 统一 CI/CD 模板 + 集中监控日志 + 一份编排起全套
2. 链路长、排查难→ traceId 全链路透传 + ELK 按单号聚合查询
3. 没有跨服务大事务 + 网络调用一定会失败→ 本地事务划边界、跨服务最终一致（MQ + 幂等 + 对账）、超时必配、熔断降级兜底
▍开口三句话（不知道从哪说起时就用它）
拆的理由三类负载节奏完全不同：AI 长等待、报表重查询、会话要实时
拆的依据负载特征 + 数据边界 + 变更频率，三条都对上才拆
拆的态度不是必要不拆；小团队、量不大，单体才是最划算的
一句话微服务就是把「一个厨师全包」改成「分工的厨房 + 谁忙给谁加人」；好处是各干各的互不拖累，代价是原来喊一嗓子的事现在要打电话 —— 所以我先看值不值得，再决定拆不拆。
记住这一句 面试前只扫这张卡：7 个服务名（auth / customer / conversation / ticket / knowledge / ai / report）+ 7 个比喻 + 3 个代价，答任何微服务问题都先从这个框架里找位置。
