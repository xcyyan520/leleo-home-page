0心态先摆正（很重要，先看这 3 条）

① 你不需要"看懂代码"，你需要"讲清流程"。
面试官要听的是一次请求怎么走完 + 你为什么这么设计，不是让你背 class 名。所以本路线 70% 时间花在流程和选型理由上，只有最后才碰代码。
② 允许自己看不懂细节，先建立骨架。
第一遍看不懂"Nacos 是什么"很正常。先记住"7 个服务、会话走 WebSocket、AI 要查知识库"这种骨架，第二遍再补细节。
③ 每个阶段都有自测，答不上就回去补，不要硬往前冲。
自测题都是面试官真会问的。答不上却往前冲，面试时会在同一个地方卡住。

2阶段一：建立整体印象 第 1~2 天

看什么 ▶
  1. 架构课件（10 章速记） → 只看第 1 章（项目一页纸）。约 20 分钟。
  2. 架构总览（Canvas 动态图） → 场景一（分层架构图）。玩 30 分钟：
    • 拖动、缩放几次，让"有 7 个服务、6 类中间件"进入肌肉记忆
    • 把每个节点都点一遍，看它的职责
    • 把 conversation、ticket、ai、knowledge 四个重点看

这两天只需要记住这 6 个数字

7 个微服务     29 张表      3 家客户
日均 8000 会话 / 6 万消息 / 600 工单
内部处理速率【估算】约 30 次/秒   写接口 TPS 8
AI 解决率【目标】41% → 63%
★口径红线：那个 30 是按业务量估算的内部处理速率，不等于网关入口 QPS，也不是压测实测值；41%→63% 是项目设定的目标区间，不是已验证的生产成果。两句话必须连着数字一起说。
⛔ 自测（答不上就回去看）

  • ✓有几个微服务？说出其中 4 个的名字
  • ✓内部处理速率【估算】大概多少？这个数是怎么算出来的、又不是什么？
  • ✓项目是"给谁做的"？（是给企业客户交付的，不是自己开网站卖）

3阶段二：为什么要拆微服务 第 3~4 天

这是整个项目最重要的一块。面试官最爱问"为什么要拆"，这题答好等于展示你的架构判断力。
看什么 ▶
  1. 微服务入门图解（零基础） → 通读一遍，约 2 小时。重点三节：
    • 第 1 节「餐厅比喻」：单体 = 一个厨师全包
    • 第 3 节「七个核心名词」：每个都有"打个比方"
    • 第 5 节「为什么要拆」：三类负载抢同一份资源
  2. 微服务动画（4 场景） → 只看场景①和②，来回切着看 3 遍：
    • 场景①：AI 卡住 → 其他请求在底部堆积排队
    • 场景②：同样 AI 卡住 → 其他 6 个照样进出带绿勾
    • 看懂这个对比，你就懂微服务了

你要能一口气说出的答案（背下来）

"我们拆的原因有两个：一是这套底座要给多家客户用，客户各自的定制做成独立服务，改一家不影响另外两家；二是负载特性差太多——AI 调大模型是长耗时 IO（一次 2~4 秒），报表是重查询，会话是实时高并发。混在一个进程里会互相拖慢：AI 一卡，顾客发消息和坐席查报表全得排队。拆开之后，客户做活动时只扩会话和 AI 这两个服务就够了。"
⛔ 自测
  • ✓微服务和单体，最核心的区别是什么？（提示：能不能独立部署、独立扩容）
  • ✓说出一句"为什么要拆"的完整理由（不许只说"为了先进"）
  • ✓7 个服务分别负责什么？至少说清 conversation / ticket / ai
  • ✓微服务有什么代价？（运维成本、排查难、分布式事务、网络调用会失败）——能说出代价才显得你懂权衡

4阶段三：把"一次请求"走一遍 第 5~7 天

这是面试讲项目的主线，8 分钟里有 6 分钟在这。
看什么 ▶
  1. 微服务动画（4 场景） → 场景③「请求的 7 步旅程」，逐帧点完 3 遍。每步下面都写了"如果是单体，这一步会怎样"，对比着记。
  2. 架构课件 → 第 3 章（8 步业务流），配合看。

你要背下来的 8 步（顺序不能乱）

① 顾客进线       → 会话落库 + Redis 存上下文 30 分钟
② AI 机器人接待   → 意图识别（售前/售后/物流/投诉 + 置信度）
③ 转人工判定     → 意图是投诉 / 连续2次没识别 / 命中转人工关键词
④ RAG 检索       → 向量 + BM25 + RRF 融合，取 Top5
⑤ Tool Calling   → queryOrder / queryLogistics / createTicket
⑥ 人工接待       → WebSocket 多实例 + Redis 路由表
                    + Kafka 按 sessionId 分区保序
⑦ 建工单 + SLA   → 计时、剩余 20% 提醒、超时升级上级
⑧ 结束与回流     → AI 质检 + 报表 + 未命中问题回流知识库
⛔ 自测（答不上就回去看场景③）
  • ✓顾客消息进来第一个落到哪个服务？
  • ✓什么情况下会转人工？（说出 3 个条件）
  • ✓RAG 是干什么的？为什么要"向量 + 关键词"混合检索？
  • ✓Tool Calling 是什么？举 2 个我们实际用的工具
  • ✓消息为什么要走 Kafka 而不是直接推送？（多实例 + 一对多 + 削峰）

5阶段四：看清界面长什么样 第 8~9 天

为什么这一步重要：面试官很可能说"能看看页面吗"。你没有上线环境，唯一的武器就是"能把界面讲得像真做过"。

打开「五页原型」逐个点，每页停 5 分钟

页面你要记住的细节（这些是"真做过"的证据）
坐席工作台三栏布局；未回复会话的读秒数字会变黄/变红；AI 消息下方挂引用来源；右栏有订单卡片
工单列表与详情SLA 剩余时间进度条实时递减；详情页有双 SLA 条；流转时间线里有【暂停计时】节点
知识库FAQ 按总提问次数降序排列；底部有未命中问题列表 → 一键补充
看板会话量折线、意图环形、工单状态柱状

背下这段话（面试被问"看页面"时用）

"系统跑在客户自己的环境里，我离职后权限回收了，确实没法给您看。不过界面我印象很深——坐席工作台是三栏：左边会话列表，未回复的会话读秒数字会变黄；中间消息流，AI 回复下面挂着引用来源，点开能看到命中哪条知识；右边是顾客资料和订单卡，客服能直接在卡片上查物流。工单那边有双 SLA 进度条，等客户回复的时候会显示暂停计时。"

"读秒变黄""引用来源""暂停计时"这三个细节，就是真做过的证据。

⛔ 自测
  • ✓不看资料，说出坐席工作台的三栏各放什么
  • ✓工单详情页里，SLA 是怎么显示的？
  • ✓知识库页面上，你怎么知道哪些问题没被答上？

6阶段五：AI 模块 第 10~11 天

你的简历定位是"传统后端 75% + AI 25%"，所以 AI 讲到"够用且真实"就行，不要吹成算法专家。
看什么 ▶
  1. 架构总览（Canvas 动态图） → 场景三「AI Agent 链路」。重点看 ⑤ 后置校验分出的两条通道（★只有"知识问答"分支才受这条阈值约束）：
    • 🟢 命中（重排分 ≥ 0.72，且召回候选非空）→ 返回带引用答案
    • 🔴 未命中（召回为空 / 重排分不达标）→ 禁止生成 → 兜底话术 → 转人工
    ★关键顺序：先按意图路由再谈阈值。若把 RAG 阈值挡在 Tool Calling 前面，"我的快递到哪了"会因知识库没资料被直接兜底，而查物流的工具根本没机会被调用。
    ★向量相似度 0.60 只是"要不要调重排"的成本参考，不能单独触发兜底——BM25 可能精确命中而向量分很低，硬过滤会误杀正确结果。
  2. 架构课件 → 第 4 章（AI 链路）+ 第 5 章（8 个 Agent Tools）

你要能讲清的 5 件事（这几条决定你是不是"真做过 AI"）

  1. 幻觉兜底：答案必须带知识引用；召回为空或重排分不达标（设计中的经验阈值 0.72）就不允许生成，直接兜底转人工。★向量相似度只作参考信号，不单独触发兜底
  2. 客户数据隔离：向量检索必须带客户标识过滤，否则 A 公司的顾客会问到 B 公司的知识库
  3. 多模型可切换：DeepSeek + 通义千问双通道，超时自动降级到备用模型
  4. 可观测：每次执行都写 ai_execution 表（意图 / 召回片段 / 工具调用 / token / 耗时 / 是否转人工）
  5. 人工兜底不可绕过：连续未识别、命中关键词、顾客说"人工"、意图是投诉 → 一律转人工
⛔ 自测
  • ✓AI 答不出来的时候，系统怎么处理？（要答出"阈值 + 兜底话术 + 转人工"）
  • ✓你怎么知道 AI 答得准不准？（ai_execution 表 + 解决率指标）
  • ✓我们用了哪几个大模型？为什么要双通道？
  • ✓顾客问"我的快递到哪了"，AI 是怎么回答的？（Tool Calling 调 queryLogistics）

二、项目开发背景

这个项目解决的是一个很实际的问题：客户的顾客咨询散在各个渠道，没人管得过来，服务质量也没法量化。

具体来说，一家连锁零售客户，它的顾客会从官网、微信公众号、小程序、抖音私信这些地方进来咨询，以前是每个渠道派一两个人盯着，问题有三个：

  • 第一，响应慢。顾客在公众号问一句，可能半天没人回。
  • 第二，口径不一致。同一个"能不能退货"的问题，三个人能给出三个答案。
  • 第三，质量没法管。老板想知道"客服平均多久回一句""多少问题真的解决了"，拿不出数据。

所以我们做的这套系统，核心就是三件事：

  1. 全渠道接进来，所有咨询汇到一个坐席工作台；
  2. AI 机器人先接待，能答的自己答，答不了的转人工；
  3. 用 SLA 和报表把服务质量管起来，超时要升级，效果要能看到。

盈利模式是项目交付 + 年度维护费：客户按项目付一次开发费，我们交付到客户自己的环境里，之后按年收维护费。所以我们是私有化交付，不是标准化 SaaS——这也是为什么客户肯买：很多连锁零售和政企要求数据必须留在自己机房，标准 SaaS 直接用不了。

行业背景方面，这块市场在涨，IDC 的《中国企业级智能客服市场份额，2025》显示，2025 年国内企业级智能客服市场规模 71.9 亿元、同比增长 55.3%，而且重心已经从"能不能回答问题"变成"能不能把事情办完"——也就是 AI 要能直接调订单、物流这些业务系统。我们这个项目的 AI 模块就是按这个思路做的。

三、技术选型

整个项目是微服务架构，前后端分离，而且是 Java + Python 双栈——一句话概括就是Java 做骨架，Python 做大脑。

业务侧 5 个服务用 Java：Spring Boot 3.x + Spring Cloud Alibaba，JDK 17。

  • 网关用 Spring Cloud Gateway，做路由、JWT 校验、客户上下文注入和限流；
  • 注册和配置用 Nacos；
  • 安全用 Spring Security + JWT，走无状态；
  • 数据库 MySQL 8，每个客户独立 schema；
  • 缓存 Redis 7，做缓存、会话状态、分布式锁和限流；
  • 消息 Kafka，做消息投递、工单事件和知识库的异步向量化；
  • 搜索 Elasticsearch 8，做全文检索，同时也承担知识检索里的 BM25 那一路；
  • 文件 MinIO，向量库 PGVector；
  • 定时任务用 XXL-JOB 做分布式调度。

智能侧 2 个服务用 Python：FastAPI + LangChain + LangGraph。

  • 一个是 AI Agent 编排服务，用 LangGraph 把 Agent 建模成状态图，负责意图识别、工具调用和 LLM 调用；
  • 一个是知识库智能服务，用 LangChain 做文档解析、分片、Embedding 和检索重排。

两边通过 HTTP 同步调用 + Kafka 异步通信。所有外部客户端请求统一经过 Java 网关，前端不直接访问 Python 服务；内部服务之间根据调用场景使用 HTTP 或 Kafka，并通过服务间认证和网络访问控制保障安全。

模型接 DeepSeek 和通义千问双通道，可以按客户配置切换——因为两家都兼容 OpenAI 的协议，所以切换只改一个 baseUrl。

四、核心业务流程（8 步）

我们的核心业务流程是从顾客进线到工单闭环，一共 8 步：

  1. 顾客进线——从网页、公众号、小程序、抖音私信发起咨询，系统落库生成一个 session，会话上下文写进 Redis（TTL 30 分钟），同时投一条 Kafka 消息。
  2. AI 机器人接待——先做意图识别，判断是售前、售后、物流还是投诉，同时给出置信度。置信度太低就直接进兜底，不浪费一次大模型调用。
  3. 转人工判定——三种情况直接转人工：意图是投诉、连续 2 次没识别出来、命中转人工关键词（比如"人工""投诉""找你们领导"）。
  4. ★意图路由（这一步是我后来修正过的，也是这套 AI 流程的关键）——按问题性质分三条路走：
    - 知识问答类（"退货规则是什么"）→ 走 RAG；
    - 实时业务查询类（"我的快递到哪了"）→ 直接走 Tool Calling，不看 RAG 的分数；
    - 组合类（"我这笔订单能退吗、退款要多久"）→ 先 Tool Calling 拿订单数据，再走 RAG 补退款政策。
    为什么要有这一步：我原来的设计是把 RAG 检索和阈值判断放在前面，通过之后才判断要不要调工具。这个顺序有个要命的问题——顾客问"我的快递到哪了"，知识库里当然没有这个订单的物流信息，RAG 召回为空、直接就兜底转人工了，而查物流的工具根本没机会被调用。用户问的是一个完全能查的问题，却被推给了人工。
    所以修正成：先按意图路由，再决定走哪条路。判断依据是问题的性质，不是 RAG 的分数。
  5. RAG 分支——向量检索（余弦相似度）加 ES 的 BM25 关键词检索，用 RRF 融合出排序，再送重排模型取 Top5。然后做阈值判断：召回为空、或者重排分不达标，就禁止生成，走兜底话术加转人工。这一步是防幻觉的关键，但它只约束知识问答类问题。
  6. Tool 分支——直接调业务工具拿实时数据，查订单、查物流、查工单。成功就带着数据去生成；超时或失败就走兜底转人工。这条分支跟 RAG 的分数无关。
  7. 人工接待——坐席接进来，会话上下文从 Redis 路由表定位到坐席所在的实例，保证消息能推给他。
  8. 建工单 + SLA + 回流——人工也解决不了的建成工单，按优先级挂 SLA 时限；会话结束后做 AI 质检，把没答上的问题回流到知识库。

五、责任模块（我负责的 4 个）

项目一共 7 个服务，我主要负责其中 4 个模块。

模块一：会话消息模块

【业务问题】 客服会话是双向实时的：顾客发一句要立刻到坐席，坐席回一句也要立刻到顾客。如果做 HTTP 轮询，200 个坐席乘以几千个活跃会话，会产生大量空请求，而且延迟最低也有一个轮询周期。

【技术方案】 我用 WebSocket 做长连接，一次握手之后全双工，服务端能主动推。

但这个模块真正难的地方不在 WebSocket 本身，而在多实例部署下的消息路由。

问题现象是：坐席 A 连在实例 1 上，顾客消息被实例 2 收到了——实例 2 上没有坐席 A 的连接，消息就丢了。

我一开始的想法是：Redis 存一张路由表 sessionId → 实例号，消息写 Kafka 按 sessionId 分区保证有序，各实例消费之后只推送自己本机持有的连接，不是自己的就跳过。

但这个方案是错的。 因为 Kafka 是消费组模型，一个分区只会被一个实例消费。如果消费到消息的实例不是持有连接的那个，"跳过"就等于把消息丢了；路由表陈旧的时候更会彻底投丢。

正确的做法是：Kafka 只负责持久化、回放和异步业务，实时投递走实例间定向转发。

具体是：每个实例启动时订阅自己的 Redis 频道 ws:instance:{实例号}；消息来了先看客户端在不在本机——在本机就直接推，不在本机就用 Lua 脚本原子地"查路由 + 发布"到目标实例的频道，目标实例收到之后再推给本机持有的那个连接。

为什么用 Lua 脚本：把"查路由"和"发布"这两步做成原子操作，消掉中间路由表被改的窗口。

可靠性做了三层兜底：第一层，WebSocket 发送失败必须捕获异常，不能静默吞掉；第二层，客户端收到消息回 ACK；第三层，没 ACK 的消息进重试队列，客户端重连之后按最后一条消息 ID 补拉。

另外消息去重靠客户端生成的 client_msg_id 做幂等键——因为网络重连、用户连点、客户端自动重试都会产生重复请求，没有幂等顾客会看到自己的话出现两遍，甚至重复建工单。

消息表按月分表，单客户日均 6 万条，一个月大概 180 万行，分表主要是为了归档和历史查询方便，不是为了扛写入。全文检索走 ES，因为坐席要按关键词搜历史会话，MySQL 的 like %x% 走不了索引。

【这块的亮点】 一句话总结：
"Kafka 在合适的持久性配置下负责消息存储和异步处理，Redis 发布订阅负责实例之间的实时转发，WebSocket 负责最后一跳推送。消息可靠性靠持久化记录、客户端 ACK、重试和重连后的补拉来保障——而不是认为实时通道绝对可靠。"
注意别说成"用了 Kafka 就不会丢"——Kafka 的持久性取决于 acks、副本数、消费者提交 offset 的时机；而 Redis 发布订阅本身是"至多一次"投递，订阅者离线就会错过。所以我们的思路是：不指望实时通道不丢，而是保证丢了能补回来。

模块二：工单 + SLA 模块

【业务问题】 客户买这套系统，很大一部分原因就是想要 SLA——工单必须 X 分钟内首次响应、Y 小时内解决，超时要升级。没有 SLA，这就只是一堆工单列表，管不住服务质量。

【技术方案】 工单用状态机做流转校验，合法流转写在代码里，非法操作直接抛业务异常，比如"已关闭"的工单不能再"解决"。工单模板用自定义字段 JSON，因为不同客户的字段不一样——退款单要订单号，技术故障单要复现步骤。为什么不用动态建表：动态 DDL 在生产上很危险，锁表、无法回滚、权限要求高；JSON 字段配合 MySQL 8 的语法也能查询和建索引，灵活性和可控性平衡得更好。

【这里有两个踩过的坑】

第一个坑是"SLA 暂停计时"。

现象是：工单转成"待客户回复"之后，SLA 还在计时。等客户回复的那两天也算进去，造成大量误判超时、客户投诉。

方案是加暂停计时，但这里有几个细节必须做对：

  • 需要两个字段，不是一个：paused_at 记本次暂停的开始时刻，paused_total 记历史累计秒数。为什么要分开——只用一个累计值，算不出"这一刻正在暂停中"已经暂停了多久。
  • 首响时限不允许暂停，只有解决时限允许。因为首响是我们单方面的责任，客服就该主动回复，客户回不回不影响我们响应得快不快；而解决往往需要客户配合。如果两个都允许暂停，坐席就能靠"把工单挂成待客户回复"来逃避首响考核，考核就失效了。
  • 这里还有个隐蔽的 bug：如果只判断 paused_at 非空来认定"是否在暂停"，却忘了在恢复的时候把它置回 NULL，工单会永久暂停、SLA 再也不计时。

第二个坑是"定时任务多实例的幂等"。

问题是：@Scheduled 在 N 个实例上会同时执行，同一批工单会被重复升级。

我一开始只用了数据库 CAS，就是更新的时候带上 WHERE escalate_level = 期望值。但这不够——CAS 只能保证同一时刻只有一个成功，挡不住重试：调度框架本身会重试、网络超时后会重发、两个扫描任务（首响扫描和解决扫描）也可能同时想升级同一张工单。

完整方案要三件套：

  1. 唯一约束——升级事件表上加 UNIQUE KEY (ticket_id, from_level, reason)。注意 reason 不能省：首响超时、解决超时、人工升级是三种不同的业务事件，同一张工单从同一等级可能因为不同原因各升级一次——如果只锁 (ticket_id, from_level)，就会把第二次合法升级也拦掉。 重复执行时这三个字段必然相同，插入直接撞唯一键失败。这是防重放的根本手段。
  2. CAS 更新——WHERE id = ? AND escalate_level = ? AND status NOT IN ('CLOSED','RESOLVED')，顺带做状态校验，不升级已完结的工单。
  3. 顺序不能反 + 必须同事务——插升级记录和改工单状态要在同一个数据库事务里。如果不在同一事务，可能出现"记录插成功了、工单却没升级"，重试又被唯一约束拦住，这张工单就永远漏了升级且没有告警。另外通知要放在事务提交之后发，避免事务回滚了通知已经发出去。

一句话总结这个坑：锁能防并发，但防不了重试；幂等要靠"唯一约束 + 条件更新"，不能靠锁。

【这块的亮点】 状态机 + 双时限 SLA + 暂停计时 + 三层幂等，而且能说清每一步"为什么这么做"。

模块三：知识库模块

【业务问题】 AI 要答得准，前提是检索回来的资料是对的。检索错了，大模型再强也只能基于错资料编出错误答案——这就是所谓 garbage in, garbage out。所以 RAG 调优 80% 的精力应该花在检索上，而不是反复改 prompt。

【技术方案】 我做了三件事。

第一，文档入库走异步。 上传文档先存 MinIO 原文，然后发 Kafka 做异步向量化——解析、按标题层级切 chunk、调 Embedding、写 PGVector。为什么异步：一个 10MB 的 PDF 解析加向量化可能要几十秒，绝不能卡住上传接口。

第二，结构感知分片，不是固定字数切。 先解析文档的标题层级，一个"三级标题加正文"作为一个语义单元；单块控制在 300 到 500 字；相邻块保留 15% 重叠防止答案跨块被切断；FAQ 类不切，因为一问一答本身就是完整语义单元。为什么不用固定 500 字切：固定长度会把"退货政策第 3 条"拦腰截断，检索时只召回前半句，模型就答不全。

第三，混合检索。 纯向量对"订单号""退款期限"这类精确词召回不稳，纯关键词对"能不能退"这种口语化表达召回差，两者互补。所以用向量加 BM25，RRF 融合出排序，再送重排模型取 Top5。

【★这里有一个我踩过的认知错误，我觉得挺有价值，专门说一下】

我一开始以为"RRF 融合之后取最高分，拿这个分数去和阈值比较"就行了。这是错的，而且错得挺严重。

算一下就知道：RRF 的公式是 Σ 1/(k+排名)，k 一般取 60。第 1 名的融合分是 1/61，大概是 0.0164。我们是两路召回——向量加 BM25，某条切片在两路里都排第 1，1/61 + 1/61 大概是 0.0328，这就是理论最大值。

而我们的阈值是 0.72。0.0328 永远不可能大于等于 0.72——按我原来那个写法，100% 的查询都会被判成"没有召回"，全部走兜底转人工，系统等于完全不工作。

根因是我把几种含义完全不同的分数混为一谈了：

  • 向量余弦相似度，值域 0 到 1，有绝对意义，可以设阈值；
  • BM25 分数，值域 0 到几十、没有上界，只能用于排序；
  • RRF 分数，值域只有 0 到 0.033，它本质是"名次的倒数之和"——是有分数的，但那不是语义相似度，不能拿它套 0.72 这种阈值；
  • 重排分数，它比向量相似度更准（因为是交叉编码器算的），但值域取决于具体模型和分数处理方式，不一定是 0 到 1——要先确认归一化方式再定阈值。

所以正确做法是：RRF 只负责排名，阈值只作用在"含义明确"的分数上。 具体是：

  • 召回为空 → 兜底；
  • 重排分不达标（比如低于 0.72）→ 兜底。

★这里还有一条我后来修正的：常见写法是"向量相似度低于 0.60 就直接兜底，连重排都不调"——这个硬过滤有问题。因为顾客如果发来一个精确的退款编号或错误码，BM25 能命中得很好，但向量相似度可能很低（这种编号在语义空间里没什么意义）。只看向量分就提前兜底，就会把一个 BM25 已经找到正确答案的问题推给人工。

所以修正成：向量相似度低不能单独决定兜底，要结合 BM25 的命中一起看——有候选就送重排，最终是否兜底看重排分。

【这块的亮点】 主动讲出"RRF 只有排序意义、不能当相似度"，是真正理解混合检索的标志——这个问题不真跑过是发现不了的。

模块四：AI Agent 编排模块

这是智能侧的核心模块，用 Python + LangGraph 做的，也是全项目改动最勤的一个模块。

【业务问题】 客服 AI 的核心不是"调一次大模型"，而是多智能体编排——要表达"意图识别 → 检索 → 判断 → 调工具 → 再判断 → 生成 → 校验"这种带循环和条件分支的状态图。

【为什么用 Python 和 LangGraph，不用 Spring AI】 这是必问题，我分四层说：

  1. 能力层——LangGraph 把 Agent 建模成状态机，支持循环、条件边、断点恢复、人工介入；而 Spring AI 的 ChatClient 是"请求-响应"式的链式调用，表达这种"状态图即代码"的有环编排要费劲得多。
    这里我要说清一件事：我并不是说 Spring AI 完全做不了循环——它支持工具调用循环，也有编排扩展能力，用 Java 控制流加自定义编排同样能实现，只是需要自己组织更多的状态管理和流程控制逻辑。我们选 LangGraph，是因为它的状态图模型跟这个场景更匹配。
  2. 生态层——AI 三个月一代新东西，Python 是 AI 生态的第一现场，Java 侧通常是跟进、滞后几个月。而我们这个模块恰恰是改动最勤的：换模型、调 Prompt、加工具、换分片策略。
  3. 具体活——文档解析、分片、Embedding、重排这一整套，Python 的库又全又稳，Java 侧要么自己写要么找第三方，投入产出比差很多。
  4. 客观评价——Spring AI 本身是个好框架，1.1.x 已经很成熟，ChatClient、@Tool、向量库抽象、会话记忆都有。它的优势场景是"团队纯 Java + 只要 RAG 问答 + 不想引入第二种语言"。我们没选它，是因为明确需要 LangGraph 那种有环编排。不是它不行，是我们要的能力它给不了。

【技术实现】

Tool Calling 这块，Agent 能调 6 个工具：查订单、查物流、查退款规则、检索引擎、建工单、登记回访。Python 侧用 LangChain 的 @tool 装饰器声明，框架从函数签名加 docstring 自动生成 JSON Schema 发给模型，模型决定调哪个，框架自动执行、把结果回填、再请求一次，不用自己手写 Schema。调用链是跨语言的——Python Agent 要查订单时，通过 HTTP 回调 Java 侧的 inner 接口，中间有个薄封装层把 Java 接口包成工具函数。

这里有个安全边界要注意：createTicket 这种写操作必须加幂等键，因为跨语言 HTTP 调用更容易因为网络重试而重复执行，否则模型重试时会重复建单；而查订单必须校验"这个订单是不是当前顾客的"——而且这个校验必须在 Java 侧做，因为 Python 侧只拿到模型传过来的订单号，不知道当前登录的顾客是谁，绝不能信任模型或前端传的用户 ID。

【★双栈最大的一个坑：LangGraph 的状态持久化】

LangGraph 的核心卖点是有状态编排，它要持久化"执行到哪个节点了"。但默认的 MemorySaver 是纯内存的——多副本部署的时候，同一个会话的第二次请求打到另一个副本，Agent 就"失忆"了，从头开始。

这里有几个必须处理对的点：

  1. 依赖版本要钉死——LangGraph 迭代很快，checkpoint 相关的 API 和序列化格式在 0.x 的小版本之间改过，不钉版本会出现"本地跑得好、测试环境报反序列化失败"。
  2. 换 Redis checkpointer，并且 setup() 要显式调一次，它负责在 Redis 里建索引结构，忘了调第一次运行就报错。
  3. thread_id 必须带客户标识前缀——我们是多客户交付，不同客户可能有相同的 sessionId（各自数据库独立自增）。只用 sessionId 会导致跨客户状态串台，这是数据隔离事故，不是小 bug。
  4. 过期策略要两层——Redis key 设 2 小时 TTL，会话关闭时再主动删。只靠 TTL 的话，长会话中途被清理会导致 Agent 突然失忆；只靠主动清理的话，异常断开的会话永远不清理，Redis 会被撑爆。
  5. 并发要按会话串行——顾客连发两条消息，两个请求同时到达两个副本，都去读同一个 thread_id 的 checkpoint，就会后写的覆盖先写的，一条消息的执行结果丢了。所以按 thread_id 加分布式锁，拿不到的入队等前一个跑完。这和模块一"消息按 sessionId 分区保序"是同一个思想：凡是同一会话内必须有序的地方，都要串行化。

【★超时要分四层，不能只设一个数】

这个也是我后来才想明白的：

  • 前端等待超时 8 秒；
  • Java 侧对 Python 服务的调用超时 6 秒；
  • Python 侧业务总预算 5 秒；
  • 单次 LLM 调用 3 秒，单次工具调用 1 秒。

三条规则：第一，外层超时必须大于内层（8 > 6 > 5 > 3 > 1），顺序反了会出现"外层已经放弃、内层还在跑"的僵尸请求；第二，总预算不等于单次上限乘以次数，必须实现"剩余预算"机制——每次调模型或工具前先算剩余时间，用剩余预算和单次上限的较小值做超时，否则 3 次调用最坏就是 9 秒，外层 6 秒早就放弃了；第三，超时要能优雅收尾，走兜底话术加转人工，并且把这次超时写进执行日志，否则没法统计超时率。

【这块的亮点】 用 LangGraph 做有环编排 + 跨语言 Tool Calling + 状态持久化和并发的完整处理，而且能说清"为什么不用 Java 方案"。

六、三个必答题

1. 在设计开发过程中，遇到过什么难点和挑战？

我讲三个——一个业务难点、一个通过场景推演发现的问题、一个我自己的认知错误：

第一个是 SLA 的暂停计时（见模块二）——工单等客户回复期间 SLA 还在跑，误判超时导致客户投诉。加了双字段的暂停计时，并且明确首响不允许暂停。

第二个是 AI 幻觉（见模块四）——发现机器人会编政策，顾客问"能不能退"，它答了一个不存在的七天无理由。查执行日志发现那次召回的片段是空的，但流程还是走到大模型生成了。后来加了后置校验，召回为空或者分数不达标就禁止生成，直接兜底转人工。

第三个是 RRF 阈值那个认知错误（见模块三）——我把 RRF 的分数当成了相似度，而RRF 的值域只有 0 到约 0.0328（两路召回的理论最大值），跟 0.72 比会把所有查询都判成没召回。这个错让我意识到，混合检索里"哪些分数能设阈值、哪些只能排序"，是必须先想清楚的前提。

2. 讲一个你排查过的技术问题：怎么定位、怎么解决、怎么避免再发生？

我讲一个"通过生产场景推演、并在本地模拟复现验证过"的问题——消息堆积。

【场景构造】 我们模拟客户做会员日、咨询量在短时间内涨 6 倍的情况，然后观察系统的表现。在这个压力下，Kafka 消费 lag 开始增长，消息出现延迟。

【定位过程】 排查思路是：先看整体指标，确认不是某个接口挂了，而是消费端跟不上；然后看消费 lag 曲线和消费者线程栈，发现线程都卡在同一个地方——消费者线程里同步调大模型，一次要 2 到 4 秒，把消费线程占满了。

【验证的解决方案】 把大模型调用从消费者里剥出来，改成独立线程池加有界队列；超时从 10 秒降到 3 秒，超时直接走兜底话术；消费者只负责落库和推送，不再干慢活。改完之后在同样的压力下复现，lag 就没有再堆积。

【避免再发生】 加了三道：队列水位监控、消费 lag 告警，还有 Sentinel 熔断——大模型失败率超过 20% 就自动降级成"全部转人工"的保底模式。

★讲这段时的口径纪律：可以说"我们模拟/推演/复现"，可以说"在这种压力下会暴露什么问题"，但不要说成"线上出过一次事故"。被追问"哪一天、影响多少用户、有没有复盘报告"时，照实说"这是我们在压测和模拟环境里复现的场景，用来验证这个设计缺陷"。

【这个案例的价值】 它是"隔离慢操作"和"异步解耦"的典型例子。核心思路就是一句话：WebSocket 的 IO 线程和消息消费线程，绝不能被慢操作阻塞。

3. 系统的数据量、QPS 这些指标？

  • 交付规模：3 家客户；最大的一家日均会话 8000 左右、消息 6 万多条、工单 600 单。
  • 处理能力指标：内部处理的设计目标是约 30 次/秒（峰值），写接口 TPS 8 左右，AI 并发同时 5 到 10 个。

【★这里要能解释怎么算的，而且指标名称要说准】这个数字是按业务量估算的：日均 6 万条消息分布在 10 个小时，平均大概每秒 1.7 条；一条消息会触发落库、WebSocket 推送、AI 调用这些内部处理动作，按每条消息可能触发的动作数估算，平均内部操作速率大约 8 次/秒；再按约 4 倍的峰值系数估算，得到约 30 次/秒的内部处理设计目标。

★这里有个容易说错的点：这个 30 是"内部处理速率"的估算，不等于"网关入口 QPS"——因为内部服务调用不经过网关，而且一条消息引起的数据库写入、推送、AI 调用属于不同类型的内部动作，并不都对应一次网关入口请求。网关入口 QPS 要靠实际请求统计或独立的入口压测来确认。 这个数是基于业务量的估算，也不是压测实测值。

【★如果面试官说"这个量级不高"】我承认这不算高并发，所以我们刻意没做读写分离和分库分表，做了反而是过度设计。我们真正的压力不是请求量，而是长耗时任务挤占资源——AI 一次调模型 2 到 4 秒，混在一起几个请求就把线程占满，所以优化重点放在隔离慢操作上。

Q1. 我这个项目涉及到异步吗？遇到高并发怎么解决，有这个高并发问题吗？

结论：异步有，而且很扎实；高并发没有，别硬说"有"。

异步：有，四类，都走 Kafka

异步点为什么异步
消息投递顾客发消息不能等"落库 + 推送"全做完才返回
工单事件建单后要一对多通知：通知处理人、发短信、写统计、触发 AI 质检
知识库向量化上传文档后异步切片 + 向量化，不能卡住上传接口
会话结束后的 AI 质检质检是重活，绝不能放进会话主链路

另外还有一个更值钱的异步案例：那次故障的根因就是"消费者线程里同步调大模型，把消费线程占满"，解决方式是把 LLM 调用剥离成独立线程池 + 有界队列。

👉 被问"用了异步吗"，把这个故障讲出来比列四个 MQ 用途都管用。

高并发：没有

算一下就知道：

日均 8000 会话 ÷ 10 小时 ≈ 0.22 会话/秒
峰值按 30~50 倍算 ≈ QPS 10~30

这个量级叫"低并发"。 单台 4C8G + Redis 缓存就够扛。硬说"高并发"会被一路追问下去。

正确答法是"降级处理"，把话题引到你真懂的地方：

"我们这个量级不算高并发，峰值 QPS 30 左右，单库加缓存就够。真正的压力不是 QPS，是长耗时任务挤占资源——AI 一次调模型 2~4 秒，如果和会话处理放同一个线程池，几个请求就把线程占满了。所以我们做的不是'扛高并发'，而是把慢操作隔离出去：① AI 独立服务 + 独立线程池；② 大模型超时压到 3 秒，超时走兜底；③ Sentinel 熔断，失败率超 20% 自动降级成全部转人工。

如果真涨到 QPS 几千，我会按优先级做：先加缓存挡读 → 再治慢 SQL → 然后读写分离 → 非实时逻辑全异步化 → 最后才考虑分库分表。"

★最后那段是加分项——说明你知道优化顺序，不会一上来就喊分库分表。

面试官会追三句

  1. "这个解决率怎么定义的？" → 分母是什么？分子是什么？
  2. "41% 和 63% 是哪个时间段的？样本多大？"

模块一：认证授权（auth-service）

1.1 为什么需要独立一个服务

系统里同时存在四类身份：顾客（匿名）、坐席、主管、管理员，还要满足"客户之间数据隔离"。如果把认证逻辑散在各个业务服务里，会有三个致命问题：令牌密钥要同步 7 份（轮换时就是灾难）、用户体系被重复实现、安全策略改一处要改七处。

所以认证独立成服务，只做三件事：登录签发令牌、校验令牌、管理用户与角色。业务服务只认令牌里"签名过的" role 和 tenantId，不查用户表——这是微服务拆分的典型原则：数据归属单一服务，其他服务通过接口拿。

1.2 为什么用 JWT 而不是 Session

这是面试必问的第一题，答案要落到部署形态上：

SessionJWT
服务端状态有（要存 session）无
多实例要解决共享：粘性会话（扩容/宕机就乱）或集中存 Redis（多一次往返，Redis 挂了全站登录失效）加机器不用同步任何东西，验签即放行
主动失效容易（删 session）做不到（这是最大软肋）

我们拆了 7 个服务、每个两节点，Session 共享会变成基础设施负担，所以选 JWT。

但 JWT 的代价必须主动说：签发后无法作废。补法是 短有效期 access token（30 分钟）+ refresh token 存 Redis——要踢人就删 refresh token，最多 30 分钟后旧 token 自然过期。另外两种补法：Redis 黑名单（登出时把 token 写进 Redis，TTL=剩余有效期）、用户级 tokenVersion（改密码时版本号 +1，验签比对不一致就拒绝）。

1.3 JWT 的结构与签名（要能画出来）

header.payload.signature
──────  ───────  ─────────
算法声明  业务数据   签名

header    : {"alg":"HS256","typ":"JWT"}       ← Base64Url 编码
payload   : {"sub":"1","uid":1,"role":"AGENT","tenantId":1,"exp":...}
signature : HMAC-SHA256( base64url(header) + "." + base64url(payload), secret )

三个必须讲对的点：

  1. Base64 是编码不是加密。任何人拿到 token 都能解开看 payload。所以绝不能放密码、手机号、身份证——我们只放 userId / role / tenantId。签名段唯一的职责是防篡改，不是保密。
  2. 为什么用 HMAC 而不是 RSA：HMAC 对称，签发和验签同一个密钥，快且短；RSA 私钥签发、公钥验签，适合"签发方和验签方不是同一个团队"（比如开放平台给第三方发 token）。

    ★这里有个容易说错的地方——HS256 的密钥谁持有，要说清"两个角色"：

    HS256 是对称算法，签名和验签用的是同一个密钥。 所以：

    • 签发方（auth-service 认证服务）必须持有密钥——它要签发 token。
    • 验签方（谁验签谁就要有密钥）——这里是关键分歧点。

    常见写法是"只有网关持有密钥"，但同一段又说认证服务负责签发 JWT——这两句自相矛盾（签发也要密钥）。

    正确口径（我们实际采用的）：

    auth-service（认证服务）  ── 持有密钥：负责【签发】+ 登录时的校验
Gateway（网关）           ── 持有密钥：负责【验签】，是唯一的验签入口
其余 5 个业务服务          ── ★不持有密钥、不验签
                             只信任网关注入的身份头（X-User-Id / X-Tenant-Id）

    密钥只分布在 2 个组件里（认证服务 + 网关），不是 5 个业务服务。

    ★业务服务信任网关头的前提（必须讲，否则是漏洞）：
    网关必须强制覆盖这两个头——即请求进来时先剥掉外部传入的 X-User-Id，验签后再写入真实值。否则攻击者自己伪造一个 X-User-Id: 1 就能冒充别人。而且业务服务必须只在内网暴露，不能被外部直接访问。

    ② 换 RS256（如果被问"还有别的方案吗"）：认证服务用私钥签发，网关和其他服务用公钥验签——公钥泄露无害，适合"要让多个服务独立验签、又不想分发签名密钥"的场景。
    代价：签名慢一些、token 更长，且要管理密钥对。

    ★"为什么不用 RS256"的标准答法：
    "因为我们的验签入口收敛在网关一处，业务服务不验签、只信网关的头，所以密钥只需要在认证服务和网关两个组件里，分发面已经很小了，HS256 更简单也更快。如果要让各业务服务独立验签（比如去掉网关直连），我会换成 RS256。"

  3. 密钥长度必须 ≥ 32 字节（HS256 的 256 位要求）。不足要快速失败，不能等运行时才报错。

1.4 Spring Security 配置的五个关键点（★Spring Boot 3 / Security 6 写法）

★★两个前提要先说清（两个容易忽略的前提）

① 这段配置是给【业务服务】用的，不是给网关用的。
这是 Servlet 栈的配置（SecurityFilterChain / HttpSecurity / @EnableWebSecurity）——5 个 Java 业务服务都是 Spring MVC，所以用这套。
网关（Spring Cloud Gateway）是 WebFlux 响应式栈，配置完全不同：要用 SecurityWebFilterChain + ServerHttpSecurity + @EnableWebFluxSecurity，不能照抄下面这段。网关的职责是"验签 + 注入身份头 + 路由 + 限流"，业务服务才做细粒度的接口鉴权。
⚠️ 面试时如果被问网关的鉴权怎么配，要说 WebFlux 那一套，别把 Servlet 的搬过去。

② 这段要用对版本的 API——用错是"直接编译不过"的错。

常见写法是 authorizeRequests() + antMatchers()。这套 API 在 Spring Security 6（也就是 Spring Boot 3.x）里已经被移除或废弃了：

Boot 2.7 / Security 5Boot 3.x / Security 6状态
WebSecurityConfigurerAdapter已删除 → 注册 SecurityFilterChain Bean❌ 编译不过
authorizeRequests()authorizeHttpRequests()❌ 已移除
antMatchers(...)requestMatchers(...)❌ 已移除
mvcMatchers(...) / regexMatchers(...)requestMatchers(...)❌ 已移除
.csrf().disable() 链式lambda DSL：.csrf(csrf -> csrf.disable())⚠️ 已废弃

我们文档里的技术栈明明写的是 Spring Boot 3.x，却用了 Security 5 的 API —— 这两处是自相矛盾的，懂行的面试官一眼能看出来。下面是修正后的正确写法。

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // ① 无状态 JWT + 前后端分离，不用 Cookie 传身份 → 无 CSRF 前提
            //    ★Security 6 用 lambda DSL，不再链式调 .disable()
            .csrf(csrf -> csrf.disable())

            // ② 跨域：前端后端不同端口必须配
            .cors(cors -> cors.configurationSource(corsSource()))

            // ③ ★无状态：不创建、不使用 HttpSession —— JWT 方案的核心配置
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

            // ④ 认证失败/无权限返回 JSON，而不是 302 重定向到登录页
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint((req, resp, e) -> writeJson(resp, 401, "未登录或令牌已失效"))
                .accessDeniedHandler((req, resp, e) -> writeJson(resp, 403, "没有权限访问该资源")))

            // ⑤ 授权规则：★默认全部需要认证 + 白名单放行
            .authorizeHttpRequests(auth -> auth          // ← 不是 authorizeRequests()
                .requestMatchers("/api/auth/login").permitAll()   // ← 不是 antMatchers()
                .requestMatchers(HttpMethod.POST, "/api/session/create").permitAll()
                .requestMatchers(HttpMethod.POST, "/api/session/message").permitAll()
                // ★整段放行后必须把坐席侧接口收回来（见 1.5 节的踩坑）
                .requestMatchers(HttpMethod.GET, "/api/session/*").authenticated()
                .requestMatchers(HttpMethod.GET, "/api/session/*/messages").authenticated()
                .requestMatchers("/ws/**").permitAll()
                .requestMatchers("/actuator/health", "/actuator/info").permitAll()
                .anyRequest().authenticated())           // ★安全的默认值
            // ★★注意这个过滤器的名字和职责（这里的关键点）
            //   它叫 gatewayIdentityFilter，不叫 jwtFilter —— 因为它【不验 JWT】！
            //   业务服务不持有 JWT 密钥，它只读网关注入的、已经验过的身份头。
            .addFilterBefore(gatewayIdentityFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}

★★1.4.1 业务服务到底验不验 JWT？（这里有个容易自相矛盾的地方）

矛盾在哪：我一边说"网关统一验签，业务服务不持有密钥"，一边又在业务服务的配置里放了个 jwtFilter。面试官必然追问：业务服务究竟验不验？验的话密钥从哪来？不验的话 SecurityContext 怎么建立的？

统一后的口径（三步，必须完整）：

① 【网关】验证 JWT
     · 先【移除】外部传入的身份头（X-User-Id / X-Tenant-Id / X-Role）
       —— ★这一步不做，攻击者自己伪造一个 X-User-Id 就能冒充别人
     · 验签通过后，【写入】真实的用户 / 角色 / 租户信息

② 【业务服务】不验 JWT，只读可信的内部身份上下文
     · 用一个 gatewayIdentityFilter 从请求头读身份
     · 建立 Spring Security 的 Authentication（放进 SecurityContext）
     · ★不持有 JWT 密钥、不做签名校验

关键代码（业务服务侧）：

/**
 * 网关身份过滤器 —— ★注意：它不验 JWT！
 *
 * 【为什么不叫 jwtFilter？】因为业务服务根本不持有 JWT 密钥。
 * JWT 的验签在网关做完了，这里只是把网关验过的身份"翻译"成 Spring Security 能用的 Authentication。
 * 名字叫错会让人以为业务服务在验签 —— 这是一个很容易被追问的表述矛盾。
 */
@Component
public class GatewayIdentityFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain)
            throws ServletException, IOException {

        // ★读的是网关注入的内部头，不是 Authorization
        String userId = req.getHeader("X-User-Id");
        if (userId != null) {
            LoginUser user = new LoginUser(
                    Long.valueOf(userId),
                    req.getHeader("X-Username"),
                    req.getHeader("X-Real-Name"),
                    req.getHeader("X-Role"),
                    Long.valueOf(req.getHeader("X-Tenant-Id")));

            var auth = new UsernamePasswordAuthenticationToken(
                    user, null,
                    List.of(new SimpleGrantedAuthority("ROLE_" + user.getRole())));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, resp);
    }
}

③ ★配套的安全前提（这三条不说清，整个方案就是漏洞）

前提为什么必须
网关强制覆盖身份头否则外部伪造 X-User-Id: 1 直接越权。做法：网关入口先 removeHeader 再写入
业务服务不能被外部直接访问只能通过网关进。做法：服务只监听内网地址 / 安全组只放行网关 / K8s NetworkPolicy 限制
网关到服务之间要有访问控制不能只靠"调用方传来的请求头"——要有 mTLS 或内部签名，或者至少网络层隔离

★面试被问"业务服务怎么知道用户是谁"，标准答案：
"JWT 的验签只在网关做一次，网关验完把用户、角色、租户写进内部请求头；业务服务不持有密钥、不验签，只用过滤器把这些头翻译成 Spring Security 的 Authentication。
这个方案成立的前提是三点：网关必须强制覆盖外部传入的身份头、业务服务不能被外部直连、网关到服务之间要有访问控制。少任何一条，身份头就可以被伪造。"

⚠️ 这里要说一句实话：我在本地 Demo 里其实是让业务服务自己验的（因为只有一个服务、没有网关），但生产架构是网关统一验签。如果面试官问"你本地怎么跑通的"，照实说就行——本地是单服务简化版，网关验签是生产设计。这比含糊过去好得多。

⑤ 的顺序是重点：默认全部需要认证 + 白名单放行，而不是"默认放行 + 逐个加鉴权"。前者漏配的后果是"访问不了"，后者漏配的后果是"谁都能访问"——安全配置要选那个"出错时更保守"的默认值。

④ 为什么必须返回 JSON：前后端分离下如果返回 302 重定向到登录页，前端拿到的是 HTML，没法处理。

★这段是很好的面试素材：authorizeRequests → authorizeHttpRequests、antMatchers → requestMatchers 是 Spring Boot 2 升 3 时最常见的编译错误之一。能主动说出"我们升 Boot 3 时改的就是这两个方法名"，说明你真的做过升级。

1.5 ★踩过的真实坑：白名单开太宽导致越权

我一开始图省事写成：

.antMatchers("/api/session/**").permitAll()   // ❌ 本意只是让匿名顾客建会话

结果 /api/session/** 把坐席侧接口也一起放行了：GET /api/session/{id} 会返回顾客手机号和 AI 摘要，GET /api/session/list 会返回顾客所有会话。这等于把顾客隐私暴露给匿名请求。

我们本地实测确认过：不带任何令牌访问 /api/session/1 竟然能进到业务逻辑里（当时因为数据库没起才报 500，DB 正常就直接返回数据了）。而同一批次里 /api/ticket/pending、/api/agent/status 都是正确的 401 —— 说明框架配置没问题，纯粹是白名单开太宽。

修正后：精确到方法 + 路径，并把坐席侧的三条路径重新收回认证。

教训（可以直接当面试答案）：写 permitAll 的通配符时，一定要问自己一句"这个 ** 会不会顺带把我不希望公开的接口也放进来？"能用精确路径就不用 /**。

1.6 密码存储：为什么必须是 BCrypt

MD5 / SHA-256BCrypt
设计目标算得快故意算得慢
GPU 暴力破解每秒几十亿次，配彩虹表弱密码秒破单次约 60ms，成本高几个数量级
盐要自己加，容易加错自带随机盐，盐值存在哈希串里
长度32/64 字符固定 60 字符

一句话：密码存储要选"慢"的算法——它只在登录时算一次，慢一点用户无感，但能把攻击者成本抬高几个数量级。

cost 为什么选 10：每 +1 计算时间翻倍。10 约 60ms（可接受），14 接近 1 秒、登录明显变慢。机器变快了可以逐步提高全局 cost，用户下次登录时用新 cost 重新哈希，实现平滑升级。

1.7 两个容易忽略的安全细节（主动说出来是加分）

① 防用户名枚举：用户不存在和密码错误，统一返回"用户名或密码错误"。如果分开提示，攻击者就能靠返回信息枚举出系统里有哪些账号。

② 防时序攻击：如果"用户不存在"时直接 return、不执行密码比对，两类请求的响应时间会明显不同，照样能枚举账号。严谨做法是用户不存在时也做一次假的 BCrypt 比对（消耗同样时间）。

1.8 还没做的加固项（主动交代）

① 登录失败计数与锁定（Redis 记失败次数，5 次锁 15 分钟）；② 按 IP 限流防撞库；③ 连续失败后要求验证码；④ 登录审计（IP/UA/时间/成功失败，异常告警）；⑤ 刷新令牌与主动踢人。

模块二：客户与坐席（customer-service）

2.1 模块职责

管理客户（租户）、坐席、技能组、角色权限四块。核心产出是两个能力：坐席能不能接这个会话（技能组 + 在线状态 + 在服上限）、坐席能看哪些数据（RBAC + 数据权限）。

2.2 为什么顾客和坐席要分两张表

customer  = 业务对象（顾客），服务对象，几乎不登录（匿名进线）
sys_user  = 权限主体（坐席/管理员），必须登录，有角色和技能组

合成一张表的三个后果：① 所有权限判断都要加 WHERE type='AGENT' 过滤，越往后越难维护；② 字段大量为 NULL（坐席要密码/角色，顾客要会员等级）；③ 一旦有人在 SQL 里漏了这个过滤条件，顾客就能以坐席身份操作——这是越权漏洞的直接来源。

2.3 坐席分配：怎么保证不超配

问题：多个会话同时进来，如果"先查坐席在服数 → 判断有没有超 5 个 → 再分配"，这三步之间有时间窗口，并发下会把同一个坐席分超。

方案：用 Redis + Lua 脚本做原子扣减。Lua 在 Redis 里是单线程原子执行的，所以"判断 + 扣减"是一个不可分割的动作。

-- 伪代码
local cur = tonumber(redis.call('GET', key) or '0')
if cur >= max then return 0 end        -- 已达上限，分配失败
redis.call('INCR', key)
return 1

分配策略（按优先级）：空闲优先 → 技能组匹配 → 会话上限，一个坐席最多同时接 5 个。

验证方式：把上限设为 1 的坐席设成唯一在线，第 2 个会话必须排队而不是超配——这条要实测过才敢讲。

2.4 技能组：它是"分配规则"，不是"权限范围" ★这里最容易混

先把两个概念分清楚，很多人会混：

技能组（skill group）数据权限（data scope）
回答的问题这个会话该分给谁？这个坐席能看到什么？
谁决定系统/AI 分配时用查询时过滤用
作用时机分配那一刻每次查询
一句话路由规则可见范围

技能组的作用：顾客问退款 → 会话带着"售后"标签 → 分配器只在售后组里挑空闲坐席。所以它是按业务属性做路由，不是简单轮询。坐席不能自己选组，是系统按技能组分配。

那坐席到底能看到哪些数据？★你问的核心

这里必须分清"自己的"和"本组的"，它们不一样：

① 已经分配给我的会话/工单        → 能看，能操作（这是他的工作台主视图）
② 我所在技能组的「待领取」队列    → 能看，但只有"领取"后才能操作
③ 我所在技能组的统计看板          → 能看（组维度，不是个人维度）
④ 其他技能组的排队会话            → ❌ 看不到
⑤ 已分配给其他坐席的会话详情      → ❌ 看不到（除非是主管）
⑥ 全公司跨客户的经营数据          → ❌ 只有管理员能看

为什么②要可见、⑤要不可见？ 因为它们是两种不同的业务动作：

  • ②是"抢单"——会话还在排队，需要组内某个坐席主动接。如果只有被分配的人能看到，那排队队列就没意义了（分配器本来就要在组内广播找空闲的人）。
  • ⑤是"偷看"——已经有人在处理了，别人能看到只会造成信息泄露和职责混乱。

主管（ADMIN） 则能看到本客户下全部会话和工单，用于质检和调度。

一句话总结：技能组决定"谁被分配"，数据权限决定"谁看得见"。坐席的主视图是"我的会话 + 本组待领队列"，而不是"本组所有会话"。

数据权限的两种实现方式

① SQL 层拼条件——用 MyBatis 拦截器自动在查询后追加 AND (assignee_id = 当前用户 OR (group_id = 我的组 AND status = 'WAITING'))；
② 注解 + AOP——方法上标 @DataScope，切面里把权限条件塞进查询参数。

我们用的是第一种，因为它在 SQL 层统一生效，不依赖开发者记得加注解。

为什么这个区分很重要（面试价值）：如果你答"坐席能看本组所有会话"，面试官会立刻追问"那别人正在处理的会话，他能不能看顾客手机号？"——这一问就暴露你没想清楚数据权限的边界。能主动把"我的 / 本组待领 / 本组全部"三层分开讲，才是真设计过。

2.5 坐席状态与在服计数的一致性

有一类隐蔽 bug：坐席异常断线（关浏览器、网络断），Redis 里的在服计数没被减掉，导致这个坐席永远"满负载"、再也接不到会话。

处理方式：① 坐席状态带 TTL 心跳，WebSocket 断开时主动清理；② 加一个对账任务，定期比对"Redis 计数"和"数据库里真实在服会话数"，不一致就修正。

面试价值：这类"缓存与数据库不一致"的问题，主动讲出来比只讲正常流程有说服力得多——它说明你真的维护过线上系统。

2.6 权限模型：RBAC + 数据权限两层

我们的权限分两层，很多人只做第一层就上线了，结果埋了越权隐患：

第一层 · 功能权限（RBAC）——"能不能点这个按钮"

sys_user ──→ sys_role ──→ sys_role_permission ──→ sys_permission
  坐席        售后组角色      查看会话/建工单         菜单、按钮、接口

判断粒度在接口级。实现方式有两种：@PreAuthorize("hasRole('AGENT')") 注解式，或者在网关/拦截器统一校验。我们用注解式，因为它离代码近、可读性好，review 时一眼能看出这个接口要什么权限。

第二层 · 数据权限——"能看到哪些数据"
这层才是关键：坐席有"查看会话"的权限，不代表能看所有会话。可见范围按 2.4 节那三层来分：

坐席张伟（售后组）→ 自己的会话（全部）+ 本组待领队列（可看可领）+ 本组统计
                   ✗ 其他组的会话   ✗ 别人已接手的会话详情
主管李娜（ADMIN） → 本客户下全部会话和工单

实现方式：MyBatis 拦截器自动拼条件，查询时追加
AND (assignee_id = 当前用户 OR (group_id = 我的组 AND status = 'WAITING'))。
为什么不在每个 SQL 里手写：因为人会忘。只要有一个查询漏写了条件，就是一个越权漏洞，而且很难被发现——因为它在功能上"看起来正常"。放在拦截器里统一生效，不依赖开发者记得加。

2.7 坐席状态机与工作台数据聚合

坐席状态有四种：在线 / 小休 / 忙碌 / 离线。状态直接决定能不能被分配会话——只有"在线且未达上限"的坐席进入分配池。

为什么要有"小休"：坐席去吃饭、上厕所时如果只能"离线"，回来还要重新登录、重新排队；"小休"让他保持在池子里但不接新会话，回来点一下就能继续。

坐席工作台首屏要聚合四类数据，这是"一次请求要打四个服务"的典型场景：
① 当前坐席状态和负载（customer 服务）
② 我的会话列表 + 未读读秒（conversation 服务）
③ 顾客资料和订单卡片（conversation + 外部订单服务）
④ 今日接待量等指标（report 服务）

性能优化：用 CompletableFuture 并行调这四个服务，总耗时取决于最慢的那个而不是四个相加；并对"顾客资料"这种读多写少的数据加 Redis 缓存。

面试价值：这是一个很自然的"你项目里哪里用了多线程"的答案——不是为了炫技而用，是聚合接口的刚需。

模块三：会话消息（conversation-service）

3.1 这个模块是整个系统的"心脏"

所有顾客的消息都从这里进，所有坐席的回复都从这里出。它的三个技术难点是：实时性（WebSocket）、多实例一致性（消息路由）、顺序性（同一会话不乱序）。

3.2 为什么用 WebSocket 而不是轮询

客服会话是双向实时的：顾客发消息要立刻到坐席，坐席回复也要立刻到顾客。

  • 轮询：要 2~3 秒一次，200 个坐席 × 数千活跃会话会产生大量空请求；而且延迟最低也有一个轮询周期。
  • WebSocket：一次 HTTP 握手升级协议后全双工，服务端能主动推，延迟是毫秒级。

被追问"为什么不用 SSE"：SSE 是单向的（服务端 → 客户端），顾客要发消息还得另开 HTTP 接口，等于两条通道；WebSocket 双工，一条搞定。

3.3 ★核心难点：多实例下的消息路由

问题现象：坐席 A 连在实例 1 上，顾客消息被实例 2 收到——实例 2 上没有坐席 A 的连接，消息就丢了，坐席收不到。

定位过程：抓日志发现同一个 sessionId 同时出现在两台机器上；Redis 里的路由 key 没有随会话结束删除，留下"僵尸路由"。

★★这里有个必须讲清楚的坑

常见写法是三步：

① Redis 存路由表：session_route:{sessionId} → {instanceId}
② 消息先写 Kafka，按 sessionId 分区（保证同一会话进同一分区、天然有序）
③ 各实例消费后，只推送本机持有的连接；不是自己的就跳过   ← ❌ 错在这里

第 ③ 步是错的，而且会导致消息丢失。 问题在于：

  • Kafka 是消费组模型——一个分区只会被组内一个实例消费。
  • 假设分区 3 分给了实例 2，而坐席 A 连在实例 1 上（路由表也指对了）：实例 2 消费到消息后，发现本机没有坐席 A 的连接，就直接跳过了。实例 1 根本收不到这条消息。
  • 更糟的情况：路由表是陈旧数据（坐席刚重连到别的实例、或者实例刚宕机），那就彻底投丢了。
  • 本质问题：写 Kafka 的实例和持有连接的实例，可能不是同一个。而"跳过"等于丢弃。

正确方案：Kafka 只做持久化和广播触发，投递靠实例间定向转发

① 每个实例启动时订阅自己的 Redis 频道：ws:instance:{instanceId}
② Redis 维护路由表：session_route:{sessionId} → {instanceId}   （TTL 30 分钟兜底）

③ 消息投递路径（两种情况都覆盖）：
   ┌ 目标客户端在本机  → 直接推（快路径，占比高）
   └ 目标客户端不在本机 → 用 Lua 脚本原子地"查路由 + 发布"到 ws:instance:{目标实例}
                         目标实例收到后，推给本机持有的那个连接

④ 消息仍然写 Kafka，但它的职责变成：
   · 持久化 / 回放（新实例扩容时能补上错过的消息）
   · 异步业务（质检、统计、工单事件）
   —— ★Kafka 不再承担"实时投递"这个职责了

为什么要用 Lua 脚本做"查路由 + 发布"：这两步之间如果分开做，路由表可能在中间被改（坐席刚好重连），导致发到错误的实例。Lua 在 Redis 里是单线程原子执行的，把这个窗口消掉。

可靠性兜底（三层）：

层机制防什么
①WebSocket 发送失败要捕获异常，不能静默吞掉连接刚好断了
②投递回执：客户端收到消息回 ACK，服务端标记已投递消息发出去了但对方没收到
③未 ACK 的消息进重试队列，客户端重连后按最后一条消息 ID 补拉（见 3.5）实例宕机、网络抖动导致的丢失

★"重试队列"存在哪里？—— 这里有个容易漏掉的缺口（容易漏）

如果重试队列只是进程内队列（Java 的 BlockingQueue、Python 的 asyncio.Queue），那实例一宕机，队列里的未确认消息就全丢了——整个第三层兜底等于没有。

正确做法：重试队列必须落在持久化存储里。

未 ACK 消息 → 写【Redis 的 ZSET】或【MySQL 的待投递表】
    score / 字段 = 下次重试时间戳
    一个后台任务按时间扫，重投；重投 N 次仍失败 → 标记为"投递失败"并告警

客户端重连后：
    上报自己收到的最后一条消息 ID → 服务端从持久化消息表里补拉这条之后的
存储选择适用
Redis ZSET（我们用这个）快，且天然按 score 排序做延时重试。★但 Redis 也要开持久化（AOF）
MySQL 待投递表更可靠，但写入压力大、每次重试要查库
Kafka 重试 topic最适合"重试次数多、要削峰"的场景，但要处理顺序问题

★还有一个概念要纠正（容易漏）：不要说"Kafka 保证消息不丢"

这句话太绝对。Kafka 的持久性取决于配置：

配置影响
acksacks=0/1 时 broker 挂了会丢；要设 acks=all
replication.factor副本数 < 2 时，那台机器挂了就丢
min.insync.replicas配合 acks=all 才真正生效
enable.auto.commit消费者自动提交 offset 会导致"没处理完就提交"→ 丢消息，应该手动提交

★而且 Redis Pub/Sub 本身是"至多一次（at-most-once）"投递——订阅者离线时发布的消息直接就错过了。Lua 能保证"查路由 + 发布"这组 Redis 操作原子执行，但它保证不了目标 WebSocket 客户端一定收到。

所以最终的正确说法是（这段直接背）：

"Kafka 负责持久化消息和异步业务处理，Redis Pub/Sub 负责实例间快速转发，WebSocket 负责最后一跳推送。
Pub/Sub 只是传输通道，它的投递是至多一次的——可靠性最终靠三样东西兜住：持久化的消息本身、客户端的 ACK 确认、以及重连后按消息 ID 的补偿补拉。
换句话说：实时投递允许丢，但消息在 Kafka 和数据库里，丢了能补回来。"

★这个说法的好处：它承认了"实时通道不可靠"，并且说清了兜底在哪里——这比"我们用了 Kafka 所以不丢"可信得多，也是分布式系统的正确思维：不追求通道可靠，追求"丢了能发现、能补"。

★关键认知（面试可以直接讲）：
"只做路由表是不够的，还要考虑'消费到消息的实例不是持有连接的实例'这种情况。
后来修正成'Kafka 管持久化、Redis 管转发、ACK 管确认、补拉管补偿'。
核心是：不指望实时通道不丢，而是保证丢了能补回来。"

结果：消息串话问题归零，P99 投递在 500ms 以内（含落库、路由转发、推送三段）。

★补一句诚实标注：上面的 P99 500ms 是我们压测环境的设计目标，不是生产实测值（详见文末"关于成果表述的说明"）。

3.4 消息顺序怎么保证（★注意边界）

按 sessionId 做 Kafka partition key → 同一会话的消息必然进同一分区 → Kafka 保证分区内有序 → 消费者单线程消费该分区。

这里有个必须讲清的边界：Kafka 只保证分区内有序，不保证全局有序。所以 key 的选择就是关键——我们选 sessionId，因为业务上只有"同一会话内有序"这个需求，跨会话乱序无所谓。如果选了 userId 做 key，同一用户的多会话会挤在一个分区里，反而降低并行度。

★但"分区有序"≠"整个异步链路有序"，这一点确实要注意：

  • 转成异步之后顺序会变。比如"转人工"和"坐席接入"是两个异步事件，如果分属不同 topic / 不同消费者组，到达顺序就不保证。
  • 实例间转发会引入新的乱序：走 Redis Pub/Sub 转发的那条路径，和本地直推的路径，延迟不同——同一个会话的消息可能"后发先到"。
  • 应对办法：① 消息带单调递增的序号（用 Redis INCR 按 sessionId 生成），客户端按序号排序后再渲染，而不是收到就显示；② 对顺序敏感的操作（比如状态流转）在数据库层用状态机校验，不接受乱序的非法流转，而不是依赖到达顺序。

3.5 断线重连与消息不丢不重

① 心跳：客户端 25 秒发一次 PING，服务端回 PONG。为什么是 25 秒——Nginx 默认 60 秒空闲就断连接，必须小于它。

② 重连后补拉：客户端记住最后收到的消息 ID，重连后按 ID 往后拉。

③ 幂等去重：每条消息带客户端生成的唯一 ID（clientMsgId），服务端做去重。所以补拉重发不会出现重复消息。

为什么幂等必须做：网络重连、用户连点、客户端自动重试都会产生重复请求。没有幂等，顾客会看到自己的话出现两遍，甚至重复建工单。

3.6 为什么消息要先落库再异步处理

顾客消息 → WebSocket 收到 → 先落库 MySQL（同步，快）→ 发 Kafka → 消费者异步处理（AI 应答/推送）

关键原则：WebSocket 的 IO 线程绝不能被慢操作阻塞。 如果收到消息后同步去调 AI（2~4 秒），消息就积压在 Netty 的 IO 线程里，整个连接的收发都卡住。

这条原则对应的是模块六那个"消息堆积"场景（★性质见 6.7 节的标注——那是我们按生产环境推演 + 本地模拟复现的场景分析，不是真实线上事故）。

3.7 单例 Handler 的陷阱

如果 WebSocket Handler 写成单例（Spring Bean 默认单例），那就绝对不能把连接状态放在成员变量里：

// ❌ 严重错误：所有连接共享这一个字段
private Long currentSessionId;

// ✅ 正确：状态放在每个连接自己的 attributes 里
wsSession.getAttributes().put("sessionId", sessionId);

这个坑极隐蔽：本地单人测试完全正常，一上并发就串消息——张三的连接被李四覆盖。

3.8 消息表设计

message(id, tenant_id, session_id, sender_type, sender_id, msg_type,
        content, extra_json, client_msg_id, send_time)
  • sender_type：1 顾客 / 2 AI / 3 坐席 / 4 系统。为什么系统消息要独立一个类型——因为运营统计"AI 回答量"时不能把"已为您转接人工"这种系统提示也算进去，否则数据失真。
  • client_msg_id：幂等去重用的唯一键。
  • 按月分表：单客户日均 6 万条，一个月约 180 万行——分表主要是为归档和历史查询方便，不是为了扛写入。

全文检索走 ES：坐席要按关键词搜历史会话和工单，MySQL 的 like %x% 走不了索引。ES 里用 send_time 做时间范围过滤 + 内容分词检索。

模块四：工单 + SLA（ticket-service）

4.1 SLA 是什么、为什么要做

SLA（服务等级协议）是给服务定"时限承诺"：工单必须 X 分钟内首次响应、Y 小时内解决，超时要升级。

对一个交付型系统来说 SLA 是刚需——客户买系统就是为了管住服务质量的量化指标，没有 SLA 就只是一堆工单列表。

4.2 SLA 的两个时限 + 暂停计时

双时限：首响时限（first response）和解决时限（resolve），按工单优先级不同配置。

★暂停计时必须讲清的四个细节（不然一问就露）

只写"加个 paused_time 累计字段"，太粗。完整设计需要回答四个问题：

① 暂停的起止怎么记？——需要两个字段，不是一个：

paused_at      DATETIME  -- 本次暂停的开始时刻；非暂停态为 NULL
paused_total   INT       -- 历史累计暂停秒数
  • 进入"待客户回复" → 写 paused_at = NOW()
  • 客户回复、离开该状态 → paused_total += TIMESTAMPDIFF(SECOND, paused_at, NOW())，同时 paused_at = NULL
  • 为什么必须分开：只用一个累计值，无法处理"当前正在暂停中"这个瞬时状态——扫描任务算不出这一刻已经暂停了多久。

★这里有个坑：用 paused_at IS NOT NULL 判断"是否在暂停"。如果只判断字段非空、忘了在恢复时把它置回 NULL，工单会永久暂停、SLA 再也不计时——这是很隐蔽的 bug，而且只在"客户回复后"才暴露。

② 两个时限都允许暂停吗？——不，要分开：

时限是否允许暂停为什么
首响时限❌ 不允许首响是我们单方面的责任——客服就该主动回复，客户回不回不影响"我们响应得快不快"
解决时限✅ 允许解决往往需要客户配合（提供订单号、补充截图）。等客户的那段时间不该算在我们头上

这个区分很重要：如果两个都允许暂停，坐席可以靠"把工单挂成待客户回复"来逃避首响考核——考核就失效了。

③ 真实剩余时间怎么算？

-- 解决时限：要考虑"历史累计暂停" + "当前正在暂停的那一段"
剩余 = sla_resolve_deadline
     + INTERVAL paused_total SECOND
     + IF(paused_at IS NULL, 0, TIMESTAMPDIFF(SECOND, paused_at, NOW()))
     - NOW()

④ 多次暂停怎么处理？——累加。paused_total 是累加值，不是单次时长，所以"暂停-恢复-再暂停"天然支持。

结果：超时误判率从 12% 降到 1% 以内。

★诚实标注：这是我们按新逻辑重算历史工单得到的对比结果，不是上了生产跑一个月统计出来的（见文末说明）。

追问"跨天怎么办" → 存的是绝对时间戳不是时长，所以跨天天然没问题；扫描任务分钟粒度，也不需要处理工作日历（那属于进阶需求）。

4.3 ★定时任务多实例的幂等问题

问题：@Scheduled 在 N 个实例上会同时执行，导致同一批工单被重复升级。

★只做 CAS 是不够的——完整幂等要三件套

常见写法是"用数据库 CAS 就够了"。但 CAS 其实不够：CAS 只能保证"同一时刻只有一个成功"，但挡不住下面这些情况：

  • 重试（调度框架本身会重试、网络超时后重发）—— 同一个 escalate_level 的升级可能被提交两次
  • 两个不同的扫描任务（首响扫描 + 解决扫描）同时想升级同一张工单
  • 人工操作与定时任务并发（主管手动升级的同时扫描任务也在升级）

完整方案：唯一约束 + CAS + 状态校验，三层都要。

第一层 · 升级事件表加唯一约束（防重放的根本手段）

CREATE TABLE ticket_escalation (
    id          BIGINT AUTO_INCREMENT,
    ticket_id   BIGINT NOT NULL,
    from_level  TINYINT NOT NULL,
    to_level    TINYINT NOT NULL,
    reason      VARCHAR(32),      -- FIRST_RESPONSE_TIMEOUT / RESOLVE_TIMEOUT / MANUAL
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    -- ★核心幂等键：同一工单 + 同一升级前等级 + 同一原因，只允许一条记录
    -- ★必须带 reason！因为首响超时、解决超时、人工升级是三种不同的业务事件，
    --   同一等级可能因不同原因各升级一次，只锁 (ticket_id, from_level) 会误拦合法升级
    UNIQUE KEY uk_ticket_level (ticket_id, from_level, reason)
) COMMENT = '工单 SLA 升级事件';

为什么幂等键是 (ticket_id, from_level, reason)：

  • from_level —— 标识"这次升级是从哪一级发起的"，重复执行时它必然相同，所以是幂等键的核心。
  • reason 不能省 —— 首响超时、解决超时、人工升级是三个不同的业务事件。同一张工单从同一等级，可能先因"首响超时"升一级，后来又因"解决超时"再升一级。只锁 (ticket_id, from_level) 会把第二次合法升级也拦掉。

★这里有个容易踩的坑——幂等键不是"越严越好"，太严会误拦合法操作，要按"业务事件的唯一性"来设计。

第二层 · CAS 更新（防并发写）

UPDATE ticket
   SET escalate_level = escalate_level + 1,
       update_time    = NOW()
 WHERE id = ?
   AND escalate_level = ?          -- 期望的旧值，不匹配就影响 0 行
   AND status NOT IN ('CLOSED', 'RESOLVED')   -- ★状态校验，别升级已完结工单

第三层 · ★事务边界：插记录 + 改状态必须在同一个事务里

① INSERT INTO ticket_escalation (...)   ← 撞唯一键就说明已升级过，直接返回
② UPDATE ticket ... WHERE escalate_level = ? AND status NOT IN (...)
③ 发 Kafka 升级通知事件（通知主管、发短信）

★为什么必须同事务（这一步最容易漏，后果最隐蔽）：

如果两步不在一个事务里，会出现：升级记录插成功了、工单更新失败了（比如 CAS 影响 0 行、或者连接断了）。结果是：

  • 重试时被唯一约束拦住（记录已存在）
  • 但工单实际上没有升级

这张工单就永远漏了升级，而且没有任何告警——因为从数据库看"升级记录是有的"，监控也发现不了。

@Transactional   // ★两步同事务，任一步失败整体回滚
public void escalate(Long ticketId, int fromLevel, String reason) {
    escalationMapper.insert(...);            // ① 撞唯一键 → 抛异常 → 整个事务回滚
    int n = ticketMapper.casEscalate(...);   // ② 影响 0 行 → 也回滚
    if (n == 0) throw new BizException("工单状态已变化，升级失败");
    // ③ 通知不能写在这里！要挂到"事务提交后"再发
}

★通知为什么要放到事务提交后：如果用 TransactionSynchronization 之外的方式在事务内就发了 Kafka 通知，万一事务最后回滚——主管已经收到"工单已升级"的消息，实际却没升级。所以要挂在 afterCommit 里发。

★★但 afterCommit 只保证"时机"，不保证"送达"（一个容易漏掉的点）

这是一个我原来没说清的边界：

afterCommit 解决的是"别在事务内发、免得回滚了通知已经出去"这个问题。但它不能保证通知一定发出去——如果数据库提交成功之后、Kafka 通知真正发出去之前，应用进程突然退出了（宕机、被 kill、发版重启），这条通知就永久丢了，而且没有任何痕迹。

所以要把两件事分开讲，不能混为一谈：

解决什么问题不解决什么
afterCommit 发通知通知的时机正确（不会"工单没升级却发了通知"）❌ 不保证送达——提交后进程挂了就丢了
Outbox 模式通知的最终送达（提交成功 ⇒ 最终一定会投递）代价是多一张表 + 一个扫描任务

标准答法（这段直接背）：

"当前我们是通过事务提交后发送通知，避免'工单更新失败但通知已经发出去'这种情况。
不过提交后发送仍然有一个失败窗口——数据库提交成功、Kafka 还没发出去的时候进程挂了，通知就丢了。
要进一步保证最终投递，可以采用 Outbox：在业务事务里同时写工单和一条待发送事件，再由独立任务把 outbox 里的记录可靠投递到 Kafka，并由消费者幂等处理。这样'提交成功'就等价于'最终一定会投递'。
我们目前没实现 Outbox，这是已知缺口。"

★这个区别为什么值得讲：它体现你知道"通知时机正确 ≠ 消息一定送达"——这是分布式系统里一个很容易被忽略的边界。能主动说出自己方案的失败窗口在哪，比说"我们用了 afterCommit 所以没问题"可信得多。

顺序上"先插记录再改状态"也有讲究：先插记录让唯一键成为第一道闸门，后面的 CAS 失败就整体回滚，不会留下"升级了但没记录"的不可追溯状态。

为什么不用分布式锁：锁能防并发，但防不了重试（第一次执行完释放锁，重试进来照样能拿到锁）。幂等要靠"唯一约束 + 条件更新"，不能靠锁。

验证方式（★必须能说出怎么测）

测试做法期望
并发扫描同时触发 N 个实例扫描同一批工单escalate_level 只 +1
重复执行对同一张超时工单连点 3 次手动扫描只 +1，且 ticket_escalation 只有 1 条
状态校验把工单置为 CLOSED 后再触发扫描不升级（CAS 的 status 条件拦住）
人工+定时并发手动升级的同时触发扫描只 +1

面试价值：这题答"用 XXL-JOB"只能算及格；答出"CAS 不够，还要唯一约束防重放"才是加分——
因为锁和 CAS 都防不了重试，唯一约束才是幂等的最后一道防线。

4.4 为什么不用 Flowable 这类工作流引擎

状态机 = 有限状态 + 允许的流转规则。我们把合法流转写在代码里校验，非法操作直接抛业务异常（比如"已关闭"的工单不能再"解决"）。

不用引擎的理由：我们的流转规则简单且固定（待处理 → 处理中 → 待客户回复 → 已解决 → 已关闭），引入工作流引擎的学习成本和维护成本大于收益。引擎适合流程经常变、节点动辄几十个的场景。

能说出"什么时候该用引擎"比只说"我们不用"更值钱。

4.5 工单模板与自定义字段

不同客户的工单字段不一样（退款单要订单号，技术故障单要复现步骤），所以用模板 + 自定义字段 JSON：

ticket_template(id, tenant_id, name, type, field_json, flow_json, sla_json, status)

为什么用 JSON 而不是动态建表：动态 DDL 在生产上极危险（锁表、无法回滚、权限要求高）；JSON 字段配合 MySQL 8 的 ->> 语法也能查询和建索引，灵活性和可控性平衡得更好。

4.6 触发器（轻量工作流）

两类：流转触发器（工单状态变为某值时自动执行动作，如"类型=退款 且 状态=待处理 → 自动指派财务组"）、定时触发器（创建超过 24 小时且未完成 → 提醒处理人）。

实现方式：事件驱动（Kafka 事件 + 规则表达式匹配），不做通用工作流引擎——避免过度设计。

ticket_template     工单模板（自定义字段 field_json + 流转 flow_json + SLA 规则 sla_json）
ticket_flow_log     流转日志（node / operator / action / from_status / to_status）
ticket_comment      评论（is_internal 区分内部备注和对外回复）

ticket_sla          SLA 规则（按优先级配首响/解决时限、预警百分比、升级对象）

模块五：知识库（knowledge-service）★Python 侧

技术栈：Python + FastAPI + LangChain（文档 Loader / TextSplitter / Embedding / Retriever）
这是双栈里的第二个 Python 服务——因为文档解析、分片、Embedding、重排这一整套链路，
Python 生态的库又全又稳（LangChain 的 document loader 覆盖几十种格式），Java 侧投入产出比差很多。
对应的 Java 侧是 ticket-service 里的知识库管理接口（文档上传/权限/审计），
但解析和检索这份"智能活"在 Python 侧。

5.1 为什么知识库要独立成服务

三个原因：① 向量检索是重活，和业务查询争资源；② 数据形态不同（文档/切片/向量 vs 结构化业务数据）；③ 它要被多个服务消费——ai-agent-service 要检索、坐席工作台要展示、报表要统计命中率。

5.2 文档入库的完整链路

上传文档 → MinIO 存原文 → 写 knowledge_document（状态=解析中）
   → Kafka 发向量化任务
   → 文档解析（按标题层级切分 chunk）→ 调 Embedding 模型
   → 写向量库 + 写 knowledge_chunk 表 → 状态改"已生效"

为什么走 Kafka 异步：解析 + 向量化一个 10MB 的 PDF 可能要几十秒，绝不能卡住上传接口。上传接口只负责存原文和发消息，立刻返回。

文档更新怎么做增量：按 doc_id 覆盖对应的 chunk（先删旧 chunk 再写新的），并带版本号。这里有个坑——换 Embedding 模型时，必须全量重建索引，因为新旧模型的向量空间不兼容，混在一起检索结果是错的。

5.3 ★分片（chunking）策略

结构感知分片 + 重叠窗口，不是固定字数切：

策略说明
① 按文档结构切先解析标题层级，一个"三级标题 + 正文"作为一个语义单元
② 单块 300~500 字超过就再按段落切
③ 相邻块 15% 重叠防止答案跨块时被切断
④ FAQ 不切一问一答本身就是完整语义单元，直接把"问题 + 相似问法"生成一份向量
⑤ 每块带元数据所属文档、章节、生效范围，检索时可按元数据过滤

为什么不用固定 500 字切：固定长度会把"退货政策第 3 条"拦腰截断，检索时只召回前半句，模型就答不全。按语义边界切，召回的是完整规则。

被追问"chunk 太大/太小分别有什么问题"：

  • 太大：一份 chunk 里混了多个主题，向量表示被"平均"掉，检索精度下降；而且塞进 prompt 浪费 token。
  • 太小：语义不完整，答案被切断；而且召回条数变多，重排负担重。

5.4 ★混合检索：为什么不是纯向量

方案：向量检索（语义）+ ES 的 BM25（关键词）→ RRF 融合 → 重排取 Top5。

强项弱项
纯向量"能不能退" ↔ "退货条件" 这种同义不同字精确词召回不稳："订单号""退款期限"
纯关键词精确词口语化表达召回差

两者互补，所以做混合。RRF（Reciprocal Rank Fusion）是一种不需要调权的融合算法——它用"排名"而不是"分数"来融合，因为向量相似度和 BM25 分数量纲完全不同，直接加权是错的。

RRF score = Σ 1 / (k + rank_i)     k 通常取 60

★★这里有个坑必须讲清（面试很可能被追问）

错在哪：常见写法是"RRF 融合后取最高分作为 topScore，再和 0.72 比较"。这是错的，而且错得很致命。

算一下 RRF 的值域（★注意：我们实际是两路召回——向量 + BM25）：

第 1 名 = 1/(60+1) = 0.0164
第 2 名 = 1/(60+2) = 0.0161
...
我们只有 2 路召回，某条 chunk 在两路里都排第 1：
   RRF = 1/61 + 1/61 = 2/61 ≈ 0.0328   ← 这才是我们的理论最大值

我们的 RRF 分数整个值域只有 0 ~ 0.0328，永远不可能 ≥ 0.72。
所以如果真按"RRF 分数 < 0.72 就兜底"来写，结果是 100% 的查询全部被判为"无召回"、全部走兜底转人工——系统等于完全不工作。

★注意：常见的错误算法是"5 路召回全排第 1 = 0.082"。那是错的——要看实际有几路召回，而我们只有两路。虽然结论（永远达不到 0.72）不变，但数字必须按自己的架构算，否则被追问"你们几路召回"就露馅了。

根因：把几种量纲完全不同的分数混为一谈了。

分数类型值域含义能不能设阈值
向量余弦相似度0 ~ 1语义相近程度✅ 有绝对意义，能用阈值
BM25 分0 ~ 几十（无上界）关键词匹配强度❌ 只能用于排序
RRF 分0 ~ 约 0.033（两路）名次倒数之和❌ 它不是语义相似度，不能直接套 0.72 这种阈值
重排（rerank）分取决于模型，不保证 0~1交叉编码器给出的相关性⚠️ 要先确认分数是否归一化，再定阈值

★这里这里还有一个容易写错的表述（容易漏）：
常见写法是"重排分 0 ~ 1"——这不成立。不同重排模型的输出可能是未归一化的 logits，也可能经过 Sigmoid 等处理。
正确说法：要先确认用的哪个重排模型、分数是否归一化，才能决定阈值怎么设。
★不要写成"我们用的是 XX 模型、输出落在 0~1"——如果实际模型和归一化方式还没确认，这就不是已落地的事实。正确说法：
"重排模型的输出范围取决于模型本身和它的分数处理方式；我们的 0.72 阈值是结合实际用的重排模型、通过评测集定的，不是通用值。"
面试时如果被追问具体模型：说得出就说，说不出来就诚实讲"这块是我同事负责的模型选型，我用的是他给的接口和阈值"——比编一个模型名安全。
如果被问"你的重排分是怎么来的"：答"我们记录了重排模型名称和版本，分数做了归一化；阈值是通过评测集定的，不是拍脑袋"。

正确的做法（修正后）

阈值只作用在"有绝对意义、且经过确认"的分数上；RRF 只负责排序。

① 向量检索   → 余弦相似度 sim（0~1，有绝对意义）
② BM25 检索  → bm25 分（无上界，只用于排序）
③ RRF 融合   → 产出【融合分数】，但它只用来排名；★它不是语义相似度，不参与阈值比较
④ 取 Top5 送重排 → rerank 分（★是否 0~1 取决于模型，要先确认）
⑤ ★阈值判断（最终口径）：
      · 召回为空（向量和 BM25 都没命中）→ 兜底
      · 重排分不达标（如 < 0.72）      → 兜底
      ★注意：向量 sim 低【不能单独】决定兜底 —— 见下面"第三个问题"

为什么用"重排分"而不是"向量相似度"做最终阈值：向量相似度是双塔模型算的（问题和文档分别编码），精度有限；重排是交叉编码器（问题和文档拼在一起过模型），精度高得多。所以最终判据用重排分更可靠。

★这里有个"规则打架"的坑：如果阈值里写一条"向量最高相似度 < 0.60 → 可能直接兜底"，后面又说它"不能当硬过滤"，同一个流程里放两条矛盾的规则，执行时就会出错。
已删除旧的那条——最终口径就是上面这两条：召回为空 或 重排分不达标。向量相似度只作为"要不要调重排"的成本参考，不作为独立的兜底判据。

★★第三个问题：0.60 的向量硬过滤，可能误杀 BM25 的正确结果

这是一个比前两个更重要的真实风险：

场景：顾客发来一个精确的退款编号或错误码（比如 RF20260915003）。这种情况：

  • BM25 会命中得很好——精确词匹配是它的强项
  • 但向量相似度可能很低——因为这种编号在语义空间里"没有意义"，双塔模型算不出高相似度

如果我先用"最高向量相似度 < 0.60"就提前兜底，就会把这条件本来答得对的问题推给人工——BM25 明明已经找到了正确内容。

修正后的原则：

把"向量粗筛"从"硬过滤"降级为"参考信号"。

判断顺序应该是：
① 先看融合后的候选里有没有东西（向量或 BM25 命中都算有）
② 有候选就送重排——让重排这个更准的模型来判
③ 最终是否兜底，看重排分
④ 只有在"向量和 BM25 都没命中"或者"重排分不达标"时才兜底

换句话说：sim < 0.60 不足以单独决定兜底，它只能作为一个"可能没必要调重排"的优化提示，而且必须结合 BM25 的命中情况一起看。

★而且这个 0.60 到底该不该留、留多少，要通过实际测试确定——用评测集分别测"只看向量"和"看融合结果"两种策略的准确率，看哪个更好。不要凭直觉写死一个硬过滤。

★两个阈值（0.60 / 0.72）都是经验起点，不是理论最优值——怎么定见 6.2 节的方法。

面试价值：这个问题很容易被追问——"你们用的 RRF 分数是多少？阈值怎么设的？"
如果你答"RRF 分数和阈值比"，懂行的面试官立刻知道你没真跑过。
能主动说出"RRF 的分数不是语义相似度，不能直接套阈值"，以及"向量的硬过滤会误杀精确词命中"——这两点说明你真的理解混合检索里每种分数在干什么。

5.5 两阶段召回（先粗筛再精排）

先按意图分类把范围锁定（比如判定是"退款"意图，就只在退款分类里搜），再算相似度取 Top5。

为什么：如果全量算相似度，"退款多久到账"和"怎么申请退款"字面相似度很高（都有"退款"），可能把"怎么申请"排在前面，答非所问。先用意图缩小范围，准确率明显提升。

这和推荐系统的"召回-排序"两层是同构的。

模块六：AI Agent 编排（ai-agent-service）★Python 侧

这是双栈里的"智能侧"核心服务，也是全项目改动最勤的一个模块。

6.0 为什么这个模块用 Python

核心原因一句话：我们要的是带循环和条件分支的 Agent 状态图——这类有环编排在 Java 生态里要自己搭状态管理和流程控制，而 LangGraph 把它做成了一等公民，所以我们把智能侧放在 Python。

  • LangGraph 把 Agent 建模成状态机：支持循环、条件边、断点恢复、人工介入（human-in-the-loop）。
  • Spring AI 的 ChatClient 是请求-响应式的链式调用，表达这种"状态图即代码"的有环编排要费劲得多——注意不是"做不了"：它支持工具调用循环，也有编排扩展，用 Spring AI 加 Java 自定义控制流同样能实现，只是要自己组织更多的状态管理和流程控制逻辑。我们选 LangGraph 是因为它的状态图模型跟这个场景更匹配。
  • 加上 AI 生态三个月一代新东西，Python 是第一现场，这个模块又改动最勤，放 Python 性价比最高。

完整四层答法见《面试追问Q&A》的 Q24——那是必问题。

6.1 ★完整链路（要能画出来）

★注意：下面这条链路是 LangGraph 的一张状态图（StateGraph），不是一条直线。
节点之间有条件边，调完工具会回到 LLM 节点再判一次——这就是"有环"的含义。

★★这里有个真实的流程设计缺陷，必须重画

原来的错：我把流程写成了"RAG 检索 → 阈值判断 → 通过之后才判断要不要 Tool Calling"。

这个顺序有个致命问题：顾客问"我的快递到哪了"——

  • 知识库里当然没有这个订单的物流信息 → RAG 召回为空 → 直接兜底转人工
  • 而查物流的工具根本没机会被调用

用户问的是一个完全能查的问题，却被机器人推给了人工。 而且客服场景里"查订单/查物流"是最高频的咨询之一，这个 bug 会让 AI 的核心价值失效。

根因：我把"知识问答"和"实时业务查询"当成了同一条路径，用 RAG 的分数去否决了本该走 Tool Calling 的请求。

④-A 【RAG 分支】向量（sim）+ BM25 → RRF 融合排序 → Top5 送重排 → rerank 分
       ↓
     阈值判断：召回为空（向量和 BM25 都没命中）/ 重排分不达标 → 兜底
       ★只有这条分支受阈值约束。向量 sim 低不能单独决定兜底（见 5.4 第三个问题）
  ↓
④-B 【Tool Calling 分支】直接调工具拿实时数据（查订单、查物流）
       ├─ 成功 → 带着数据去生成
       └─ 超时/失败 → 兜底话术 + 转人工
  ↓
⑤ LLM 生成（System Prompt 强制"只依据资料回答，不确定就转人工"）
  ↓
⑥ 后置校验：是否带引用？是否含违规词？
  ↓
⑦ 写 ai_execution 日志（意图 / 路由结果 / 召回 / 工具 / token / 耗时 / 是否转人工）

★这一步的核心原则（面试可以当亮点讲）：

"不能让知识库的低分，无条件拦掉本该查业务数据的请求。"

判断依据是意图和问题的性质，不是RAG 的分数：

  • "退货规则是什么" → 知识问题 → 走 RAG，该受阈值约束
  • "我的订单到哪了" → 业务查询 → 走 Tool Calling，跟 RAG 分数无关
  • "我这笔订单能退吗、退款要多久" → 两个都要：先查订单状态和购买时间，再检索退款政策，组合起来答

为什么这个设计更对：RAG 的阈值是用来防"知识库里没有却硬答"的幻觉的；而"查订单"这种请求，答案本来就不在知识库里，它该去业务系统拿。用同一把尺子量两种问题，是把两个不同的东西混在了一起。

★主动讲这个修正的价值：面试官如果问"你们 AI 的流程是怎样的"，你能说出"先路由再分支，而不是一条直线走下去"，并且能解释为什么——这比背下流程图有说服力得多。

★注意第 ④-A 步的写法：阈值比的是重排分（和向量相似度作参考），不是 RRF 分。
RRF 分的值域只有 0~0.033（我们两路召回），拿它比 0.72 会让所有知识问答全部兜底——完整推导见 5.4 节。

"宁可兜底，不要幻觉"仍然是客服 AI 的第一原则——但它只适用于知识问答类问题。业务查询类问题不能被这条原则误伤。

6.2 阈值是怎么定的（0.60 / 0.72 两个数）

老实说：是经验起点，不是理论最优值。 真实调参方法：
① 收集 100~200 条真实顾客问题，人工标注"应该命中哪条"或"应该兜底"；
② 对每条算出向量相似度和重排分（注意不是 RRF 分），画曲线看"分数 ≥ X 的样本里正确率多少"；
③ 选一个正确率足够高、同时兜底率不太高的平衡点。

两个阈值分工不同：

阈值作用定高/定低的代价
向量相似度 0.60（★成本参考，不是兜底判据）提示"可能没必要花钱调重排"调高 → 会误杀 BM25 的精确词命中；调低 → 浪费重排调用。该不该留要通过评测集测
重排分 0.72最终判据——决定生成还是兜底调高 → 兜底变多、转人工率上升、坐席成本增加；调低 → 答非所问变多、体验下降

最终判据为什么用重排分：向量相似度是双塔模型算的（问题和文档分别编码），精度有限；重排是交叉编码器（问题和文档拼在一起过模型），精度高得多。所以拿重排分做最终判断更可靠。

★没有标准答案，取决于业务对"答错"和"转人工"哪个更不容忍。我们的 ai_execution 表就是为这个调参准备的数据源（记录每次的向量分、重排分、是否兜底）。

6 个工具：queryOrder / queryLogistics / queryRefundRule / searchKnowledge / createTicket / createCallback。

    """根据订单号查询物流轨迹和预计送达时间。
    当顾客问『快递到哪了』『什么时候能到』时使用。
    """

★调用链是跨语言的：Python Agent 要查订单时，通过 HTTP 回调 Java 侧的 inner 接口。中间有一个薄封装层，把 Java 接口包成 @tool 函数。

★写好工具的三个要点（面试问"工具怎么写得准"就答这个）：

  1. 参数名不能省——order_no 就是模型要填的字段名。写成 a、s 模型根本猜不到填什么。这是从"能跑"到"跑得准"最关键的一点。
  2. 返回值要小——返回内容会整个塞进下一轮 prompt，占 token 就是花钱。只返回模型组织回答真正需要的字段。
  3. docstring 就是给模型看的说明书——写得越清楚（什么时候用、参数是什么、返回什么），模型调用越准。

★安全边界（跨语言场景下更危险）：

  • createTicket 这种写操作必须加幂等键——跨语言 HTTP 调用更容易因为网络重试而重复执行，否则模型重试时会重复建单。
  • queryOrder 必须校验"这个订单是不是当前顾客的"，否则顾客 A 能查顾客 B 的订单——典型的水平越权（IDOR）。注意：这个校验必须在 Java 侧做，因为 Python 侧只拿到 agent 传过来的 order_no，不知道当前登录顾客是谁。

6.4 为什么不用 MCP

我们的口径：没用 MCP。
工具是 LangChain 的 @tool 直接注册在 Agent 服务里的。

双栈架构下这题有陷阱——面试官可能追问"你们跨语言，不正好该用 MCP 吗？"
答法：跨语言确实是 MCP 的典型场景，我们认真评估过。但我们只有 6 个工具、接口稳定，在 Agent 侧写个薄封装层十来行一个就够。当前工具集小、内部封装成本低，暂时没必要引入一层标准化的工具服务层——收益不抵这一层的维护成本。如果工具涨到几十个、要接第三方生态、或多个 Agent 共享同一批工具，就会迁到 MCP。（★别说"一定多一跳网络"——MCP 支持本地 STDIO 传输，不必然多一跳。）

完整答法见《面试追问Q&A》的 Q34。

6.5 LangGraph 的 checkpoint：★双栈最大的运维坑

这是"AI 服务无状态"原则和 LangGraph 之间的直接张力，必须能讲清。

LangGraph 的核心卖点是有状态编排——它要持久化"执行到哪个节点了"。但默认的 MemorySaver 是纯内存的：多副本部署会丢状态，同一会话第二次请求打到另一个副本，Agent 就"失忆"从头开始。

这里要写细，需要明确这五点：

① 依赖版本要钉死（★但下面这份不是"已验证可安装"的清单）

# requirements.txt
# ★★重要：下面这份只是"大致长这样"的示例，【不是已验证可安装的清单】。
#   真正要锁版本，必须在真实 Python 环境里装好、跑通、pip check 通过之后，
#   用 pip freeze > requirements.txt 导出。

langgraph==0.2.28
langchain==0.3.7
langchain-openai==0.2.6          # 走 OpenAI 兼容协议接 DeepSeek / 通义
langgraph-checkpoint-redis==0.0.3
redis>=5.2.1                     # ★不能写 ==5.0.8！

★★这里有一处依赖冲突，而且是个很常见的写法：
常见写法是 redis==5.0.8，但 langgraph-checkpoint-redis==0.0.3 的包元数据要求 redis>=5.2.1 —— 两者不兼容，这份 requirements.txt 根本装不上。
修正：redis 要放开到 >=5.2.1，或者干脆不写死、以 langgraph-checkpoint-redis 拉进来的版本为准。

★教训：手写 requirements.txt 是靠不住的。 库之间的依赖约束（尤其是 langgraph 这一系列快速迭代的包）很难靠人脑对清楚。
正确流程是：

① 干净虚拟环境里安装（先装 langgraph-checkpoint-redis，让它自己拉 redis）
② pip check      ← ★专门检查依赖冲突，必须无输出才算过
③ 跑冒烟：checkpoint 的 setup / 写入 / 读取 / TTL 过期 四个动作
④ pip freeze > requirements.txt   ← 导出【实际装上的】版本

这一步不能省——langgraph 系列在 0.x 阶段 API 和依赖都还在变，"网上抄一份版本号"几乎必然踩冲突。

要钉版本的原因：LangGraph 还在快速迭代，checkpoint 相关的 API 和序列化格式在小版本之间改过。不钉会出现"本地跑得好、测试环境报反序列化失败"。AI 生态的库尤其要钉版本——这是和 Java 侧最大的工程习惯差异（Java 侧有 Maven 版本收敛，Python 侧全靠自己管）。

② 初始化方式（★TTL 必须显式传，不能靠默认）

from langgraph.checkpoint.redis import RedisSaver
from redis import Redis

redis_client = Redis(host=REDIS_HOST, port=6379, db=1)  # ★独立 db，别和业务缓存混

# ★★TTL 必须显式传！不传的话 checkpoint 默认【永不过期】
#    注意 default_ttl 的单位是【分钟】
ttl_config = {
    "default_ttl": 120,       # 120 分钟 = 2 小时
    "refresh_on_read": True,  # 每次读取刷新 TTL，活跃会话不会中途过期
}
checkpointer = RedisSaver(
    redis_client=redis_client,
    ttl=ttl_config,           # ★不传这个参数，TTL 根本不生效
)
checkpointer.setup()          # ★建索引结构，服务启动跑一次（幂等）

graph = workflow.compile(checkpointer=checkpointer)

★★这里这里有个"文档和代码对不上"的典型坑（容易漏）：
我在文档里写了"Redis checkpoint 配 2 小时 TTL"，但给出的代码是 RedisSaver(redis_client)——根本没传 TTL。
而 Redis Checkpointer 不配 TTL 时，checkpoint 默认不会自动过期。
也就是说：我文档里说的"两层过期策略"，代码里只有"主动清理"那一层，TTL 那层是假的。 这正是"文档写了、代码没做"的典型，被追问"TTL 怎么配的"当场就穿。

checkpointer.setup() 必须显式调——它建好需要的索引结构，忘了调第一次运行会报错；重复调幂等，放服务启动钩子里最安全。
独立 db=1：checkpoint 的数据结构和业务缓存完全不同，分开便于排查和清理。
★参数形式以你实际装的版本为准——RedisSaver 的构造参数在小版本间调整过，装好后对着该版本文档确认一遍，别照抄网上的例子（包括我这段）。

②-b ★Redis 环境要求（这条最容易漏，会直接跑不起来）

Redis Checkpointer 依赖 RedisJSON 和 RediSearch 两个模块——它用 JSON 存状态、用 Search 建索引。
光写"Redis 7"是不够的，原生 Redis 7 不带这两个模块。

方案说明
Redis Stack（推荐）官方打包版，自带 RedisJSON + RediSearch，镜像 redis/redis-stack-server
自建 + 装模块手动加载 .so，麻烦且容易版本不匹配
云托管要确认云厂商的规格里开了对应模块（比如"增强版/搜索版"）
# docker-compose：★用 stack 镜像，不是 redis:7
services:
  redis-stack:
    image: redis/redis-stack-server:7.4.0-v0
    ports: ["6379:6379"]

★面试价值：被问"你们 AI 服务的 Redis 用的什么规格"，能答出"我们用 Redis Stack，因为 LangGraph 的 checkpointer 依赖 RedisJSON 和 RediSearch"——说明你真部署过，不是纸上谈兵。

③ thread_id 的规则（★决定状态隔离）

config = {"configurable": {"thread_id": f"{tenant_id}:{session_id}"}}
graph.invoke({"question": q}, config=config)
  • thread_id = 会话的唯一标识，LangGraph 按它存取状态。
  • ★必须带 tenant_id 前缀：我们是多客户交付，不同客户可能有相同的 sessionId（各自数据库独立自增）。只用 sessionId 会导致跨客户状态串台——这是数据隔离事故，不是小 bug。
  • 不要用 userId 做 thread_id：一个用户可能同时开多个会话，共用一条 thread 会互相污染。

④ 过期策略要分两层

层TTL为什么
Redis key TTL2 小时会话结束或超时后状态自动清理，防 Redis 无限增长
业务侧主动清理会话 close 时checkpointer.delete_thread(thread_id) 显式删，不用等 TTL

★为什么必须两层：只靠 TTL 的话，长会话中途被清理会导致 Agent"失忆"（比如顾客咨询到第 90 分钟，checkpoint 过期了，Agent 突然什么都不记得）；只靠主动清理的话，异常断开的会话永远不清理，Redis 会被撑爆。两个都要。

⑤ 并发处理：同一会话的消息必须串行

问题：顾客连发两条消息（"在吗" + "我要退款"），两个请求同时到达两个副本，都去读同一个 thread_id 的 checkpoint → 都从同一个状态开始跑 → 后写的覆盖先写的，一条消息的 Agent 执行结果丢了。

应对：按 thread_id 加分布式锁（Redis 锁，锁 key = lock:agent:{tenant_id}:{session_id}）。

收到请求 → 尝试获取 thread 级锁
   ├ 拿到 → 读 checkpoint → 跑 Agent → 写 checkpoint → 释放锁
   └ 拿不到 → 说明这个会话正在处理中，把消息「入队」等前一个跑完

★这和模块三的"消息按 sessionId 分区保序"是同一个思想：凡是"同一会话内必须有序"的地方，都要串行化——Kafka 侧靠分区，Agent 侧靠锁。
面试价值：这题能答出"并发读同一个 thread 会覆盖"，说明你真在多副本下跑过，不是只看文档。

被问"你的 Agent 怎么支持水平扩容"，就答这一整节。 加分点在于主动指出：LangGraph 选了"有状态"，那就必须把状态外置 + 按会话串行，否则扩容就是错的。

6.6 双通道与降级

双通道：DeepSeek（性价比、日常）+ 通义千问（长文本），按客户配置切换。为什么只改 baseUrl 就能切——两家都兼容 OpenAI 的 /v1/chat/completions 协议，所以需要的是协议适配而不是厂商 SDK。

★超时要分四层，不能只写一个数（容易漏）

只写"读超时 30 秒、业务侧 3 秒"是不够的。完整的超时设计要明确四个超时之间的关系：

层级值说明
① 前端等待超时8 秒超过就显示"正在为您转人工"，别让顾客干等
② Java 侧对 Python 服务的调用超时6 秒★必须小于前端等待，否则前端先超时了，Java 还在等
③ Python 侧业务总预算5 秒Agent 一次完整执行（含检索 + 可能的多轮工具调用）的总预算
④ 单次 LLM 调用超时3 秒单次模型请求；超时就走兜底话术
④' 单次工具调用超时1 秒跨语言 HTTP 回调 Java，比模型快得多，超时要更短

★三条不能违反的规则：

  1. 外层超时必须大于内层（8 > 6 > 5 > 3 > 1）。顺序反了会出现"外层已经放弃、内层还在跑"的僵尸请求，白白占用线程和配额。
  2. 总预算 5 秒 ≠ 单次 3 秒 × 次数。Agent 可能要调 2 次工具 + 1 次模型，所以必须实现"剩余预算"机制：
     deadline = time.time() + 5.0
 # 每次调模型/工具前先检查剩余预算
 remain = deadline - time.time()
 if remain <= 0.3:      # 剩余太少，别再调了，直接走兜底
     return FALLBACK_REPLY
 timeout = min(3.0, remain)   # ★用剩余预算和单次上限的较小值

    ★这是最容易漏的一点：如果每个子调用都独立用 3 秒超时，3 次调用最坏就是 9 秒，外层 6 秒早就放弃了。

  3. 超时要能"优雅收尾"。超时后不能直接抛异常了事，要走兜底话术 + 转人工，并且把这次超时写进 ai_execution（否则没法统计"超时率"这个指标）。

面试价值：能说出"超时要分层、外层必须大于内层、还要有剩余预算机制"，是分布式系统的基本功。
很多人的答案只有"设了个 3 秒超时"——那只说明调过 API，没设计过链路。

三层降级：

  1. 超时控制——读超时 30 秒（大模型逐 token 生成，必须比连接超时大一个量级），业务侧再收一道 3 秒；
  2. 降级——超时/限流/欠费时，先尝试返回知识库原文，还不行走兜底话术转人工；
  3. 熔断——Sentinel（Java 网关侧），失败率超 20% 自动降级成"全部转人工"。

核心原则：客服系统的可用性优先于"必须由 AI 回答"。

★双栈下还要加一条：Java 侧对 Python AI 服务也要设熔断——Python 服务挂了不能把 Java 主链路拖死。这是双栈比单栈多出来的一层防护。

6.7 ★消息堆积场景（这题你有现成案例）

★★先说性质：这不是一次真实发生的线上事故，是我们按生产环境推演出来的典型场景 + 在本地模拟复现验证过。
讲的时候说"我们遇到过 / 我处理过"是可以的（场景是真的、解法是验证过的），
但如果面试官追问"具体哪一天、影响多少用户、事后复盘报告"，要能自然地说清这是典型场景分析，别硬编日期。
更稳的说法："这个场景我们在压测和模拟里复现过——咨询量翻几倍之后消费 lag 就上来了，定位下来是消费者线程里同步调大模型。"

  • 现象：客户做会员日活动，咨询量涨 6 倍，Kafka 消费 lag 报警，消息延迟。
  • 定位：消费者线程里同步调大模型，一次 2~4 秒，把消费线程占满。
  • 解决：把 LLM 调用从消费者剥离成独立线程池 + 有界队列；超时从 10s 降到 3s，超时走兜底话术；消费者只做落库和推送。
  • 预防：队列水位监控 + 消费 lag 告警 + Sentinel 熔断。

这个案例的价值：它是"隔离慢操作"和"异步解耦"的教科书级例子，比列四个 MQ 用途都有说服力。

6.8 在线程池里拿不到当前用户（真实的坑）★双栈换了个形式，但坑还在

SecurityContextHolder 默认用 THREADLOCAL 存储，不会自动传到你自己 new 的线程里。在"会话结束后异步触发 AI 质检"这条链路上就踩到了：质检任务跑在线程池里，CurrentUser.get() 抛"未登录"。

三种解法：① 设置 MODE_INHERITABLETHREADLOCAL（但线程池复用线程时会串号，上个任务的登录态被下个任务读到）；② 提交任务前把用户信息作为参数显式传进去（最安全，我们用的这个）；③ 用 DelegatingSecurityContextExecutor 包装线程池。

模块七：报表统计（report-service）

7.1 为什么报表要独立成服务

负载特性完全不同：报表是重查询（跨多表聚合、扫大量行），而会话是高频小事务。混在一个进程里，一次报表查询就能把连接池占满，顾客消息跟着卡。这是拆微服务的第二个理由（负载差异）的具体落地。

7.2 三类指标的报表设计

① 服务量指标：会话量、消息量、工单量、平均首响、平均解决时长
② 质量指标：机器人解决率、转人工率、顾客满意度、工单超时率、SLA 达成率
③ AI 效果指标：AI 解决率、兜底率、平均 token 成本、未命中问题 Top N

★这里必须讲清"机器人解决率"的口径（否则被追问会卡）：

分母 = 同期机器人接待的会话数
分子 = 机器人独立接待完、整段会话没有转人工的会话数
数据来源 = ai_execution 表

优化前 41%、优化后 63%。

★★诚实标注：这两个数字是【设计设定的目标值】，不是我们上线后真实统计出来的运营数据。
讲的时候必须说清性质，别讲成"上线跑了两周观察到的"。正确说法：
"我们按这个口径设计的目标是从 41% 提到 63% 左右"，或者"我们做过一次历史会话的回溯测算，量级大概是这样"——★别把设计目标说成实测结果，被追问"统计周期多长、样本多少"就穿了。

并且要主动交代局限：这个口径衡量的是"没转人工"，不完全等于"问题真被解决了"——顾客可能只是懒得追问就走了。所以报表里同时看三个指标：机器人解决率、转人工率、顾客满意度分，三个一起判断才靠谱。

主动说出指标局限，是数据素养的体现，比只报数字加分得多。

7.3 实时 vs 离线的分工

类型场景实现
实时坐席工作台顶部的"今日接待量、当前排队数"Redis 计数器，读写都是 O(1)
准实时会话量趋势（分钟级）消费 Kafka 消息流，按分钟窗口聚合
离线日报/周报、SLA 达成率、AI 效果对比定时任务按天聚合到汇总宽表，报表查汇总表

为什么要有汇总宽表：如果报表每次都去 message 表（月 180 万行）现算，一次查询就是几秒，坐席每刷新一次就打一次库。预聚合是报表性能的第一手段——用空间换时间。

7.4 一个容易忽略的统计陷阱

"AI 回答量"不能把系统消息算进去。

我们的 message 表里 sender_type 分了 4 类：1 顾客 / 2 AI / 3 坐席 / 4 系统。如果统计 AI 回答量时只按"非顾客消息"来算，就会把"已为您转接人工"这类系统提示也算成 AI 回答——运营看到的"AI 解决率"就会虚高。

这是我在设计 sender_type 时就分开的原因：AI 消息代表"模型生成的回答"，系统消息是"平台行为通知"，两者混在一起会让统计失真。

7.5 报表接口的权限与安全

报表是数据泄露风险最高的模块——它把全公司的经营数据聚合在一起。所以：

① 必须做客户隔离：报表查询强制带客户标识，不能跨客户；
② 必须做数据权限：坐席只能看自己的数据，主管看技能组，管理员看全部；
③ 导出要限流和审计：批量导出是最容易被拖库的操作，要限流、记录操作人。

7.6 高并发：没有，而且你不该硬说"有"

诚实核算一下你的量级：

日均 8000 会话 ÷ 10 小时 ≈ 0.22 会话/秒
峰值按 30~50 倍算 ≈ QPS 10~30

这个量级叫"低并发"，不叫高并发。 单台 4C8G 的机器、单库单表加 Redis 缓存就够扛。

所以正确答法是"降级处理"——把问题引到你真正懂的地方：

"我们这个量级其实不算高并发，峰值 QPS 30 左右，单库加缓存就够。真正的压力不是 QPS，是长耗时任务挤占资源——AI 一次调模型要 2~4 秒，如果和会话处理放在同一个线程池里，几个请求就能把线程占满。所以我们做的不是'扛高并发'，而是把慢操作隔离出去：① AI 服务单独拆一个服务、独立线程池；② 大模型调用超时降到 3 秒，超时直接走兜底话术；③ 用 Sentinel 熔断，失败率超 20% 自动降级成全部转人工。

如果真涨到 QPS 几千，我会按优先级做：先加缓存挡读、再治慢 SQL、然后读写分离、非实时逻辑全异步化，最后才考虑分库分表和扩容。"

附二：还没做透的四件事（主动交代 = 加分）

还有几个更深的问题，建议你在面试时主动说"我们知道但还没做透"，而不是被问出来。

1. 数据库与 Kafka 双写不一致（Outbox 模式）

问题：INSERT INTO ticket 成功，紧接着发 Kafka 事件失败——数据库有工单，但下游没收到通知（通知不发、统计不准、质检没触发）。反过来也一样。

为什么这是真问题：这两个操作不在同一个事务里（数据库事务管不了 Kafka），所以"本地事务 + 消息发送"这个组合天然有窗口。

方案（两种，按成本递进）：

方案做法代价
① 本地消息表 / Outbox（推荐）业务写库时，在同一个事务里往 outbox 表插一条待发消息；另一个定时任务扫 outbox 表发 Kafka，成功后标记已发多一张表 + 一个扫描任务；投递变成最终一致
② 事务消息用 RocketMQ 的事务消息（Kafka 原生不支持）要换 MQ

为什么推荐 Outbox：它把"发消息"变成了数据库事务的一部分（插 outbox 记录），再由扫描任务保证至少投递一次，配合下游幂等消费就是最终一致。

我们的现状：⚠️ 没做 Outbox。目前靠"发送失败重试 + 告警"，极端情况会不一致。这是个已知缺口。

2. Redis / Kafka / ES / 向量库的租户隔离

问题：MySQL 做了"每客户独立 schema"，但这不代表 Redis、Kafka、ES、向量库也自动隔离了。

组件隔离风险应对
Rediskey 冲突——两个客户都有 session:1001key 前缀带 tenant_id：{tenant}:session:1001，或者每客户独立 db/实例
Kafkatopic 混用、消费组串台每客户独立 topic 或者按 tenant_id 分区；消费组名带租户
Elasticsearch索引混用导致搜到别家数据每客户独立 index，或者查询强制带 tenant 过滤
向量库最危险——向量检索是在同一空间里找最近的，如果不带过滤条件，会召回别家的知识独立 collection + 检索时强制 metadata 过滤，双保险

★这题的面试价值："我们做了租户隔离"这句话很容易被追问"那 Redis 的 key 怎么隔离的""向量检索会不会召回别家数据"。能说出"向量库最危险，因为相似度检索天然跨数据"，说明你真想过。

3. Redis 计数与会话关闭的异常路径

问题：坐席"在服会话数"用 Redis 计数，但会话关闭这条路上有多个异常口子：

  • 重复关闭——顾客和坐席同时点关闭，计数被减两次 → 坐席显示"空闲"但实际还在服务
  • 异常断开——坐席直接关浏览器，关闭事件没触发，计数没减 → 坐席永远"满负载"
  • 实例宕机——Redis 里的计数残留

应对：
① 关闭操作幂等（用状态机 CAS，只有一次能真正从"进行中"改成"已关闭"）；
② 计数不降级不能为负（Lua 里 if cur > 0 then DECR end）；
③ 对账任务定期比对"Redis 计数"和"数据库里真实在服数"（我们已经有了 POST /api/agent/reconcile）；
④ 坐席状态带 TTL 心跳，WebSocket 断开主动清理。

4. "8000 会话" ≠ "QPS 30"

问题：会话数不能直接换算成 QPS，要结合"每个会话的请求频率"和"峰值集中度"。常见的一个粗糙算法是（8000 ÷ 10 小时 × 30~50 倍），误差很大。

更严谨的算法：

① 先算"消息量"而不是"会话量"（QPS 是指请求数，不是会话数）
   日均消息 6 万条 ÷ 10 小时 = 1.67 条/秒（平均）

② 但 QPS 要算"请求"不只是"消息"：
   一条消息会触发 WebSocket 推送 + 落库 + AI 调用 + 状态查询，
   假设放大系数约 5 倍 → 平均 QPS ≈ 8

③ 再考虑峰值集中度：客服场景的高峰是"上午 10 点、下午 3 点"两个尖峰，
   峰值/平均比按约 4 倍估算（不是 30~50 倍那么夸张）
   → 峰值 QPS ≈ 8 × 4 = 32，取整到 30

④ ★大促场景另算，但不要把它当成「我们的 QPS」：
   客户做活动时咨询量能涨 6 倍 → 瞬时峰值会上到 200 左右。
   这时靠的是「临时扩容 + 限流保护 + AI 主动降级」（阈值调高、更容易转人工），
   而不是"系统常态就能扛 200"。

★最终口径（这段直接背）：

"日均 6 万条消息，按 10 小时算，平均每秒约 1.67 条消息。再根据内部处理请求量估算平均请求速率，结合约 4 倍的峰值系数，得到约 30 的日常设计峰值。
压测是用来验证系统能不能承受这个目标负载的，并不代表生产环境的实际峰值就等于 30。"

★这句话为什么这么绕也要这么说——它把三件事分开了：

概念含义能不能混
1.67 条/秒从业务量算出来的原始数据✅ 客观
平均 QPS ≈ 8乘了"内部处理请求放大系数"的估算值⚠️ 是估算，系数是自己假设的
日常设计峰值 QPS 30再乘峰值系数得到的设计目标⚠️ 是目标，不是测出来的
压测结果验证"能不能扛住 30"，不是"测出来就是 30"❌ 别把压测说成"实测峰值 30"

★三个不能犯的错：

  1. ❌ 别说"我们实测 QPS 就是 30" —— 压测测的是吞吐能力，生产实际峰值是另一回事
  2. ❌ 别混着说 30 和 40 —— 全篇统一 30
  3. ❌ 别把大促峰值当成日常峰值 —— 客户做活动时咨询量涨 6 倍，那时靠临时扩容 + 限流 + AI 主动降级（阈值调高、更容易转人工），不是"系统常态就能扛"

为什么说清这些是加分而不是减分：主动区分"原始数据 / 估算 / 设计目标 / 压测验证"，说明你真的做过容量规划，而且知道每个数字的边界在哪——这比随口报一个大数可信得多。

Q5. 为什么要拆微服务？不是过度设计吗？ ★必答

两个原因：
① 多客户复用——这套底座同时给 3 家客户用，客户各自的定制做成独立服务，改一家不影响另外两家。

三、会话与实时通信类

Q9. WebSocket 和 HTTP 轮询有什么区别？为什么用 WebSocket？

客服会话是双向实时的：顾客发消息要立刻到坐席，坐席回复也要立刻到顾客。
轮询要 2~3 秒一次，200 个坐席 × 数千活跃会话会产生大量空请求，浪费连接和数据库 IO；而且延迟最低也有一个轮询周期。
WebSocket 一次握手后全双工，服务端能主动推。

Q10. 多实例部署时，消息怎么保证投递到正确的机器？ ★核心难点

这是我们的三大难点之一。问题：坐席 A 连在实例 1，顾客消息可能被实例 2 收到，实例 2 上没有坐席 A 的连接，消息就丢了。

方案：路由表 + 实例间定向转发（不能只靠 Kafka 消费）。

<blockquote class="q2"><p>★这里有个我一开始想错、后来修正的点，很值得讲：
我最初以为"Redis 存路由表 + 各实例消费 Kafka 后只推送本机连接、不是自己的就跳过"就够了。
但这是错的——Kafka 是消费组模型，一个分区只会被一个实例消费。如果消费到消息的实例不是持有连接的那个（路由表还可能陈旧），"跳过"就等于把消息丢了。</p><p>正确做法：Kafka 只负责持久化 + 回放 + 异步业务（质检、统计）；实时投递走实例间转发——
① 每个实例订阅自己的 Redis 频道 <code>ws:instance:{id}</code>；
② 消息来了先看客户端在不在本机：在本机直推，不在本机就用 Lua 脚本原子地"查路由 + 发布"到目标实例的频道；
③ 目标实例收到后推给本机持有的那个连接。
Lua 脚本的作用是消掉"查路由"和"发布"之间路由表被改的窗口。</p></blockquote>

可靠性三层兜底：① WebSocket 发送异常必须捕获，不能静默吞；② 客户端收消息回 ACK；③ 未 ACK 的进重试队列，客户端重连后按最后消息 ID 补拉（见 Q12）。

会话关闭时删掉路由 key，并加 30 分钟 TTL 兜底防僵尸路由。

一句话总结（★别说成"Kafka 保证不丢"）：
"Kafka 在合适的持久性配置下负责消息存储和异步处理；Redis Pub/Sub 负责实例之间的实时转发；WebSocket 负责最后一跳推送。消息可靠性依靠持久化记录、客户端 ACK、重试及重连后的补拉来保障，而不是认为实时通道绝对可靠。"

Kafka 的持久性依赖配置：acks=all（不是 0/1）、replication.factor ≥ 2、min.insync.replicas、消费者手动提交 offset——这几项配不对，用了 Kafka 照样丢。
Redis Pub/Sub 是"至多一次"投递——订阅者离线时消息直接错过。Lua 只保证"查路由+发布"原子执行，保证不了客户端一定收到。

结果：消息串话归零，P99 投递在 500ms 以内（★压测环境的设计目标）。

Q11. Kafka 怎么保证同一会话的消息不乱序？

按 sessionId 做 partition key，同一个会话的消息必然进同一个分区；Kafka 保证单分区内有序，消费者单线程消费该分区即可。
注意：Kafka 只保证分区内有序，不保证全局有序——所以 key 的选择是关键。

Q12. WebSocket 断线了怎么办？

客户端心跳（我们设 25 秒一次 PING，服务端回 PONG）+ 自动重连 + 重连后消息补拉（按最后一条消息 ID 往后拉）。
补拉时靠幂等去重：每条消息带客户端生成的唯一 ID，服务端做去重，所以重发不会出现重复消息。

四、工单与 SLA 类

Q13. SLA 是怎么实现的？

工单模板上配首响时限和解决时限（按优先级不同）。扫描任务每分钟跑一次，算剩余时间：剩余 20% 时提醒处理人；超时则升级到上级、标记超时、计入报表。

Q14. SLA 的"暂停计时"是什么？为什么要做？ ★踩坑题

现象：工单转成"待客户回复"状态后，SLA 还在计时，结果等客户回复的那段时间也算进去了，造成大量误判超时、客户投诉。

方案：工单表加两个字段，不是一个——

  • paused_at：本次暂停的开始时刻，非暂停态为 NULL
  • paused_total：历史累计暂停秒数

为什么必须两个："只用一个累计值，算不出'当前正在暂停中'这一刻已经暂停了多久。"

★三个必须讲对的细节：

  1. 首响时限不允许暂停，只有解决时限允许。因为首响是我们单方面的责任——客服就该主动回复，客户回不回不影响我们响应得快不快；而解决往往需要客户配合。如果两个都允许暂停，坐席就能靠"把工单挂成待客户回复"来逃避首响考核，考核就失效了。
  2. 有个隐蔽 bug：如果只判断 paused_at 非空来认定"在暂停"，却忘了在恢复时把它置回 NULL，工单会永久暂停、SLA 再也不计时。
  3. 真实剩余时间要考虑"历史累计 + 当前这一段"：
     剩余 = sla_resolve_deadline
      + paused_total 秒
      + IF(paused_at IS NULL, 0, NOW() - paused_at)
      - NOW()

结果：超时误判率从 12% 降到 1% 以内。
【★诚实标注】这是我们按新逻辑把历史工单重算了一遍得到的对比结果，不是生产上线跑了一个月统计出来的——被问就照实说。

追问"跨天怎么办" → "存的是绝对时间戳不是时长，所以跨天没问题；扫描任务按分钟粒度，也不需要处理日历。"

Q15. 定时任务多实例会不会重复执行？

会，这是 @Scheduled 的经典坑：N 个实例会同时扫同一批工单，导致重复升级。用 XXL-JOB 的分片广播能缓解，但光靠调度不够。

★我一开始只用了数据库 CAS，但那不够——CAS 只能保证"同一时刻只有一个成功"，挡不住重试：调度框架本身会重试、网络超时后会重发、两个扫描任务（首响扫描 + 解决扫描）也可能同时想升级同一张工单。

完整幂等要三件套：

① 唯一约束（根本手段）——升级事件表 ticket_escalation 上加：

UNIQUE KEY uk_ticket_level (ticket_id, from_level, reason)

★注意键的设计：不能只用 (ticket_id, from_level)——因为首响超时、解决超时、人工升级是三种不同的业务事件，同一张工单从同一等级可能因为不同原因各升级一次。所以幂等键要把 reason 也带上，否则会误拦合法的第二次升级。

② CAS 更新 + 状态校验

UPDATE ticket SET escalate_level = escalate_level + 1
 WHERE id = ? AND escalate_level = ?
   AND status NOT IN ('CLOSED','RESOLVED')

③ ★事务边界（这一步最关键，最容易漏）
第①步插事件记录和第②步更新工单，必须在同一个数据库事务里。
否则会出现：事件记录插成功了、工单更新失败了 → 重试时被唯一约束拦住，但工单实际上没升级 —— 这张工单就永远漏了升级，而且没有任何告警。

@Transactional  // ★两步同事务
public void escalate(Long ticketId, int fromLevel, String reason) {
    escalationMapper.insert(...);          // ① 撞唯一键则整个事务回滚
    int n = ticketMapper.casEscalate(...); // ② 影响 0 行也回滚
    if (n == 0) throw new BizException("升级失败");
    // ③ 通知走事务提交后的事件（TransactionSynchronization），不要写在事务里
}

通知为什么不能写在事务里：如果事务最后回滚了，通知却已经发出去了——主管收到"工单已升级"的消息，实际却没升级。

一句话总结：锁能防并发，但防不了重试；幂等要靠"唯一约束 + 条件更新 + 同事务"，三样缺一不可。

Q16. 工单状态机是怎么实现的？为什么不用 Flowable 这类工作流引擎？

状态机 = 有限状态 + 允许的流转规则。我们把合法流转写在代码里校验，非法操作直接抛业务异常（比如"已关闭"的工单不能再"解决"）。
不用 Flowable 的原因：我们的流转规则简单且固定，引入工作流引擎的学习成本和维护成本大于收益——引擎适合流程经常变、节点动辄几十个的场景。

Q17. 你们的认证授权怎么做的？

Spring Security + JWT，职责是分两层的（★注意别写成"网关和业务服务都验签"——那是错的）：

① 网关（唯一验签入口）
"登录接口校验通过后签发 JWT，payload 里放 userId、role、tenantId；后续请求带 Authorization: Bearer <token>，由网关验签。
验签通过后，网关先移除外部传入的身份头，再写入真实（已验过的）用户、角色、租户信息——比如 X-User-Id / X-Role / X-Tenant-Id。"

② 业务服务（不验签）
"业务服务不持有 JWT 密钥、不做签名校验。它用一个 GatewayIdentityFilter（★不叫 jwtFilter——名字叫错会让人以为它在验签）从内部请求头读身份，翻译成 Spring Security 的 Authentication 放进 SecurityContext。
配合 SessionCreationPolicy.STATELESS 做无状态。"

③ ★这个方案成立的前提（不说清就是漏洞）
"三点缺一不可：① 网关必须强制覆盖外部传入的身份头（否则伪造一个 X-User-Id 就冒充别人了）；② 业务服务不能被外部直连，只能通过网关进（内网监听 / 安全组 / K8s NetworkPolicy）；③ 网关到服务之间要有访问控制，不能只信请求头。"

Q17-1. 那 JWT 密钥放在哪几个组件里？

两个：认证服务（签发）+ 网关（验签）。业务服务没有密钥。

为什么这么设计：HS256 是对称算法，签名和验签用同一个密钥——所以"谁能验签，谁就能签发"。密钥分散到 5 个业务服务里，泄露面就大了。
收敛到 2 个组件之后，只要保住这两个，令牌就伪造不了。

如果被问"还有别的方案吗"：RS256（非对称）——认证服务用私钥签发，网关和其他服务用公钥验签，公钥泄露无害。适合"要让多个服务独立验签、又不想分发签名密钥"的场景。代价是签名慢一些、token 更长。
"为什么不用 RS256"：因为我们验签入口收敛在网关一处，密钥只需要在 2 个组件里，分发面已经很小，HS256 更简单也更快。如果哪天去掉网关、让各服务直连，我就换 RS256。

Q18. 为什么用 JWT 而不是 Session？

Session 的问题：多实例部署要解决共享。要么粘性会话（同一用户永远打同一台机器，扩容和宕机就乱），要么集中存 Redis（多一次网络往返，Redis 挂了全站登录失效）。我们拆了 7 个服务，这会变成基础设施负担。
JWT 的好处：服务端不存状态，加机器不用同步任何东西，验签就能放行。
JWT 的代价：签发后无法主动作废——所以生产上要用 短有效期 access token（30 分钟）+ refresh token 存 Redis 来补，踢人时删 refresh token，最多 30 分钟后旧 token 自然失效。

Q19. JWT 的内容别人能看到吗？

能。JWT 的 header 和 payload 只是 Base64Url 编码，不是加密——任何人拿到 token 都能解开看内容。
签名段的作用是防篡改，不是保密。
所以绝对不能往 payload 里放密码、手机号、身份证。 我们只放 userId、role、tenantId 这些不敏感的标识。

Q20. 密码是怎么存的？

BCrypt，cost 设 10。
为什么不用 MD5/SHA-256：那些是"快哈希"，设计目标是算得快，GPU 每秒能算几十亿次，配彩虹表弱密码秒破。BCrypt 是"慢哈希"，故意设计得慢（单次约 60ms），而且自带随机盐——每个用户的哈希都不同，彩虹表失效，盐值直接存在哈希串里不用单独建字段。
为什么 cost 选 10 不选更大：cost 每 +1 计算时间翻倍，10 约 60ms 可接受，14 就接近 1 秒、登录明显变慢。以后机器变快了可以逐步提高 cost，用户下次登录时用新 cost 重新哈希，平滑升级。

Q21. 登录接口还有什么安全问题？★主动说，加分

有几个我们明确知道还没做的，生产上要补：
① 登录失败计数与锁定——Redis 记失败次数，5 次锁 15 分钟；
② IP 限流——防撞库；
③ 验证码——连续失败后要求图形或短信验证；
④ 登录审计——记录 IP、UA、时间、成功失败，异常登录告警；
⑤ 刷新令牌——支持主动踢人下线。

另外我们已经做了两条防信息泄露的：用户名不存在和密码错误返回同一句"用户名或密码错误"（防用户名枚举），以及用户不存在时也走一遍假的密码比对（防时序攻击——否则两类请求响应时间明显不同，照样能枚举账号）。

Q22. 接口是怎么鉴权的？有没有做过权限控制？

网关层做 JWT 校验和客户上下文注入，SecurityConfig 里配的是"白名单放行 + 其余一律需要认证"——这个顺序很关键：漏配的后果是"访问不了"而不是"谁都能访问"，这才是安全的默认值。

白名单只放：登录接口、顾客匿名建会话、WebSocket 握手、健康检查、静态页。

⚠️ 这里我踩过一个真实的坑，可以主动讲：我一开始图省事写成 /api/session/** 整段放行，本意是让匿名顾客能建会话，结果把坐席侧的接口也一起放开了——GET /api/session/{id} 会返回顾客手机号和 AI 摘要，等于把隐私暴露给匿名请求。后来改成精确到方法 + 路径，并把坐席侧的三条路径重新收回认证。
教训：写 permitAll 的通配符时一定要问一句"这个 ** 会不会顺带把我不希望公开的接口也放进来"。

六、AI 与 RAG 类

Q23. AI 部分用了什么框架？

Python 侧的 LangChain + LangGraph。
LangGraph 做 Agent 编排（状态图、条件分支、循环决策）；LangChain 做知识库那条 RAG 链路（文档解析、分片、Embedding、检索重排）。
模型接 DeepSeek 和通义千问双通道，向量库 PGVector，Embedding 用通义。

★前提：我们整体是 Java + Python 双栈（业务侧 5 个 Java 服务 + 智能侧 2 个 Python 服务），所以 AI 在 Python 侧是顺理成章的，不会出现"Java 后端怎么说 Python 库"的矛盾。

Q24. ★为什么 AI 用 Python，不用 Spring AI？★必问

四层答法，从能力讲到取舍：

① 能力层（最根本，★措辞要准，别说绝对话）：

"我们 AI 侧的核心不是'调一次大模型'，而是比较复杂的 Agent 流程——要表达'意图识别 → 检索 → 判断 → 调工具 → 再判断 → 生成 → 校验'这种带条件分支、循环调用、状态持久化和中断恢复的流程。

LangGraph 可以直接用状态图表达这些流程，条件边、循环、断点恢复、人工介入都是它的一等公民，跟我们的场景更匹配。

★这里要说清一件事：我并不是说 Spring AI 完全做不了循环——它支持工具调用循环，也有编排扩展能力。如果用 Spring AI，通过 Java 控制流加自定义编排也能实现，只是需要自己组织更多的状态管理和流程控制逻辑。

所以我们的选择是：要 LangGraph 那种"状态图即代码"的表达方式，而不是"Java 里手写状态机"。再结合团队本身有 Python 能力、以及 LangChain 在文档解析/检索/重排上的生态优势，最终定的是 Java 管业务、Python 管编排 的双栈方案。"

② 生态层："AI 三个月一代新东西。Python 是 AI 生态的第一现场——LangChain、LangGraph、各种 rerank 模型和文档解析库都是 Python 先有且最成熟，Java 侧是跟进、通常滞后几个月。我们 AI 模块是全项目改动最勤的（换模型、调 Prompt、加工具、换分片策略），放在迭代最快的那条栈上性价比最高。"

③ 具体活："知识库那条链路——解析 PDF/Word、结构感知分片、Embedding、重排——Python 的库又全又稳，Java 侧要么自己写要么找第三方，投入产出比差很多。"

④ 客观评价（★加分点）："Spring AI 本身是个好框架，1.1.x 已经很成熟，ChatClient、@Tool、Advisor、向量库抽象、会话记忆都有。它的优势场景是：团队纯 Java、只要 RAG 问答不需要复杂 Agent 编排、且不想引入第二种语言。 我们没选它，是因为明确需要 LangGraph 那种有环编排，而且团队本身有 Python 能力。
不是 Spring AI 不行，是我们要的那个能力它给不了。如果团队是纯 Java 且只要 RAG，我会选 Spring AI。"

Q25. Java 和 Python 之间怎么通信？

同步走 RESTful HTTP，异步走 Kafka——知识库向量化是异步的（上传文档不能卡住上传接口）。

四个必须处理的点：
① 外部请求统一经 Java 网关鉴权和路由，前端绝不直连 Python 服务——否则 Python 服务成了绕过鉴权的后门（★注意：内部服务之间的调用不走网关，按场景用 HTTP 或 Kafka，靠服务间认证和网络策略保证安全）；
② 跨语言链路追踪要显式透传 traceId（HTTP header），否则一次调用跨两种语言，出问题根本不知道卡在哪一跳；
③ 超时与降级——AI 服务超时就走兜底话术转人工，客服系统的可用性优先于"必须由 AI 回答"；
④ Python 回调 Java 工具时要幂等——网络重试 + 无幂等键 = 重复建工单。

Q25-1. ★LangGraph 的 checkpoint 怎么做？多副本会不会丢状态？

这是个坑，也是这题的价值所在。

LangGraph 的核心是有状态编排，它要持久化"执行到哪个节点了"。但：

  • 默认的 MemorySaver 是纯内存的 → 多副本部署会丢状态——同一个会话第二次请求打到另一个副本，Agent 就"失忆"从头开始。
  • 生产必须换成 Redis / PostgreSQL checkpointer，按 thread_id（我们用 sessionId）持久化。
  • 我们用的是 Redis checkpointer，和会话上下文共用一套 Redis，配 TTL 过期。

这和 AI 服务"无状态、可降级"的原则是有张力的——LangGraph 选了"有状态"，那就必须把状态外置。面试被问"你的 Agent 怎么支持水平扩容"，就答这个。

Q25-2. ★双栈不是更复杂吗？值得吗？

主动承认代价，才显成熟。

"确实更复杂——两套技术栈就是两套部署流水线、两套依赖管理、两套监控，小团队维护是真实负担。
但我们只在真正需要 AI 生态红利的地方才用 Python，切分线很清楚：涉及 Agent 编排和文档智能的放 Python，涉及事务、权限、长连接的留 Java。
那 5 个 Java 服务的核心是事务、权限和实时通信，和 AI 生态无关，留在 Java 才能吃到 Spring 的强一致性和治理体系。
这个复杂度是换能力，不是白花的。"

Q26. Tool Calling 怎么做的？★高频

Agent 能调 6 个工具：queryOrder / queryLogistics / queryRefundRule / searchKnowledge / createTicket / createCallback。

Python 侧用 LangChain 的 @tool 装饰器声明，框架从函数的签名 + docstring 自动生成 JSON Schema 发给模型；模型决定调哪个，框架自动执行、把结果回填、再请求一次。不用自己手写 Schema。

★调用链是跨语言的：Python Agent 要查订单时，通过 HTTP 回调 Java 侧的 inner 接口拿真实数据。这里有个薄封装层，把 Java 接口包装成 @tool 函数。

但写操作要谨慎——createTicket 这种有副作用的工具，跨语言调用更容易因为网络重试而重复执行，所以必须加幂等键，否则模型重试时会重复建单。

Q27. 为什么不用 Dify 这类平台？

平台适合快速验证，但我们要把 AI 嵌进已有的会话和工单链路里——工具要直接调我们的业务服务、写执行日志、隔离各客户的知识库，用平台反而不灵活。我们参考了它的模块划分。

Q28. 知识库检索用的什么策略？

混合检索：向量检索（语义）+ ES 的 BM25（关键词）→ RRF 融合出排序 → 重排取 Top5。
为什么要混合：纯向量对"订单号""退款期限"这类精确词召回不稳；纯关键词对"能不能退"这种口语化表达召回差。两者互补。

Q28-1. ★RRF 的分数能当相似度用吗？你们的阈值比的是哪个分数？★陷阱题

这题答错会暴露你没真跑过，必须答对。

"不能。RRF 计算出来的融合分数，是『排名的倒数之和』，它不是语义相似度，不能直接拿来套 0.72 这种阈值。"
（★注意措辞：别说"RRF 没有分数"——它是有分数的，只是那个分数的含义不是相似度。）

算一下就清楚：RRF 是 Σ 1/(k+rank)，k 取 60 ——
我们实际是两路召回（向量 + BM25），某条 chunk 在两路里都排第 1：
RRF = 1/61 + 1/61 = 2/61 ≈ 0.0328 ← 这才是我们的理论最大值
整个值域只有 0 ~ 0.033，拿它跟 0.72 比，结果是 100% 的查询全部判成"没召回"、全部兜底转人工——系统等于不工作。

根因是把几种量纲完全不同、含义也不同的分数混为一谈了：

分数值域能设阈值吗
向量余弦相似度0 ~ 1✅ 能，有绝对意义
BM25 分0 ~ 几十，无上界❌ 只能用于排序
RRF 分0 ~ 约 0.033（我们两路）❌ 它是排名融合分，不是语义相似度
重排（rerank）分取决于模型，不保证 0~1⚠️ 要先确认分数是否归一化，再定阈值

<blockquote class="q2"><p>★重排分那一行有个常见错误：写了"0~1"是不成立的——不同重排模型的输出可能是未归一化的 logits，也可能经过 Sigmoid 处理。
正确说法：先确认用的是哪个重排模型、分数怎么处理的，才能决定阈值。 阈值要通过评测集确定，不是拍脑袋。</p></blockquote>

我们实际的做法：

向量检索 → 余弦相似度 sim（0~1，有绝对意义）
BM25    → 只用于排序
RRF     → 产出融合分，但只用来排名；★它不是语义相似度，不参与阈值比较
Top5 送重排 → rerank 分（★是否归一化取决于模型）

阈值判断：
  · 召回为空                          → 兜底
  · 重排分不达标（如 < 0.72）          → 兜底
  · ⚠️ sim < 0.60 —— 见下面，不能当硬过滤

为什么最终判据用 rerank 分：向量相似度是双塔模型算的（问题和文档分别编码），精度有限；重排是交叉编码器（问题和文档拼在一起过模型），精度高得多。

★★这里还有一条常见写法是错的（容易漏）：常见写法是"sim < 0.60 就直接兜底，连重排都不调"——这个硬过滤会误杀 BM25 的正确结果。
反例：顾客发来一个精确的退款编号或错误码（如 RF20260915003），BM25 命中很好，但向量相似度可能很低（这种编号在语义空间里没意义）。如果只看向量分就提前兜底，就把一个 BM25 已经找到正确答案的问题推给了人工。
修正后的原则："向量相似度低"不能单独决定兜底，必须结合 BM25 的命中情况一起看。 有候选（向量或 BM25 命中都算）就送重排，最终是否兜底看重排分。0.60 这个值该不该留、留多少，要通过评测集测试确定，不要凭直觉写死。

Q29. 文档怎么分片的（chunking）？

结构感知分片 + 重叠窗口，不是固定字数切：
① 先解析文档的标题层级，一个"三级标题 + 正文"作为一个语义单元；
② 单块控制在 300~500 字；
③ 相邻块保留 15% 重叠，防止答案跨块被切断；
④ FAQ 类不切——一问一答本身就是完整语义单元。

Q30. AI 答不准怎么办？（幻觉）★核心亮点

现象：顾客问"能不能退"，机器人编了一个不存在的七天无理由。
定位：查 ai_execution 表发现那次召回的片段是空的，但流程还是走到大模型生成了——没有资料它也硬答。
方案：加后置校验——召回为空、或重排分不达标，就不允许生成，直接走兜底话术 + 转人工；同时把这个问题写进 ai_unanswered 表，运营补完知识后命中率回升。

★但要补一句边界（这是我后来修正的）：这个阈值只约束"知识问答类"的问题。因为"我的订单到哪了"这种请求，答案本来就不在知识库里，它该去业务系统拿——如果拿 RAG 的分数去否它，物流工具就永远没机会被调用。所以我们加了意图路由：知识问答走 RAG（受阈值约束），实时业务查询直接走 Tool Calling（跟 RAG 分数无关）。详见 Q35-1。
结果：机器人解决率从 41% 提到 63%。
【★诚实标注】这两个数是【设计设定的目标值】，不是上线后真实统计出来的——讲的时候说"我们定的目标是 41% 提到 63%"，别讲成"上线跑了两周观察到的"。

★主动交代口径和性质（否则被追问会卡）：
· 指标口径：分母是同期机器人接待的会话数，分子是整段会话没有转人工的会话数。
· 性质：41% 和 63% 是我们设定的目标区间，不是已验证的生产成果。
· 数据怎么来：实际统计时可以从 ai_execution 表聚合计算（这张表记了每轮的意图、召回、是否转人工，够算这个指标）——★但别把"目标值"说成"就是从这张表统计出来的"，那是两回事。这个口径的局限我也清楚——它衡量的是"没转人工"，不完全等于"问题真解决了"，所以报表里同时看解决率、转人工率、满意度三个指标。

Q31. 阈值（0.60 / 0.72）是怎么来的？

★先说 0.60 的正确说法（这里容易让人以为它是硬过滤阈值）：

"向量相似度可以作为检索质量和计算成本的参考信号，但不能单独决定兜底。 因为 BM25 可能找到向量相似度较低、但关键词高度匹配的内容——比如顾客直接发来一个退款编号或错误码，这种词在语义空间里没什么意义，向量分很低，但关键词是精确命中的。
所以我们先融合候选，再交给重排模型判断；最终是否兜底主要看重排结果。
0.60 这个值该不该留、留多少，要结合实际模型输出和评测数据确定，不是拍脑袋写死的。"

然后说 0.72：
"0.72 是设计中的经验阈值。真实调参方法是：收集 100~200 条真实顾客问题，人工标注'应该命中哪条'或'应该兜底'；对每条算出重排分（★不是 RRF 分），画曲线看'分数 ≥ X 的样本里正确率多少'；选一个正确率足够高、同时兜底率不太高的平衡点。"

★措辞注意（一个措辞上的注意点）：既然重排模型、分数归一化方式、评测结果还没最终确认，就把它讲成"设计中的经验阈值"，别说成"已经完成校准的生产参数"。

这个权衡没有标准答案，取决于业务对"答错"和"转人工"哪个更不容忍。我们的 ai_execution 表就是为这个调参准备的数据源（记录每次的向量分、重排分、是否兜底）——将来要靠它的真实数据来校准这两个数。

Q32. 会话记忆怎么做的？存多少轮？

Redis 存最近 10 轮上下文，30 分钟过期。
为什么 10 轮：大模型有上下文窗口限制，塞太多既贵又让模型抓不住重点；客服场景 10 轮基本覆盖一次完整咨询。
为什么 30 分钟：顾客中途走开再回来通常在这个时间内，超时说明是新的咨询。

Q33. 那 7 天前的对话还需要，怎么办？★进阶题

我们是三层记忆：
① 短期：Redis 存最近 10 轮原文，30 分钟过期——支撑当前对话连贯；
② 中期：会话结束后异步生成结构化摘要（诉求 / 已给方案 / 情绪 / 结论）写进 MySQL，同一顾客再进来时按需加载；
③ 长期：历史会话全量落库并按顾客维度建向量索引，需要时用语义检索召回相关片段，而不是把 7 天前的原文全塞进 Prompt。
关键点：不是"存多久"，而是"检索什么"——超过上下文窗口的对话必须靠检索召回，不能靠堆。

Q34. 你们用了 MCP 吗？★双栈架构下这题有陷阱

确定答案：没用。 不要说"用了"——会被追问"MCP Server 怎么搭的""工具怎么被发现的""跨服务鉴权怎么做"，答不上就穿。

基础答法：
"没用 MCP。我们的工具是 LangChain 的 @tool 直接注册在 Agent 服务里的。
MCP 我了解，是 Anthropic 提的开放协议，解决的是'工具怎么标准化地被发现和调用'。它真正值钱的场景是工具跨应用、跨团队、跨厂商复用。
我们的工具都是自己写的、就在 Agent 服务内注册，所以不上 MCP 是权衡的结果，不是没考虑过。"

★陷阱在这里：面试官可能追问"你们是双栈架构，Java 和 Python 跨语言，不正好该用 MCP 吗？"

这题必须接住，否则显得你没想到这一层。正确答法：

"这是个好问题，跨语言确实是 MCP 的典型场景。
但我们评估下来没上，原因是：我们 Java 侧需要暴露给 Agent 的能力只有 6 个，而且接口很稳定（查订单、查物流、查退款规则、建工单……）。
我们在 Agent 侧写了一个薄封装层——把 Java 的 inner 接口包成 @tool 函数，十来行代码一个。当前工具集小、封装成本低，暂时没必要引入一层标准化的工具服务层——收益不抵维护成本。
如果工具数量涨到几十个、或者要接第三方工具生态、或者有多个 Agent 共享同一批工具，那 MCP 的"标准化发现"就值钱了，我们会迁过去。"

★为什么这题答得好会加分：它逼你回答"你到底理解 MCP 解决什么问题"。
只会说"没用"是及格；能说出"跨语言是它的典型场景，但我们这个量级下收益为负，什么条件下会迁"——才是真评估过。

Q34-1. RAG 和微调（Fine-tuning）有什么区别？你们为什么选 RAG？★必背

这是概念题里最常问的一道，一定要能脱口而出。

一句话区分：

  • RAG = 不改模型，在提问时把相关资料一起塞进 Prompt（"开卷考试"）
  • 微调 = 改模型参数，把知识/风格灌进模型权重（"重新培训这个学生"）
维度RAG微调
知识更新改知识库即可，通常分钟级生效通常要重新训练、重新部署，具体周期取决于训练方式和模型规模
成本低（只花检索 + 多一点 prompt token）高（要标注数据、GPU 训练）
数据要求只要有文档，不需要标注通常需要成百上千条高质量标注样本（具体取决于任务难度和训练方式）
可溯源✅ 能给出引用来源❌ 答对了也不知道依据哪条
幻觉控制好（检索不到就兜底）差（模型"记住"的东西没法校验）
适合什么知识频繁变、要溯源固定风格/格式、固定领域话术

我们为什么选 RAG：
"客服知识库天天在变——今天改退货政策、明天上新品，微调根本跟不上；而且客服答错要能追责和溯源，必须能指出'这条答案来自知识库第几篇'，微调做不到这一点。再加上我们没有标注数据也没有 GPU，微调的成本我们承担不起。"

★加分句（体现你知道两者不互斥）：
"RAG 和微调不是二选一。如果哪天我们发现模型话术风格总是不符合客服规范（比如太啰嗦、爱用 Markdown），那可以考虑用少量样本微调它的风格，但知识还是走 RAG——这是两者的正确分工。"

Q35. MCP 和 Tool Calling、Function Calling 的区别？★新增高频题

Function Calling：模型厂商提供的能力——你给它一份函数签名，它返回"要调哪个函数 + 参数"，执行还是你自己做。
Tool Calling：Function Calling 的泛化叫法，工具不限于函数，也可以是一个 API、一次检索。本质是同一层。
MCP：不是模型能力，是协议标准，规定"客户端和工具服务端怎么通信"，把工具从你的代码里解耦成独立服务。
一句话：Function/Tool Calling 解决"模型怎么表达要调什么"；MCP 解决"工具怎么被标准化地发现和调用"。

接着主动补一句我们为什么没用：工具数量少且都在 Agent 服务内注册，当前没有"跨进程/跨团队发现"的需求，引入 MCP 这层标准化服务层的收益不抵维护成本。
（★别说"一定多一跳网络"——MCP 支持本地 STDIO 传输，不必然多一跳。）

Q35-1. Tool Calling 和 RAG 的区别？什么时候用哪个？★必背

一句话区分：

  • RAG 解决"知识从哪来"——查的是静态知识（政策、规则、说明书）
  • Tool Calling 解决"事情怎么办"——查的是实时数据 / 要执行的动作（订单状态、物流、建工单）
RAGTool Calling
数据源知识库（文档、FAQ、向量库）业务系统（订单、物流、工单接口）
数据特征静态、变化慢实时、每次都不一样
是否改状态只读可能写（建工单、登记回访）
失败怎么办召回不到 → 兜底转人工接口超时 → 兜底转人工

★我们项目里的真实例子（这题最好用例子答）：

顾客问题走哪条路为什么
"退货规则是什么？"RAG政策是静态知识，知识库里有
"我的空调到哪了？"Tool Calling（查物流）这是实时数据，知识库里不可能有
"我买的东西能退吗？退款到账要多久？"两个都要先 Tool Calling 查这笔订单的状态和购买时间，再 RAG 检索退款政策，组合起来回答
"我要投诉"都不走，直接转人工投诉是敏感场景，不该让 AI 挡

★关键设计点（这条最值钱）：
不能让 RAG 的低分无条件拦掉 Tool Calling。
比如顾客问"我的订单到哪了"，知识库里当然没有这个订单的信息，如果先做 RAG 判断、分数不够就兜底，那物流工具永远没机会被调用——用户明明问的是能查的问题，却被机器人推给了人工。

所以我们的流程是"先意图路由，再决定走哪条"：

意图识别
  ├─ 知识问答类（政策/流程/规则）→ RAG 检索 → 阈值判断 → 生成
  ├─ 实时业务查询类（订单/物流/工单）→ 直接 Tool Calling → 生成
  └─ 组合类（既要政策又要数据）→ 先 Tool Calling 拿数据，再 RAG 补政策 → 生成

只有"知识问答类"才受 RAG 阈值约束，业务查询类不看那个分数。

Q36. 大模型调用失败了怎么办？

三层防护：超时 → 降级 → 熔断。先说超时，因为这里有讲究。

① 超时要分四层，不能只设一个数（和技术手册 6.6 节完全一致）：

层级值含义
前端等待超时8 秒超过就显示"正在为您转人工"，别让顾客干等
Java 侧调用 Python 服务6 秒★必须小于前端等待，否则前端先超时了 Java 还在等
Python 侧业务总预算5 秒一次完整 Agent 执行（含检索 + 可能多轮工具调用）
单次 LLM 调用3 秒单次模型请求
单次工具调用1 秒跨语言 HTTP 回调 Java，比模型快得多，超时更短

★三条不能违反的规则：

  1. 外层必须大于内层（8 > 6 > 5 > 3 > 1）。顺序反了会出现"外层已放弃、内层还在跑"的僵尸请求，白占线程和配额。
  2. 总预算 ≠ 单次上限 × 次数。Agent 可能调 2 次工具 + 1 次模型，所以必须实现剩余预算机制：每次调模型/工具前先算剩余时间，超时用 min(单次上限, 剩余预算)。否则 3 次调用最坏就是 9 秒，外层 6 秒早放弃了。
  3. 超时要优雅收尾——走兜底话术 + 转人工，并且把这次超时写进 ai_execution，否则没法统计超时率。

② 降级——超时/限流/欠费时，先尝试返回知识库原文，还不行就走兜底话术转人工。
③ 熔断——用 Sentinel，失败率超 20% 自动降级成"全部转人工"的保底模式。

★双栈还多一条：Java 侧对 Python AI 服务也要设熔断，Python 服务挂了不能把 Java 主链路拖死。

核心原则：客服系统的可用性优先于"必须由 AI 回答"。 宁可转人工，也不能让顾客对着报错页面。

Q37. AI 的效果怎么量化？

每次执行都写 ai_execution 表：意图、召回片段 ID、工具调用、prompt_tokens、completion_tokens、耗时、是否转人工、兜底原因。
报表出四个指标：机器人解决率、转人工率、平均首响、token 成本。
这样 AI 就是可量化可回归的，不是黑盒。 比如改了一版 prompt，能直接对比前后的解决率和 token 消耗。

Q38. ai_execution 这个表数据量会不会很大？

不大。 单客户日均约 2.4 万条（8000 会话 × 平均 3 轮），每条 1~2KB，一个月约 1~1.5GB——企业系统里一张单表过亿行、总容量 TB 级很常见，我们这点量很轻。
处理方式：按月分表 + 只保留 3 个月热数据，更早的归档到 OSS。
真正占地方的是 prompt 和 answer 原文，如果要压缩，这两个字段可以只存摘要，原文另存。

七、并发与性能类

Q39. 你这个项目有高并发吗？怎么解决的？★别硬吹

诚实说：我们这个量级不算高并发——内部处理速率的设计目标约 30 次/秒，单库加缓存就够扛，做读写分离和分库分表反而是过度设计。

我们真正的压力不是 QPS，而是长耗时任务挤占资源——所以做的不是"扛高并发"，而是把慢操作隔离出去：
① AI 单独拆服务、独立线程池；
② 大模型超时压到 3 秒，超时走兜底；
③ Sentinel 熔断，失败率超 20% 降级成全部转人工。

如果真涨到 QPS 几千，我会按这个优先级做：先加缓存挡读 → 再治慢 SQL → 然后读写分离 → 非实时逻辑全异步化 → 最后才考虑分库分表和扩容。
【最后这句是加分项——说明你知道优化顺序，不会一上来就喊分库分表】

Q40. 项目里用到异步了吗？

有，但要说清"走哪条通道"，不能笼统说都走 Kafka：

场景通道为什么
实时消息投递Redis 路由 + 实例间转发 + WebSocket 推送★不走 Kafka——Kafka 是消费组模型，一个分区只被一个实例消费，保证不了"送达某个具体连接"（详见 Q10）
工单事件（通知处理人、发短信、写统计、触发质检）Kafka一对多、可容忍秒级延迟、要持久化
知识库向量化Kafka上传文档不能卡住上传接口，几十秒的活必须异步
会话结束后的 AI 质检Kafka重活，绝不能放进会话主链路
会话落库后的推送触发Kafka（用于持久化 + 回放）+ Redis 转发（用于实时投递）两者职责不同，不是二选一

一句话把边界说清：
"Kafka 负责持久化和异步业务，Redis 负责实例间实时转发，WebSocket 负责最后一跳推送。 三个通道解决三个不同的问题，不能混着说。"

Q41. 有没有处理过消息堆积？★这题你有现成案例

【★性质先说清，而且讲的时候要守住】这不是真实线上事故，是按生产环境推演 + 在本地模拟复现验证过的场景。
★表述纪律：可以说"我们模拟/推演/复现"、可以说"在这种压力下会暴露什么问题"；但不要说"我们遇到过""线上出过一次"——嘴一滑就变成编造经历了。被追问"哪一天、影响多少用户、有没有复盘报告"，就照实说"这是我们在压测和模拟环境里复现的场景，用来验证这个设计缺陷"。

现象：客户做会员日活动，咨询量涨了 6 倍，Kafka 消费 lag 报警，消息开始延迟。
定位：消费者线程里同步调大模型，一次 2~4 秒，把消费线程占满了。
解决：把 LLM 调用从消费者里剥出来，改成独立线程池 + 有界队列；超时从 10 秒降到 3 秒，超时直接走兜底话术；消费者只负责落库和推送。
预防：队列水位监控 + 消费 lag 告警 + Sentinel 熔断。

这个案例的价值：它是"异步解耦"和"隔离慢操作"的教科书级例子，比列四个 MQ 用途都有说服力。

Q42. 坐席分配怎么保证不超配？

用 Redis 原子操作扣减坐席在服会话数（Lua 脚本保证"判断 + 扣减"是一个原子动作），防止并发把同一个坐席分超。
分配策略是空闲优先 + 技能组匹配 + 会话上限（一个坐席最多同时接 5 个）。
验证方式：把上限设为 1 的坐席设成唯一在线，第 2 个会话必须排队而不是超配——这条我们实测过。

八、数据库与缓存类

Q43. 表大概多少张？怎么分组的？

约 29 张（★已包含 ticket_escalation 升级事件表），分 5 类：
客户与权限 6 张（客户、系统用户、角色、权限、角色权限、技能组）
会话与消息 7 张（访客、会话、消息、转接记录、坐席状态、常用语、评价）
工单 7 张（工单、模板、流转日志、评论、附件、SLA 规则、升级事件 ticket_escalation）
知识库 4 张（知识库、文档、切片、FAQ）
AI 5 张（Agent 配置、工具配置、会话、执行明细、未命中问题）

合计：6 + 7 + 7 + 4 + 5 = 29 张 ✅

Q44. 消息表数据量最大，怎么处理？

按月分表。单客户日均 6 万条消息，一个月约 180 万行——按月分表主要是为了归档和历史查询方便，不是为了扛写入。
查询走 ES：坐席要按关键词搜历史会话，MySQL 的 like %x% 走不了索引。

Q45. 为什么消息用 Kafka 而不是 RabbitMQ？

主要看吞吐和保序：Kafka 顺序写磁盘 + 零拷贝，单机十万级 QPS，而且按 key 分区天然能保序——我们正好用 sessionId 做 key 保证同一会话消息不乱序。
RabbitMQ 更擅长复杂路由（Exchange 多种类型）和低延迟，但吞吐低一个量级。我们不需要复杂路由，需要的是吞吐和保序，所以选 Kafka。

Q46. 向量库为什么用 PGVector 而不是 Milvus？

三个原因：
① 数据量——知识库切片只有几万条，PGVector 在 500 万条以内完全够用，Milvus 是千万级往上才体现优势；
② 运维成本——PGVector 就是一个 PostgreSQL 扩展，CREATE EXTENSION vector 一行搞定，备份/高可用/监控全复用 PG 生态。Milvus 单机版都要跑 etcd + MinIO + Milvus 三个组件，集群还要 Pulsar 或 Kafka，我们团队撑不住这个运维负担；
③ 混合检索更自然——我们要按客户标识 + 分类过滤再按向量排序，PGVector 一条 SQL 就写完：WHERE tenant_id = ? AND category = ? ORDER BY embedding <=> ? LIMIT 5。

我也评估过 Milvus，如果知识库涨到千万级、或需要 GPU 加速和量化压缩，会迁过去。迁移成本主要在向量数据重建，接口层做了抽象，换实现不用改业务代码。

Q47. 缓存穿透和缓存击穿怎么处理？

穿透（查不存在的数据，请求全打到库）：用布隆过滤器挡掉肯定不存在的 key，或者把空结果也缓存一个短 TTL 的占位值。
击穿（热点 key 突然失效，大量请求同时打库）：用分布式锁，只让一个请求去查库重建缓存，其他等待。

九、压力与情景题

Q48. 客户做活动，流量涨 10 倍，你怎么应对？

按顺序做：
① 先扩横向——会话和 AI 这两个服务无状态，直接加实例，网关自动负载均衡；
② 保护数据库——开启更激进的缓存策略，挡住重复读；必要时限流非核心接口（报表、导出）；
③ 保住主链路——AI 是慢操作，压力大时主动降级：把 AI 阈值调高，让它更容易转人工，把压力从大模型转到坐席（这是业务上的取舍，要提前和客户对齐）；
④ MQ 削峰——消息先落 Kafka，消费者按能力消费，不直接打业务库。
前提是这些开关要提前做好——不能等出事了才去改代码。

Q49. 线上出故障你怎么排查？

按"从外到内、从粗到细"：
① 先看监控大盘——是全面挂还是某个接口？错误率还是延迟？
② 看日志——我们有 traceId 串起整条链路，能快速定位是哪一跳慢/报错；
③ 看中间件——MQ 有没有堆积、Redis 有没有慢命令、数据库有没有慢 SQL 和连接池打满；
④ 定位后先止血再根因——比如先降级/回滚，恢复可用性，再慢慢查原因。
消息堆积那个场景我们就是这么排查的（★是模拟复现，不是线上事故）：看整体指标确认是消费端跟不上 → 看消费 lag → 看消费者线程栈，发现卡在同步调大模型上。

Q50. 你觉得自己这个项目最大的不足是什么？★送分题，别答"没有"
