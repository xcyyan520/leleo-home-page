一

父子块架构 vs 传统单级递归切分

题目：父子块架构与传统单级递归切分（带重叠）方案，在检索准确率、语义完整性、存储成本、检索耗时四个维度的优劣。

30 秒版

"这两种方案的差别，本质是同一个矛盾的两头：chunk 切大了，向量表示被平均掉、检索不准；切小了，语义不完整、答案被切断。

单级递归切分是用一个尺寸硬扛这个矛盾，靠重叠来缓解；父子块是把'检索'和'生成'拆成两个粒度——小块做检索、大块做生成。

所以结论是：父子块在检索准确率和语义完整性上更好，代价是存储成本和生成侧开销都上去了。它不是全面更优，是拿成本换质量。"

先把两者讲清楚

传统单级递归切分（RecursiveCharacterTextSplitter 那类）

按分隔符的优先级递归往下切，直到每块小于设定长度：

\n\n（段落） → \n（换行） → 。！？（句子） → ，、 → 空格

切完之后，相邻块之间保留一段重叠（overlap），防止答案正好压在边界上被切断。

特点：一份文本、一个粒度、一套向量。

父子块架构（Parent-Child / Small-to-Big）

同一份文档建两级：

层级粒度用途
父块（Parent）章节级，比如 1500~2500 字只做生成，进 prompt
子块（Child）段落级，比如 200~400 字只做索引和检索，算 embedding

流程是：子块建向量索引 → 检索命中子块 → 顺着 parent_id 取回父块 → 父块给模型生成。

关键点是：父块本身通常不做向量化（否则等于两套索引都白建）。父块的价值在于"它是一段完整上下文"。

四个维度逐条对比

维度单级递归切分父子块谁更好
检索准确率受 chunk_size 拖累：大块多主题，向量被"平均"，语义焦点糊掉；小块准但语义残。只能取折中子块只承载一个语义单元，向量表示更聚焦，同义不同字的口语化提问更容易命中父子块更好，这是它的核心收益
语义完整性靠 overlap 缓解。overlap 的本质是"让相邻块共享内容"，不是让块变完整——答案跨三块时，任何一块都可能只有一部分给模型的是完整父块，答案天然不会从半句话开始父子块更好，且这是它比 overlap 更彻底的地方
存储成本一份文本 + 一份向量，最低子块数变多（一般 2~4 倍）→ 向量条数、Embedding 调用、索引体积同步上涨；父块文本还要再存一份单级更省，父子块明显更贵
检索耗时一次向量查询，返回即可用召回延迟基本不变（都是一次向量查询，索引条数增加的影响有限）；但生成侧延迟和 token 成本明显上升，而且多一次"按 parent_id 取父块"的查询单级更快，差距主要在生成侧

算一笔账（10 万字政策文档，讲的时候可以口算）：

单级   ：500 字/块 → 200 块  → 200 条向量 → Top5 进 prompt ≈ 2500 字
父子块 ：父块 2000 字/章节 → 50 个父块
        子块 250 字/段落  → 400 个子块 → 400 条向量（2 倍）
        Top5 取到父块 → 进 prompt ≈ 10000 字（4 倍）

所以输出 token 成本和首字延迟都会跟着上去，这是父子块最容易被忽略的代价。

讲出这些，才像真的做过

① 父子块里"重排"是在哪个粒度上做的？

一般是对子块重排，然后返回父块。这里有个不一致：你优化的是子块的排序，但生成用的是父块——父块里可能包含好几个子块，"相关性"的粒度对不齐。如果坚持对父块重排，成本会高很多（交叉编码器要处理长文本）。

② 多个子块命中同一个父块，必须去重。

这个不加处理就会出问题：Top5 很可能全是同一个父块的 5 个子块，等于只召回了 1 个父块，另外 4 个名额浪费了。正确做法是先按父块聚合去重，再取 Top-N 个父块。

③ 父块的更新是个麻烦事。

文档改了，父块和它的子块要级联更新；删除文档时两边都要删。这是实打实的运维成本。

④ 上下文窗口变大了，父子块还需要吗？

需要，但理由变了。窗口大不等于能塞——塞得多有成本和"中间内容容易被忽略"的问题，而且瓶颈从来在检索精度，不在窗口。所以父子块的价值还在，只是它解决的是"检索粒度"问题，不是"窗口不够"问题。

结合项目怎么讲

口径提示：我们目前用的是结构感知切分 + 15% 重叠，父子块是评估过、没上。 把这一点说清楚，比假装上了要安全得多。

推荐答法（约 90 秒）：

"我们这个项目用的是结构感知切分——先解析文档的标题层级，一个『三级标题 + 正文』作为一个语义单元，单块控制在 300 到 500 字，相邻块留 15% 重叠，FAQ 不做切分。

父子块我们评估过，最后没上，主要两个原因。

第一个原因是我们的切分策略已经把父子块要解决的主要痛点解决掉了。 父子块之所以存在，是因为纯按长度切会把语义切碎，所以要用小块检索、大块补上下文。但我们是按文档结构切的——政策文档本身一个标题下面就是一条完整规则，切出来天然是完整的语义单元，不是半句话。也就是说，我们没有那个"小块才检索得准"的压力。

第二个原因是成本，而且在我们这个场景下成本是放大的。 我们现在 Top5 召回，每块 300 到 500 字，进 prompt 大概两三千字。如果换成父块，按章节算一块可能两三千字，Top5 就是一万多字，输入 token 直接涨四倍，首字延迟也会跟着涨。而客服场景对响应速度是有要求的。

所以我的判断是：父子块更适合那种"必须切得很小才检索得准"的场景——比如法律条文、技术文档、代码库，里面有大量相似但不相同的概念，小块才能区分开。我们这个政策问答，结构感知切分加混合检索的组合已经够用了。

不过我们保留了往回走的能力：每个 chunk 都带了所属文档和章节的元数据，如果以后发现召回片段经常缺上下文，升级到父子块的路是通的，不用重建整个链路。"

这段答法的关键：

  • 主动说"评估过、没上"——比假装上了安全，而且面试官会觉得你分得清"知道"和"做过"。
  • 给的两个理由都落在项目实情上（结构感知切分、Top5 的字数换算），不是泛泛的"成本高"。
  • 最后主动说"升级的路是通的"——显示你知道往哪走。

如果面试官追问"那你会怎么把它加进来"：

"改动点有三处：一是解析阶段同时产出父子两级，父块按章节、子块按段落，子块带 parent_id；二是索引阶段只对子块做 embedding，父块文本存在关系库里；三是检索阶段命中子块后按父块去重、取回父块再进重排和生成。要额外注意的是父块的级联更新和删除，还有重排粒度要对齐——不然容易出现'给模型的内容'和'用来排序的内容'不是一回事。"

追问预案

追问怎么答
"overlap 设多少合适？""我们取 15%，是经验值。重叠太大会造成同一段内容在多条里重复出现，既浪费重排算力又浪费 prompt token；太小防不住跨块切断。这个值应该跟分块策略一起用评测集调。"
"递归切分的分隔符顺序为什么是那样？""按语义强度从大到小排：段落比换行强，换行比句号强，句号比逗号强。目的是优先在语义边界上切，实在不行才退到更细的分隔符。中文还要额外把中文标点加进去。"
"小块检索会不会反而不准？""会。子块切得太碎，它自己也语义不全，向量表示反而偏。所以父子块的子块不能无限小，一般还是保持在段落级，不是句子级。"
"那你觉得父子块和 Rerank 冲突吗？""不冲突，是两件事。Rerank 解决'排序准不准'，父子块解决'给模型的内容够不够'。 我们现在的组合是混合检索加 Rerank，缺的是后半段。"
二

文档解析 → Markdown 优化 → 文本切分 → 双库入库

题目：这四个环节的流程说一下。

30 秒版

"这是知识库离线构建的完整流水线，四个环节各解决一个问题：

文档解析解决『把各种格式变成文本』——PDF、Word、Excel、扫描件，格式五花八门； Markdown 优化解决『把解析出来的脏文本变成结构化文本』——去页眉页脚、合并硬换行、保留标题层级； 文本切分解决『切成检索单元』——按结构切、控制长度、留重叠； 双库入库解决『让两路检索都能查到』——向量库管语义，全文检索库管关键词。

一句话串起来就是：解析把文件变成字，优化把字变成结构，切分把结构变成块，入库把块变成可检索的索引。"

环节一：文档解析

输入：PDF / Word / Excel / HTML / 扫描件。 输出：带结构的原始文本 + 版面信息（标题、段落、表格、图注）。

这个环节的难点几乎都在 PDF 上：

难点后果
双栏排版直接按坐标顺序读，会把左右两栏交错串成一句话
页眉页脚页码混进正文，而且每个 chunk 都带一份，污染向量表示
PDF 里的硬换行每一行末尾都有一个 \n。直接按 \n 切，一个完整的句子会被切成好几段
表格跨页表格被拆成两个不完整的表，检索到哪一半都读不懂
扫描件没有文本层必须先 OCR，而 OCR 一定会有错字

常见工具分层：

  • 有文本层的 PDF：PyMuPDF / pdfplumber 直接抽
  • 版面复杂、要识别标题层级和表格：版面分析类工具（MinerU、Unstructured、Docling 这一类）
  • 纯扫描件：走 OCR（PaddleOCR 之类）

口径提示：这一块不需要报具体库名，说清楚"我们是怎么分情况的"就够了。报不出具体库名不扣分，把双栏和硬换行的坑讲错才扣分。

环节二：Markdown 优化

为什么是 Markdown，而不是纯文本、也不是 HTML？

格式问题
纯文本丢了结构。标题层级没了，后面切分只能靠长度猜
HTML太冗长。标签占掉大量 token，而且噪声多
Markdown结构和内容的折中：# 表示标题层级、- 表示列表、`\` 表示表格，又短又能被模型直接理解，而且人也能读

具体做什么优化：

① 去噪    ：删页眉页脚、页码、水印、重复的免责声明
② 合段    ：把被 PDF 硬换行打断的句子重新拼回完整段落
③ 提层级  ：把"第一章 / 1.1 / （一）"这类编号统一映射成 # / ## / ###
④ 修表格  ：把跨页表格合并，恢复成 Markdown 表格
⑤ 清乱码  ：处理 OCR 错字、全角半角混用、多余空格

这一步的真正价值有两个，讲出来很加分：

  1. 它是"切分质量"的前置条件。 标题层级要在这一步提出来，后面的结构感知切分才有依据。上游不干净，下游怎么切都是错的。
  2. Markdown 可以同时当存储格式。 chunk 存成 Markdown，运营在后台预览时看到的是带标题和表格的片段，而不是一坨文字——这对"让人检查召回质量"很实用。

环节三：文本切分

按 Markdown 的结构切，而不是按字数切：

规则内容
切法按标题层级：一个「三级标题 + 正文」作为一个语义单元
大小超过 300~500 字就再按段落切
重叠相邻块保留 15%
特殊FAQ 不切——一问一答本身就是完整语义单元
元数据每块带上所属文档、章节路径、生效范围

为什么不能按固定字数切：固定 500 字会把「退货政策第 3 条」拦腰截断，检索时只召回前半句，模型答不全。按语义边界切，召回的是完整规则。

环节四：双库入库

"双库"= 向量库 + 全文检索库，对应两路召回：

库存什么干什么项目里是
向量库chunk 的 embedding + 元数据语义召回（口语化提问）PGVector
全文检索库chunk 原文 + 倒排索引关键词召回（订单号、编号）Elasticsearch

入库顺序（这段要能画出来）：

① 先写关系库 knowledge_chunk，拿到 chunk_id   ← 拿到幂等键
② 批量算 embedding → 写向量库（带 chunk_id / tenant_id / 章节 元数据）
③ 写全文检索库（中文分词建 BM25 索引）
④ 两个库都成功 → 文档状态改「已生效」
   任一步失败 → 状态留在「解析中」，消息重试

为什么是这个顺序：关系库里的 chunk_id 是两个检索库的幂等键。重试时用同一个 chunk_id 覆盖写，不会产生重复数据。这也解释了为什么文档状态要有「解析中 → 已生效」这个中间态——它是给"双写可能失败"留的位置。

这里有个真实的取舍，能讲出来是加分：

"两个库就有一致性问题——向量库写成功、全文库失败，就会出现'能语义搜到、但关键词搜不到'的半成品状态。我们的处理是以关系库的 chunk_id 为准、写操作做成幂等、失败整体重试，状态不到「已生效」就不对外可见。真正的分布式事务我们没上，靠的是幂等加状态机。

另外一种更彻底的做法是只用一个库：ES 8 本身支持 dense_vector，向量和 BM25 可以放同一个索引里，一次查询出两路结果。代价是向量检索的性能和调优不如专用向量库。我们选双库是因为 PGVector 的向量检索更成熟，ES 只专心做它擅长的全文检索。"

结合项目怎么讲

完整链路（目前链路中采用）：

运营上传政策文档
  ↓
原文存 MinIO（数据库只存 URL，不存文件本体）
  ↓
写 knowledge_document 表，状态 = 解析中
  ↓
发 Kafka 消息，异步做向量化        ← 为什么异步
  ↓
【解析】PDF / Word 抽文本，处理双栏、页眉页脚、硬换行
  ↓
【优化】规范成 Markdown，提出标题层级
  ↓
【切分】按标题层级切，300~500 字，15% 重叠
  ↓
【入库】写 knowledge_chunk 拿 chunk_id
        → 批量调 Embedding 模型（通义）算向量 → 写 PGVector
        → 写 ES 建 BM25 索引
  ↓
两个库都成功 → 状态改「已生效」，运营看到就能被检索

★为什么走 Kafka 异步（一定会被追问）：一个 10MB 的 PDF，解析加几十个 chunk 的向量化，跑完要几十秒。同步做会把上传接口卡死，运营以为页面挂了。所以上传接口只做"存原文 + 落记录 + 发消息"，秒回；后台消费者慢慢算。失败能重试，事务也不会被长耗时操作占着。

两个容易漏但很值钱的点：

  • 增量更新：文档改了，按 doc_id 覆盖对应的 chunk（先删旧再写新）+ 版本号，不是全量重建。
  • 换 Embedding 模型必须全量重建索引：新旧模型的向量空间不兼容，混在一起检索结果是错的。这条要能主动说出来。

追问预案

追问怎么答
"为什么要转 Markdown 再切？直接切文本不行吗？""直接切会丢掉两个东西：一是标题层级，切分就没有结构依据了；二是表格和列表的结构，检索回来的片段会散架。而且 Markdown 本身又短又结构化，模型也熟，塞进 prompt 的效果比纯文本好。"
"PDF 解析最容易出什么问题？""双栏串行和页眉页脚污染。尤其是页眉页脚——它会在每个 chunk 里都出现一遍，向量表示会被这些无意义的重复内容带偏。还有 PDF 的硬换行，不合并的话一个完整句子会被切碎。"
"扫描件怎么办？""走 OCR。但要接受 OCR 一定会有错字，所以OCR 出来的内容我会单独标记来源，运营审核后才入库——政策类文档答错是有法律风险的。"
"表格怎么处理？""小的转成 Markdown 表格。特别大或者特别复杂的表，我会考虑把每一行单独作为一个 chunk，带上表头信息——因为'某型号的保修期是多久'这种问题，答案其实在表的一行里。"
"两个库的一致性怎么保证？"见上面的「双库一致性」段：chunk_id 做幂等键 + 状态机 + 失败重试，真正的分布式事务没上。
三

你怎么评估 Agent 项目好坏？

30 秒版

"我不会只看一个准确率。Agent 的评估要分四层：效果、效率、工程、业务。

效果看答案对不对、工具选没选对；效率看延迟和 token 成本；工程看可观测性和稳定性；业务看解决率和人工成本。

而且 Agent 评估有个特殊难点——同一个问题可以走不同的路径都对，所以不能只评最终答案，还要评中间过程。

最关键的判断标准是：有没有一套人工标注的评测集。 没有评测集，任何'效果提升了多少'的数字都是不可信的。"

四个层次

① 效果层——答得对不对

指标衡量什么
任务完成率端到端有没有把事办成
工具调用正确率拆两个：选对工具（该查物流的时候没去查知识库）+ 参数填对（订单号没传错）
忠实度（Faithfulness）答案是不是都能从召回资料里找到依据——这是衡量幻觉的核心指标
答案相关性有没有答到点上，而不是答了一堆正确但没用的话
上下文精度 / 召回精度=召回的片段里几条真相关；召回=该召回的有没有被召回到

② 效率层——花多大代价

  • 端到端延迟（尤其 P99）：Agent 是多轮调用，一轮慢就全慢
  • 单次成本 / token 消耗：输入 token 往往比输出贵得多，因为要反复塞上下文
  • 工具调用轮数：步数越少通常越好——同一个任务用 2 步和用 8 步，能力和成本差很多

③ 工程层——靠不靠得住

  • 可观测性：每一步（意图、检索、工具、生成）有没有留痕，出问题能不能回放
  • 幂等：工具被重复调用会不会产生副作用（重复建单、重复发短信）
  • 降级能力：模型超时、限流的时候有没有兜底
  • 可复现性：同一套题跑两次，结果稳不稳

④ 业务层——值不值

  • 解决率 / 转人工率：这是最直接的业务指标
  • 人工成本节省：省了多少人力
  • 用户满意度（CSAT）：有没有投诉、有没有答错导致的工单

Agent 评估的特殊难点

难点一：路径不唯一。

传统模型评估是"输入 → 输出 → 对答案"。Agent 不一样，同一个问题走不同的工具链都可能是对的。所以要看轨迹（trajectory），不只看最终答案：

"评估 Agent 要比评估普通模型多一维——不但要看结果对不对，还要看过程合不合理。比如同一句『我的订单怎么还没到』，正常路径是先查订单再查物流；如果它先去翻了十遍知识库、最后才想起来查订单，答案可能对，但这个 Agent 的设计是有问题的。"

难点二：没有标准答案的任务怎么办。

有些任务是开放式的（"帮我整理这份材料"）。这时候要么人工打分，要么用大模型当裁判（LLM-as-a-Judge），但要注意裁判本身有偏差，得抽样人工复核。

难点三：评测集从哪来。

  • 从真实线上问题里抽（最有价值）
  • 人工标注"应该命中哪个片段""应该调哪个工具"
  • 规模不用大，100~200 条就能看出方案差异
  • 关键是标注要落在可验证的东西上（命中的 chunk_id、调用的工具名），而不是"这个回答好不好"这种主观判断

结合项目怎么讲

这一段要用"诚实档"，因为我们的评估确实不严谨。

"我们这个项目，评估做得分两部分：有的做得还行，有的不够。

做得还行的是可观测性。 我们有一张 ai_execution 表，每一次 AI 调用都会记：识别出的意图、路由到哪条分支、召回了哪些 chunk、调了哪些工具、消耗了多少 token、耗时多少、最后有没有转人工。 有了这张表，改一版 prompt 能直接对比前后的解决率和 token 消耗，不用凭感觉。

另外还有一张 ai_unanswered 表，专门记没答上来的问题——运营按提问次数降序看，哪些问题问得多又答不好，就去补知识。这两张表合起来，其实就是一个粗糙的'失败样本集'。

做得不够的是效果评估。 我们目前只有『机器人解决率』这一个代理指标，它衡量的是'没转人工'，不完全等于'问题真的解决了'——有些问题顾客懒得追问，也算在里面了。

如果让我重新设计，我会做三件事： 第一，建人工标注的评测集——从真实会话里抽 100 到 200 条问题，人工标注应该命中哪个 chunk、应该调哪个工具； 第二，分开评检索和生成——检索用 Hit@5 和 MRR，生成看忠实度和答案相关性，这样出问题能定位到是哪一段的锅，而不是只知道'整体不好'； 第三，做 A/B 对比——固定其他变量，只换一个东西（比如换分块策略、换重排模型），跑同一套题。

现在能做的是弱证据：人工抽查召回片段完不完整、看兜底率有没有异常升高、看 ai_unanswered 里有没有『知识库里明明有却答不出来』的问题。这些是信号，不是测量结果，我不会把它说成准确率。"

这段为什么加分：

  • 主动说"我们这块不严谨"——面试官最怕的是候选人不知道自己不知道什么。
  • 但马上给出具体的、可执行的改进方案（评测集怎么建、指标怎么选、A/B 怎么做）——说明你不是没做好，是知道该怎么做还没做。
  • 用 ai_execution 和 ai_unanswered 落到项目实处，证明你真的用过这套东西，而不是背了一套评估理论。

追问预案

追问怎么答
"LLM-as-a-Judge 你觉得可靠吗？""能省人力，但不能当唯一依据。 它本身有偏差——比如偏向更长的回答、偏向和自己风格接近的回答。我的用法是用它做粗筛，人工抽样复核，而且裁判用的模型最好和被测模型不是同一个。"
"Agent 的延迟怎么优化？""三个方向：① 能并行的工具调用并行——比如同时查订单和查物流，不要串行；② 减少不必要的轮数——把常用信息放进 System Prompt 或者缓存；③ 流式输出——用户能早点看到第一个字，感知延迟会好很多。"
"怎么衡量幻觉？""忠实度：把生成的答案拆成若干断言，看每一条能不能在召回片段里找到依据。工程上更简单的做法是强制模型输出引用，然后校验引用是不是真的来自召回内容。"
"如果模型答错了，你怎么定位是哪一步的锅？""看链路留痕。 意图识别错了、检索没召回对、召回对了但模型没用、还是生成本身胡说——这四种情况的修法完全不一样。所以 ai_execution 里要把每一步的中间结果都记下来。"
四

知识的入库，这个数据的来源于哪里？

30 秒版

"我们的知识来源有四类，按权威性和更新频率分：

一是客户提供的政策文档——退换货政策、保修条款、运费规则这类，权威性最高，更新最慢； 二是运营整理的 FAQ——高频问题做成问答对，质量最高、更新最频繁； 三是历史会话回流的问题——AI 没答上来的问题会被记下来，运营看到问得多的就补一条，这是个闭环； 四是坐席在工单里沉淀的解决方案——被标记为可入知识库的，由运营审核后入库。

核心不是'从哪来'，而是'谁负责、谁审核、什么时候失效'。"

四类来源的细节

① 客户提供的政策文档（PDF / Word / Excel）

  • 谁给：签约后由客户方的业务部门提供，我们只负责入库，不负责判断内容的正确性。
  • 特点：结构化程度低、更新频率低（季度或年度）、权威性最高。答错有法律风险。
  • 处理：走完整的解析 → Markdown 优化 → 切分 → 双库入库流水线。

② 运营整理的 FAQ

  • 谁维护：客户方的客服运营，我们提供管理后台。
  • 结构：「标准问题 + 相似问法（JSON 数组）+ 标准答案 + 生效范围」。
  • 特点：质量最高、直接可用，而且更新最频繁——运营每周都在补。
  • 处理：不切分。一问一答本身就是完整语义单元，把"问题 + 相似问法"合成一份向量。

③ 历史会话回流的高频问题（这是闭环）

顾客提问 → AI 没召回/答不好 → 记进 ai_unanswered 表
   ↓
运营在后台按【提问次数】降序看
   ↓
看到一个问了很多次又答不好的问题 → 补一条答案
   ↓
补完之后，这类问题的命中率回升

为什么按"提问次数"而不是"最近时间"排序：问得多的说明影响面大，补一条的收益最高。 这是把有限的运营精力花在刀刃上。

④ 坐席在工单里沉淀的解决方案

  • 坐席处理完工单之后，写的解决方案如果被标记为"可入知识库"，进审核队列。
  • 必须经过运营审核才生效——因为坐席写的是针对某一个客户的具体处理，直接入库可能把个案当通用规则。

结合项目怎么讲

表结构上怎么体现（这段能证明你真设计过）：

knowledge_base       知识库（名称、类型、Embedding 模型）
knowledge_document   文档（原文 URL、类型、分段数、解析状态、版本）
knowledge_chunk      切片（内容、token 数、vector_id 指向向量库）
knowledge_faq        FAQ（问题、相似问法 JSON、答案、命中次数、提问次数）
ai_unanswered        未命中问题（问题、意图、提问次数、状态）

推荐答法（约 60 秒）：

"来源上主要是客户给的政策文档、运营维护的 FAQ、还有从历史会话里回流的高频问题，另外坐席处理工单时写的解决方案，如果被标记为可入库，审核之后也会进知识库。

落到系统里，这四类数据在表上是分开的：政策文档走 knowledge_document 加 knowledge_chunk，是解析切分出来的；FAQ 单独一张 knowledge_faq 表，因为它不切分，而且多两个计数字段——命中次数衡量'这条知识有用'，被提问次数衡量'这个问题问得多'，运营就是按提问次数降序去补答案的。

而问题从哪来，是靠 ai_unanswered 表——AI 没答上来的问题会记进去，和 FAQ 表配合形成一个闭环：顾客问得越多、答得越差的问题，越优先被补上。

有两件事我们做得比较克制。第一是审核——坐席沉淀的内容必须经过运营审核才能生效，因为坐席处理的是个案，直接入库会把个案当通用规则。第二是版本——政策文档是有时效的，所以我们按版本管理，改文档时按 doc_id 覆盖对应的 chunk 并带版本号，不是全量重建索引。

还有一点是隔离：每个客户独立 schema 加独立向量 collection，物理分开，检索时还会带客户标识做过滤——A 客户的政策文档绝不会出现在 B 客户的检索结果里，这在交付型项目里是底线。"

如果被问"你们会去网上爬资料吗"：

"不会。知识库的内容是客户方提供的，我们只做入库和处理。 政策类内容答错是要担责任的，来源必须可追溯——每条 chunk 都能回溯到原始文档，这是我们做元数据的基本要求。"

追问预案

追问怎么答
"政策变了怎么办？""版本管理。 新版本入库后旧版本归档，检索只命中生效中的版本；如果是小改动，就按 doc_id 覆盖对应的 chunk 加版本号。关键是历史会话里引用过旧版本的记录不能受影响，所以日志里存的是 chunk_id，不是内容快照。"
"谁有权限上传知识？""知识库的管理接口在 Java 侧，走网关鉴权，按客户和角色授权。Python 侧只负责解析和检索，它不对外暴露上传入口。而且上传、修改、删除都有审计日志。"
"冷启动的时候知识库是空的怎么办？""先灌政策文档和 FAQ。 交付的时候，客户方会先给一批政策文档，运营整理一批高频 FAQ，这两块能覆盖大部分常见咨询。剩下的就靠上线后从 ai_unanswered 里慢慢长——这是知识库运营的常态，不是一次灌满。"
"怎么保证入库质量？""三道：上传时校验格式和大小、解析完成后运营能看到切片预览（这也是我们保留 Markdown 存储的原因，人能读）、上线前抽样测一批问题看召回得对不对。"
"知识库里答错了怎么办？""先下线那条知识，再排查是知识本身错了还是检索召错了。 另外我们在生成前有检索门控：召回为空或者重排分不达标，就不调用生成模型，直接走兜底或转人工——宁可转人工，不能胡说。"
五

你上一份工作为什么离开？

这题看的是三件事：会不会抱怨前公司、职业规划清不清楚、稳定性如何。 这题必须用你的真实情况替换——下面给的是结构和模板，事实部分你自己填。

答题结构：三段式，控制在 1 分钟内

第一段  肯定前公司（不抱怨）+ 客观事实
第二段  给一个正向的、和应聘岗位挂钩的理由
第三段  说明为什么是现在、为什么是你们

关键是第三段。 只说离职原因是"逃离"，说清楚"为什么来"才是"选择"。

模板一：项目交付完成，进入维护期（★和本项目口径最契合）

"我上一家做的是企业软件定制开发，项目的节奏是跟着交付走的。我负责的那个客户项目，去年底上线交付完成，后面就进入运维期了，工作内容会偏向维护和响应——这半年我做的事情重复度比较高。

我自己的想法是，我还想继续做有挑战的新项目，特别想把 AI 应用这块做深。在这个项目里我负责了 AI Agent 编排那块，从 RAG 检索、Tool Calling 到生成前检索门控和生成后输出校验都有参与，做下来觉得这个方向我挺感兴趣，也愿意继续投入。

所以我看机会的时候，主要是看这个岗位有没有真实的 AI 落地场景——不是只挂个 AI 的名字，而是真的能碰到检索、Agent 这些事。这也是我投你们的原因。"

为什么推荐这个：它和你的项目口径天然一致——定制交付型公司本来就是"项目制"节奏，交付完转维护是行业常态，这个理由不需要编，也经得起追问。

模板二：公司方向调整 / 项目组缩编

"我上一家公司做企业软件定制开发，去年下半年公司整体在往另一个方向调整，我们那条业务线的投入缩了，团队也有调整。我评估下来，留在那边能做的新东西会比较有限，所以想出来看看机会。

这段经历我还是挺感谢的，我从需求评审到上线交付完整跟过一遍，对客服和工单这类业务也比较熟。我下一个方向想更聚焦在 AI 应用开发上，因为我在这块做过完整的一轮。"

注意：如果是被动离职，照实说，但说清楚原因（业务线调整、整体缩编），并且不要带情绪。面试官最怕的是候选人把责任全推给公司。

模板三：方向不匹配（技术方向想转）

"上一家的工作偏传统业务开发，我做得也不错，但说实话，我更想往 AI 应用这个方向走。我在那个项目里主动争取做了 AI 编排那一块，做完之后确定了这是我接下来想深耕的方向。

而上一家短期内没有新的 AI 项目，我不想一直等，所以想找一个真的有 AI 场景的团队。"

必须避开的五条

不要说为什么
抱怨薪资低、领导差、管理乱、加班多第一杀手。 面试官会想"你以后也会这么说我们"。而且抱怨换不来同情，只会换来风险判断
"想换个环境""想挑战一下自己"太虚，等于没答。没有具体事实支撑的理由，听起来都是在掩饰
"和同事/领导合不来"直接把人际风险摆上桌
"公司没前途"你在评价一家你待过的公司，评价得越绝对，越显得主观
"我就是想涨薪"涨薪可以是理由之一，但不能是唯一理由，而且要放在最后、轻描淡写

追问预案

追问怎么答
"如果给你加薪，你会留下吗？""这不是钱的问题。 我在那边薪资是符合我预期的，主要是方向上——我想继续做 AI 落地这块，那边短期没有这样的项目。" （★如果你用的理由是薪资，这题就没法答，所以主理由千万不要选钱）
"你和上家领导关系怎么样？""挺好的。离职前我跟他聊过，他也理解我的想法，交接也做完了。"
"上家离职率高吗？""这个我不太清楚，也没统计过。 我们组当时还算稳定。" （★不评价、不猜测，尤其不要说"挺高的"）
"你离职多久了？这段时间在做什么？""主要在做两件事：一是把上个项目的技术点系统复盘了一遍，特别是 RAG 和 Agent 编排这块；二是补了一些工程化的东西，比如评测和可观测性——这些是我在项目里觉得做得不够的地方。" （★这题一定要有内容，空窗期说"在休息/在找"会掉分）
