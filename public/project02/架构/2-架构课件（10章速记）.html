01

项目一页纸概览

面试开场 60 秒要能讲完的东西：是什么、给谁用、多大、扛多少量。

项目名称

云联客服工单平台

一套可复用的客服底座：在线会话 + 智能机器人 + 工单协同 + 知识库 + 报表。

产品定位（必须说准）

企业软件定制交付 不是多租户 SaaS 产品

交付给 3 家企业客户：1 家连锁零售 + 2 家电商，部署在客户自己的环境里。 因为是交付型，天然没有对外产品官网 —— 这正好避开面试官"打开官网给我看看"的致命问题。

规模自洽性（面试官一定会算这笔账）

  • 最大客户日均 6 万条消息，集中在 10 小时 ≈ 1.7 条消息/秒；按每条消息可能触发的内部处理动作估，平均内部操作约 8 次/秒，再乘约 4 倍峰值系数 ≈ 30 次/秒。
  • 所以报"内部处理速率【估算】约 30 次/秒 / 写 TPS 8"是自洽的；报 QPS 120 就和"40 人公司交付 3 家客户"的规模对不上了。
  • 口径红线：这个 30 是基于业务量的估算，不等于网关入口 QPS，也不是压测实测值。压测只能验证"扛不扛得住"，不能反推生产峰值。
  • 数据量口径统一说"按最大单客户"，不要把三家相加。
  • 坐席规模 200 人左右，单坐席同时在服会话上限 5 个。
  • 团队：项目经理 1、产品 1（共享）、架构师 1、后端 6（高级 1 : 中级 4 : 初级 1）、前端 2（共享）、测试 2（共享）、运维 1（共享）。
  • 开发周期 12 个月，其中我负责的模块开发 7 个月。
口径铁律：凡是要说"租户"的地方，口头一律换成"客户"；隔离方式说"每个客户独立 schema + 独立向量 collection"，不能说成"SaaS 共享库 tenant_id 隔离"。

03

核心业务流程图

从顾客进线到数据回流知识库的完整闭环 —— 这是你面试讲 15 分钟的主线。每一步下面都标了"技术点是什么"。

1
顾客进线
顾客在网页 / H5 发起咨询，建会话、写库、状态=机器人接待中。
技术点：Redis 存会话上下文（最近 10 轮），过期 30 分钟。
➜
2
机器人接待
意图识别 → RAG 检索 Top5 → Tool Calling → LLM 生成。
技术点：SSE 流式返回；答案必须带知识引用。
➜
3
转人工（接待分配）
按技能组分配坐席：轮询 → 空闲优先 → 技能组匹配 → 会话上限超 5 个不再分配。
技术点：Redis Lua 原子扣减坐席在服会话数，防并发超分。
➜
4
人工接待
双向消息 WebSocket 收发，落 MySQL + 异步投 Kafka。
技术点：Kafka 按 sessionId 分区，单会话串行消费保序。
➜
5
建工单
坐席点"转工单"，选模板（退款/发票/技术故障/投诉），自动带入顾客信息 + AI 会话摘要 + 附件。
技术点：发 Kafka 事件：通知处理人、写统计、SLA 计时启动。
➜
6
SLA 计时与超时升级
每分钟扫描未完成工单，算首响 / 解决 SLA 剩余。
技术点：剩余 20% 提醒处理人；超时升级上级 + 标记超时；支持暂停计时（等客户回复时暂停，paused_time 累计）。
➜
7
结束 + AI 质检
会话结束触发 AI 质检（Kafka 异步）：情绪、违规词、服务态度、是否解决；生成满意度邀请（1~5 星）。
技术点：异步解耦，不阻塞主链路。
➜
8
数据回流知识库
未命中的问题写 ai_unanswered，运营补充知识后重新向量化生效。
技术点：Kafka 异步向量化，形成"AI 接待 → 未命中 → 补知识 → 命中率回升"的闭环。

转人工的触发条件（人工兜底不可绕过，这是真实客服产品铁律）

意图 = 投诉 连续 2 次未识别 命中转人工关键词（最多 30 个） 顾客主动说"人工" 召回为空 / 重排分不达标

命中任意一条 → 直接返回 TRANSFER，交给 conversation 服务做接待分配。

知识库从上传到生效（第二条能讲的流程）

上传文档到 MinIO → 写 knowledge_document（parse_status=解析中）→ 发 Kafka 异步任务 → 文档解析切分 chunk → 调 embedding 模型向量化 → 写 knowledge_chunk（vector_id 指向向量库主键）+ 写 PGVector → 同时写 ES 供 BM25 → parse_status=已完成，检索立即可用。

04

AI Agent 链路图

顾客一句话，在系统里到底走了多少步。这张图是"你真的做过 AI 落地"的证明。

顾客消息
网页 / H5 / 公众号等渠道进来的一句话。
conversation 服务
WebSocket 收消息 → 落库 → Redis 存会话上下文（最近 10 轮，TTL 30 分钟）。
OpenFeign 调用
conversation-service → ai-service：POST /inner/ai/chat 机器人接待。
ai 服务（编排入口）
所有智能能力都收敛在这一个服务里，业务服务不感知模型细节。
① 意图识别
一次轻量 LLM 调用或小模型分类，输出 intent + confidence。分类：售前咨询 / 售后 / 物流 / 投诉 / 其他。
命中转人工条件 → 直接返回 TRANSFER，不再往下走。
② RAG 检索（混合检索 + 融合）
调 knowledge 服务：POST /inner/knowledge/search
问题向量化 → 向量库召回 → 与 ES BM25 结果做 RRF 融合 → 重排取 Top5 知识片段。
只查本客户知识库（客户之间物理隔离），并带 tenant_id metadata 过滤做二次防护。
③ 判定是否需要业务数据
需要 → Tool Calling（LLM Function Calling 决策），用 OpenFeign / RestTemplate 调业务服务，把结构化结果回填 Prompt；
不需要 → 仅用知识片段进生成。
④ LLM 生成答案
System Prompt 强制约束：只依据给定资料回答，不确定就转人工。走 DeepSeek / 通义千问双通道，失败自动降级备用模型。
⑤ 后置校验（幻觉兜底）
召回片段为空，或重排分不达标（设计中的经验阈值 0.72）→ 禁止生成，直接走兜底话术（"我帮您转人工确认一下"）+ 转人工。
★注意：向量相似度只作参考信号，不能单独触发兜底——BM25 可能精确命中而向量分很低，硬过滤会误杀正确结果。 其余校验：是否引用知识、是否包含违规词、长度是否合理。
⑥ 写 ai_execution 日志（Kafka 异步）
记录：intent / confidence / retrieved_chunk_ids / tool_calls_json / prompt_tokens / completion_tokens / latency_ms / model_code / answer_source / is_transferred。
同时把未命中的问题写进 ai_unanswered，回流知识库优化。
返回：答案 + 知识引用 + 是否转人工
回到 conversation 服务，通过 WebSocket 推给顾客；若 is_transferred=1，转入接待分配流程。

面试官追问"你怎么知道 AI 答得准不准"→ 指这张图

  • 可观测：ai_execution 全链路日志（意图 / 召回 / 工具 / 耗时 / token / 是否转人工）。
  • 可量化：AI 解决率 = robot_resolved 会话数 ÷ 机器人接待会话数。
  • 可回归：报表里出平均首响、token 成本、AI 解决率；answer_source 标 KB / TOOL / LLM / FALLBACK 一眼看出答案从哪来。
  • 闭环：未命中 → ai_unanswered → 运营补知识 → 命中率回升。

Agent Tools 清单（8 个，直接背）

工具签名存在 ai_agent_tool.param_schema_json 里给 LLM 看；调用明细落到 ai_execution.tool_calls_json。

工具入参出参对应业务场景
queryOrder 订单号 / 手机号 订单状态、商品、金额、下单时间 顾客问"我买的东西到哪了/我的订单什么状态"
queryLogistics 订单号 物流公司、运单号、最新轨迹 物流进度查询，替代人工查快递
queryRefundRule 商品类目 / 订单号 退款规则、可退期限 退货退款规则咨询（也是幻觉高发问题）
queryProduct 商品 ID / 关键词 商品属性（成分 / 尺码 / 功效）、价格、活动价 商品属性联动导购
queryActivity 商品 ID / 客户标识 当前活动、优惠券、会员权益 活动关联，售前促单
queryTicket 工单号 工单状态、当前处理人、SLA 剩余 工单衔接在线客服：顾客问"我的问题处理得怎么样了"
createTicket 意图、摘要、顾客 ID 工单号 转人工前兜底建单，保证问题不丢
createCallback 手机号、原因 回访任务号 留资 / 回访，顾客要"稍后让客服打给我"
被追问时的一句话：工具不是让 LLM 随便调外部 HTTP，而是每个工具在 ai_agent_tool 里配好 tool_code / param_schema_json / api_path / method / timeout_ms， LLM 只输出"工具名 + 参数 JSON"，真正发请求的是 ai 服务，参数要过 JSON Schema 校验，超时可控、可审计。

三大难点（现象 → 定位 → 方案 → 结果）

这三张卡是面试的核心弹药，每张都要能脱稿讲 2 分钟。

难点 1 多实例 WebSocket 的消息路由与会话一致性

现象

坐席 A 连在实例 1，顾客消息却被实例 2 收到，坐席 A 收不到消息（消息"串话"）；会话结束后 Redis 里残留路由信息。

定位

抓日志发现同一个 sessionId 同时出现在两台机器上；进一步查 Redis，发现 session_route key 没有随会话结束删除。

方案

Redis 存 session_route:{sessionId} → {instanceId} 路由表；消息先写 Kafka（按 sessionId 分区保证单会话有序），各实例消费后只推送本机持有的连接；会话关闭事件里删除路由 key，另加兜底 TTL 30 分钟。

结果

消息串话问题归零，P99 消息投递在 500ms 以内（含落库、Kafka、推送三段）。

难点 2 SLA 引擎的超时计算与"暂停计时"

现象

工单等客户回复期间 SLA 仍在计时，导致大量误判超时，客户投诉。

定位

扫描任务只按 deadline 算剩余时间，没有把"等客户回复"这段排除掉；而且多实例各自跑扫描任务，同一张工单被重复升级。

方案

工单加 paused_at（本次暂停开始时间）+ paused_total（累计暂停时长）两个字段；状态切到"待客户回复"时写 paused_at，切回时把这次暂停时长累加进 paused_total 并清空 paused_at；扫描任务用 deadline + paused_total 计算真实剩余；扫描用 XXL-JOB 分片广播避免多实例重复执行。

结果

超时误判率从 12% 降到 1% 以内。

难点 3 AI 答案不准 / 幻觉

现象

顾客问"能不能退"，机器人编了一个不存在的 7 天无理由政策。

定位

查 ai_execution，发现 retrieved_chunk_ids 为空却仍然走了 LLM 生成 —— 也就是"没有命中知识也硬答"。

方案

加后置校验：retrieved_chunk_ids 为空，或重排分低于设计中的经验阈值 0.72 时不允许生成（★向量相似度只作参考信号，不单独触发兜底——BM25 可能精确命中而向量分很低，硬过滤会误杀正确结果），直接走兜底话术 + 转人工；同时把该问题写入 ai_unanswered 表，运营补充知识后命中率回升。

结果

机器人解决率【目标】从 41% 提升到 63%（★项目设定的目标区间，不是已验证的生产成果），转人工率下降 15 个百分点，误答投诉归零。

附加弹药：线上问题一个（面试官问"讲一个你处理过的线上故障"）

  • 现象：客户做会员日活动当天咨询量涨了 6 倍，出现消息延迟和部分消息丢失。
  • 定位：Kafka 消费者 lag 报警 → 发现消费逻辑里有同步调 LLM（每次 2~4 秒），把消费线程占满了。
  • 解决：把 LLM 调用从消费者里剥离成独立的线程池 + 有界队列；LLM 超时从 10s 降到 3s，超时走兜底话术；消费者只做落库和推送。
  • 预防：加入队列水位监控和消费 lag 告警；对 LLM 调用做熔断（Sentinel），失败率超 20% 自动降级为"全部转人工"的保底模式。

6 个"为什么不选另一个"（点开看答案）

① 为什么用 WebSocket，不用轮询？
客服会话是双向实时的：顾客发一句，坐席要立刻看到；坐席回一句，顾客要立刻看到。

轮询要 2~3 秒一次，200 个坐席 × 数千个活跃会话会产生大量空请求 —— 大部分轮询返回的是"没有新消息"， 既浪费连接数，也白白打数据库 IO，还把实时性拖到秒级。

换成 WebSocket 长连接后：服务端有消息主动推，实时性是毫秒级；连接复用，没有无效请求。

追问"WebSocket 多实例怎么办" → 正好接难点 1：Redis 存 session_route:{sessionId} → {instanceId}， 消息先写 Kafka（按 sessionId 分区保序），各实例消费后只推本机持有的连接。
② 为什么用 Redis 做会话路由？
因为 WebSocket 是有状态的：坐席 A 的连接实实在在握在实例 1 的内存里。 顾客消息可能被任意一台实例收到（网关负载均衡），但只有实例 1 能把消息推给坐席 A。

所以需要一张"会话 → 实例"的路由表，而且必须满足三点：
· 读写极快：每条消息都要查一次，QPS 不低；
· 多实例共享：不能存在单机内存里；
· 可设过期：会话结束后要能自动清理，避免残留脏路由。

Redis 的 SET key value EX 1800 正好三件事全满足。库里再配一个会话关闭事件主动删 key， 双保险（主动删 + 兜底 TTL 30 分钟）。

另外坐席分配的"在服会话数原子扣减"也用 Redis + Lua 做，防止并发把同一个坐席超分。
③ 为什么用 Kafka，而不是服务间直接调用？
工单创建之后要做的事是一对多、且允许延迟的：通知处理人、发短信、写统计、触发 AI 质检。

如果直接同步调四个下游：
· 强耦合 —— 短信服务挂了，工单就建不了；
· 响应变慢 —— 建单接口要等四个下游全返回；
· 扛不住峰 —— 大促咨询洪峰时，下游被打穿。

用 Kafka 之后：工单服务只管发一条事件，下游各自订阅；解耦、削峰、可重放（下游补数据时能重消费）。 同时 Kafka 的按 sessionId 分区还顺手解决了单会话消息保序的问题 —— 同一 sessionId 一定落到同一分区，串行消费不乱序。

追问"那 LLM 调用为什么也放消费者里" → 这就是我踩过的坑：LLM 单次 2~4 秒，把消费线程占满导致 lag 飙升。 后来剥离成独立线程池 + 有界队列，消费者只做落库和推送。
④ 为什么用 Elasticsearch？
因为坐席要按关键词搜历史会话和工单，而 MySQL like '%关键词%' 无法走索引， 只能全表扫描 —— 消息表一个月就 180 万行，扫一次就崩。

ES 解决的问题：
· 倒排索引，全文检索走索引；
· 中文分词，能搜"退款"也能搜到"退货退款流程"；
· 检索 + 高亮 + 分页 + 聚合统计，坐席工作台直接能用。

另外 ES 在知识检索里还有第二个身份：BM25 那一路的召回器，和向量召回做 RRF 融合。 关键词精确命中（比如订单号、专有名词）向量检索往往不如 BM25，两路互补。
⑤ 为什么向量库要独立部署？
三个理由：
· 资源不能争：知识库检索是 AI 的输入，每次问答都要跑。如果和业务库放一起， 向量检索的 CPU / 内存消耗会直接影响下单、建单这些核心链路；
· 检索方式不同：需要 "BM25 + 向量" 的混合检索，这是 PGVector / Milvus 这类专用向量库的能力， MySQL 的全文索引做不到；
· 隔离更好做：每个客户一个独立向量 collection，物理隔离；再在检索时带 tenant_id 做 metadata 过滤， 防同一客户内部多品牌 / 多门店串数据。

初中级阶段我选了 PGVector 而不是 Milvus，理由是降低运维门槛、和已有的 PG 生态复用， 但要能说出取舍：数据量再上一个量级会考虑换 Milvus。
⑥ 为什么不用 Flowable / Activiti 做工作流？
因为我们的工单流转不需要通用工作流引擎。

实际需求是：按 ticket_template.flow_json 配置若干节点（提交 → 处理 → 待客户回复 → 已解决 → 已关闭）， 每次流转写一条 ticket_flow_log，并且和 SLA 计时 / paused_time 暂停计时 / 超时升级强联动。

用 Flowable 的代价：
· 引入 BPMN 建模、流程定义部署、各类 Activator / Listener，团队学习成本高；
· 多出一整套引擎表（ACT_* 几十张），和"约 29 张表"的口径也对不上；
· SLA 这种跟业务状态强耦合的计时逻辑，写在引擎监听器里反而比写在状态机里更难维护、更难排查。

所以最终选了"自定义状态机 + 模板配置 + 流转日志"的轻量方案： 状态枚举清晰、流转日志可追溯、SLA 计算和状态切换在同一个事务里，出问题看 ticket_flow_log 一眼定位。

这样答的好处：体现你是按需求选型，而不是"什么火用什么"。可以补一句 "如果将来要支持跨系统、多角色的复杂审批流，会再评估引入 Flowable"。

还有 4 句话，随时能接上

  • AI 解决率怎么算：robot_resolved 会话数 ÷ 机器人接待会话数。
  • 多模型可切换：ai_agent.model_code 配置化，DeepSeek 走性价比、通义千问走长文本；模型超时或失败自动降级到备用模型 + 记录降级次数。
  • 隔离怎么说：独立库 / schema 物理隔离 + 表内 tenant_id 二次防护 + 向量库 collection 隔离 + Redis key 前缀，四层防越权。
  • 人工兜底不可绕过：连续 N 次未识别、命中转人工关键词、顾客主动说"人工"、意图是投诉 → 一律转人工。

Demo 复现路线（从零搭一个最小可跑的 Demo）

6 个阶段，每个阶段都能独立跑起来、独立验证。前 5 个阶段是单体，第 6 阶段才拆成 7 个微服务 —— 先跑通再拆分。

阶段一：单体 Spring Boot + MySQL + Redis 起架子

目标：服务能起来、能连库、能读写缓存，把"工程底座"钉死。

要写的类 / 表 / 接口 工程：Spring Boot 2.7 工程 + MyBatis-Plus + Druid + Redis 客户端。
类：Tenant / SysUser / SkillGroup 实体与 Mapper、 TenantLineInnerInterceptor 配置类（自动拼 tenant_id）、RedisConfig、统一返回 Result<T>、全局异常处理。
表：tenant、sys_user、skill_group。
接口：POST /api/auth/login（返回 JWT）、 GET /api/tenant/agents。
验证标准 · 启动无报错，Nacos / 本地都能注册；
· 登录拿到 JWT，带 token 请求 /api/tenant/agents 能分页返回坐席；
· 不带 token 返回 401；
· 手动改库里另一个 tenant 的数据，接口查不到（隔离生效）；
· Redis 里能看到写入的 key（redis-cli keys '*'）。

阶段二：WebSocket 聊天 + 消息落库

目标：两个浏览器窗口能互相发消息，消息不丢、按序、能拉历史。

要写的类 / 表 / 接口 类：WebSocketConfig（注册 handler）、ChatWebSocketHandler、 SessionManager（Map<sessionId, WebSocketSession>）、 MessageService、RedisContextService（存最近 10 轮上下文，TTL 30 分钟）。
表：visitor、session、message。
接口：POST /api/session/start、 GET /api/session/{id}/messages、 WS 路径 /ws/chat?sessionId=。
验证标准 · 打开两个页面连同一 sessionId，一边发一边立刻收到；
· 刷新页面调 /messages 能拉到完整历史；
· 断网重连后消息不丢（client_msg_id 去重生效）；
· redis-cli ttl 看到上下文 key 是 1800 秒左右；
· 连发 100 条，库里顺序与发送顺序一致。

阶段三：坐席工作台 + 转工单

目标：坐席能接会话、能改状态、能把会话转成工单。

要写的类 / 表 / 接口 类：AgentAssignService（轮询 → 空闲优先 → 技能组匹配 → 上限 5 个）、 RedisLuaScript（原子扣减在服会话数）、TicketService、TicketFlowService、 SessionSummaryService（会话摘要，先用规则拼，后面阶段换成 AI）。
表：agent_status、session_transfer、quick_reply、 ticket、ticket_template、ticket_flow_log、ticket_comment。
接口：POST /api/session/{id}/transfer、 POST /api/tickets、 GET /api/tickets/{id}、 PUT /api/tickets/{id}/status。
验证标准 · 用 JMeter / 脚本并发 20 次转人工，坐席在服数不会超过 5（Lua 原子扣减生效）；
· 建单后 ticket_flow_log 有一条初始流转记录；
· 工单详情接口能一次返回流转日志 + 评论；
· 转工单时自动带入会话摘要和顾客信息快照（customer_snapshot_json）。

阶段四：工单 SLA 定时任务

目标：SLA 能算准、能暂停、能升级，且多实例不会重复执行。

要写的类 / 表 / 接口 类：SlaScanJob（XXL-JOB 分片广播）、SlaCalculator （真实剩余 = deadline + paused_time - now）、PauseTimeService（状态切"待客户回复"开始暂停、切回累加）、 EscalateService（剩余 20% 提醒、超时升级上级）。
表：ticket_sla，以及 ticket 的 sla_response_deadline / sla_resolve_deadline / paused_time / is_timeout 字段。
接口：PUT /api/tickets/{id}/status（含 SLA 校验）。
验证标准 · 建一张 SLA 首响 5 分钟的工单，到点后 is_timeout 变 1 并产生升级记录；
· 把工单切到"待客户回复"放 10 分钟，再切回来，剩余时间没有减少（暂停生效，paused_time 正确累加）；
· 起两个实例同时跑，同一张工单只被升级一次（分片广播生效）；
· 用长事务压测扫描任务，单轮扫描不拖垮库（加索引 (status, sla_resolve_deadline)）。

阶段五：知识库上传 + RAG 问答（接 DeepSeek）

目标：传一份文档进去，问一个相关问题，机器人能基于它回答并带引用；问不相关的能兜底转人工。

要写的类 / 表 / 接口 类：DocumentParseService（解析 + 切分 chunk）、EmbeddingService（调 embedding，写 PGVector）、 EsIndexService（写 ES 供 BM25）、HybridSearchService（向量 + BM25 → RRF 融合 → 重排 Top5）、 IntentService、ToolCallingService、LlmClient（DeepSeek）、 PostCheckService（召回为空或重排分不达标禁止生成，走兜底 + 转人工；向量相似度只作参考）、 AiExecutionLogger（异步写日志）。
表：knowledge_base、knowledge_document、knowledge_chunk、knowledge_faq、 ai_agent、ai_agent_tool、ai_conversation、ai_execution、ai_unanswered。
接口：POST /api/knowledge/documents、 POST /api/ai/chat（SSE 流式）、 POST /api/ai/knowledge/search（调检索用）、 GET /api/ai/executions。
验证标准 · 上传文档后 knowledge_document.parse_status 从"解析中"变"已完成"，chunk_count > 0；
· 问文档里的问题，答案是基于文档内容且带知识引用（不是瞎编）；
· 问一个文档里完全没有的问题，命中兜底话术并转人工，同时 ai_unanswered 多一条记录；
· 查 ai_execution：intent / retrieved_chunk_ids / prompt_tokens / latency_ms / is_transferred 都有值；
· 问"我的订单到哪了"，tool_calls_json 里能看到 queryLogistics 被调用；
· /api/ai/chat 是流式的（curl 能看到逐字输出）。

阶段六：编排成 7 个微服务

目标：把单体按业务边界拆成 7 个服务，加上网关、注册中心、消息队列，变成架构图里的样子。

要做的拆分与改造 拆服务：auth / customer / conversation / ticket / knowledge / ai / report 七个 Spring Boot 工程（report 最后做，先读别人的库出报表）。
加组件：Spring Cloud Gateway（路由 + JWT 校验 + tenantId 注入 + /inner/** 不放行）、 Nacos（注册 + 配置 + 动态刷新）、OpenFeign（/inner/* 六个内部调用）、Kafka（消息投递 / 工单事件 / 异步向量化 / 写执行日志）。
多实例一致性：Redis session_route:{sessionId} → {instanceId} 路由表 + Kafka 按 sessionId 分区 + 会话关闭删 key + TTL 30 分钟兜底。
中间件补齐：MinIO 存附件与知识文档、Elasticsearch 8 做全文检索与 BM25、PGVector 独立部署（每客户一个 collection）。
验证标准 · 起 2 个 conversation 实例，两个浏览器分别连不同实例，消息能互通且不串话，P99 投递 < 500ms；
· 关掉 knowledge 服务，/api/ai/chat 走降级（兜底转人工）而不是整个链路 500；
· 从网关访问 /inner/knowledge/search 返回 404 / 403（不放行）；
· 改 Nacos 里一个配置项，服务不重启就生效；
